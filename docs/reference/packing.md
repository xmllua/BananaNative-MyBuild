# Packing

## Build tools

### Homebrew .NET is on PATH but apphosts cannot find the runtime

- **Symptom:** the shader translator (a standalone .NET apphost) stops with exit code 131 and `.NET location: Not found`, even though `dotnet` is on `PATH`.
- **Cause:** standalone .NET apphosts search runtime roots and registered installations, not `PATH` ([.NET runtime discovery](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-environment-variables#dotnet_root-dotnet_rootx86-dotnet_root_x86-dotnet_root_x64)). Homebrew's formula installs the runtime under `libexec` and its `bin/dotnet` can be a wrapper that sets `DOTNET_ROOT` only for its own child ([Homebrew caveat](https://formulae.brew.sh/formula/dotnet)). Resolving that wrapper's symlink gives `bin`, not the runtime root.
- **Fix:** `scripts/build_ipa_from_nsp.py` `configure_dotnet` derives the root from the `Microsoft.NETCore.App` entry in `dotnet --list-runtimes`, using the build's environment, before any tool runs. It exports `DOTNET_ROOT` both to that environment and to `os.environ`, for tools launched with an explicit environment and those that inherit it. Caller-supplied roots, including architecture-specific overrides, retain precedence. A failed or malformed probe leaves the environment unchanged rather than guessing the wrapper's directory.
- **Found on:** [Balatro](../../dm/games/0100CD801CE5E000/README.md), first build with Homebrew .NET ([PR #284](https://github.com/seedds/nxnative/pull/284)). Applies to every game's build on that installation setup.

### The shader step stops with an empty `xlate_source`

- **Symptom:** the packing and captures succeed, then the shader step stops with `translation chain tools do not match the lock file: xlate_source: lock … / actual` and nothing after `actual`, which reads like a stale translator.
- **Cause:** the translator (`dmsh_xlate_bin/dmsh_xlate`) is a universal framework-dependent apphost. When it finds no .NET 10 runtime for the slice it starts as, it exits 131 with an empty stdout. A Python under Rosetta (an Intel Homebrew's) starts it as x86_64, and it finds only the arm64 .NET. An Intel .NET on Apple silicon, or a `DOTNET_ROOT` that names one, fails the same way. `tools_now` (then in `dmsh_chain.py`) kept only the stdout of `dmsh_xlate --source-sha`, without its exit code or stderr, so the apphost's own message was lost.
- **Fix:** the NSP script checks the environment before packing anything: `check_native_python` stops under Rosetta (`sysctl.proc_translated`), and `check_prereqs` starts the translator once with `--source-sha` and stops with its first message line (`check_translator`). It also checks glslang and, for an iPhone build, the iOS SDK (`check_ios_sdk`, before the Metal check, whose message would blame the Metal toolchain). `own_compilers.py` no longer asks a Mac-only shader build (`DMSH_TARGETS=mac`) for the iOS Metal compiler. `tool_lock.py` records `--source-sha`'s failure instead of its empty stdout (`xlate_embedded`: `does not run (<first message line>)`), so `dmsh_build.py` run directly and `--update-lock` stop with the same message as the NSP script, without the lock and rebuild lines. The tool checks used to be in `dmsh_chain.py`, which is part of the chain version and of every shader's cache key, so that fix rebuilt every library; they now live in `tool_lock.py`, outside both, and a change to them rebuilds nothing.
- **Found on:** NX2Apple builds ([LNPANDY/NX2Apple#31](https://github.com/LNPANDY/NX2Apple/issues/31), item 3; [PR #477](https://github.com/seedds/nxnative/pull/477), [PR #487](https://github.com/seedds/nxnative/pull/487)); reproduced with `arch -x86_64`. Applies to every game.

## IPA archives

### A streamed file changes size and the IPA fails its CRC check

- **Symptom:** packing succeeds, but `unzip -t` or Python's `ZipFile.testzip()` reports a bad CRC for a large deflated file.
- **Cause:** `pack_ipa.py` wrote the uncompressed size collected before reading. Its streaming check compared the output size only for stored files, so a compressible file that grew or shrank still published an archive with the old size.
- **Fix:** count uncompressed bytes as they are read and compare them with the listed size before completing either streamed method. A mismatch stops the pack and removes the partial archive, preserving the previous IPA and its reuse index. Regression tests cover growth and shrinkage with both deflate and store.
- **Found on:** synthetic IPA inputs while reviewing [PR #279](https://github.com/seedds/nxnative/pull/279); no game files required.

## RomFS images

### RomFS folder transfers fail or leave stale game files

- **Symptom:** `devicectl` copying a large RomFS folder fails with POSIX error 24 (`EMFILE`) or spends most of its time on small files; deleting an old folder during iOS startup hits the launch watchdog. A push after changing extracted files can also keep sending old assets if an image is reused solely because it exists.
- **Cause:** a folder transfer performs hundreds of thousands of file operations. The image cache must track its source tree, and magic plus total length cannot establish that an image's index is valid. Accepting that weak check before deleting the working folder loses the fallback when mounting later rejects the index.
- **Fix:** `dm/tools/romfs_image.py` packs one `DMROMFS1` file: a 32-byte header, file bytes, then the index and name pool. Each directory has a sorted, contiguous run of child entries; the host binary-searches each path component and reads file ranges with `pread` through one descriptor per mount. Overlay folders keep precedence and directory listings merge both sources. The shared `dm/host/romfs_image.h` loader checks the full index before either mounting or iOS folder cleanup: length, entry and name bounds, file ranges, a rooted breadth-first directory tree, and sorted, unique child names. It supports an empty root too. Invalid images fall back to the folders on iOS; an explicit invalid `DM_ROMFS` image is refused with a `[RED]` line. The index check detects interrupted sequential transfers and structural damage, not same-length corruption inside file contents. The packer publishes by rename only after the source stays stable. Its reuse stamp tracks source names and file metadata including ctime, the packer and image identity; the push helper always checks it, and `--repack` forces a rebuild. Usage: [Quick reinstalls](../development.md#quick-reinstalls).
- **Found on:** [Tears of the Kingdom](../../dm/games/0100F2C0115B6000/README.md#files-and-shaders), whose 304,000-file transfer and startup deletion failures are reported in [PR #369](https://github.com/seedds/nxnative/pull/369). [ANIMAL WELL](../../dm/games/010020D01AD24000/README.md#files) provides the empty-image boot case. Synthetic packer/host tests cover actual file reads, case aliases, overlay merging, corrupt indexes and changed sources; the macOS Foundation test executes iOS's locator to check that rejected images preserve its folder.

### A stale `DM_ROMFS` path crashes the game soon after `nnMain`

- **Symptom:** a direct `dmhost` run logs `fs mount rom: → <path> (read-only)` for a path that does not exist, then crashes in the game's code a fraction of a second after `nnMain` (Echoes of Wisdom: `CRASH sig=11 addr=0x88` 0.3 s in). The host now stops at the mount instead with `FATAL the game files <path> (rom:) are missing: neither a folder nor a RomFS image`.
- **Cause:** an old run command still named the extraction's `RomFS` folder after a rebuild replaced it with `RomFS.img` ([RomFS folder transfers](#romfs-folder-transfers-fail-or-leave-stale-game-files)). The read-only mount accepted any path, so every read failed and the game used the missing data. The iOS app and the Mac app launcher check their game files before they start the host; direct runs had no such check.
- **Fix:** `mount_ex` (`dm/host/hle_fs.c`) stops on a read-only, non-save mount whose path is neither a folder nor a regular file, with the same `stat` that tells an image from a folder. Add-on content and system data check their paths before mounting, so only the rom mount (`DM_ROMFS`, or `$DM_ROOT/romfs` when it is unset) reaches it. `dm/host/tests/t_fs.c` checks a missing path and a fifo in a forked child.
- **Found on:** [Echoes of Wisdom](../../dm/games/01008CF01BAAC000/README.md#found-on-this-game) 1.1.0 on the Mac ([issue #615](https://github.com/seedds/nxnative/issues/615), [PR #616](https://github.com/seedds/nxnative/pull/616)).

### Separate RomFS deployment loses its image or folder fallback

- **Symptom:** a successful `--romfs separate --no-keep-extracted` build prints a push command pointing at deleted game files. On iOS, a complete image for another build can also prevent startup despite a valid `Documents/romfs` folder.
- **Cause:** separate mode omitted the extraction-retention check, so normal post-build cleanup deleted the image needed for transfer. The startup identity rejection returned before the existing folder lookup.
- **Fix:** reject separate mode without `--keep-extracted` before extraction or building. Reject a mismatching image while continuing to the validated folder fallback; move a folder aside for deletion only after accepting the image. Matching images and the default bundled route retain their behavior. The identity covers image size, header and index, not same-length file-content changes.
- **Found on:** synthetic CLI and Foundation startup tests while integrating [PR #493](https://github.com/seedds/nxnative/pull/493), after [PR #478](https://github.com/seedds/nxnative/pull/478); no game or device is needed to reproduce either failure.

### A hand-copied RomFS.img is not found on iOS

- **Symptom:** a `--romfs separate` app whose image was copied into its Documents folder by hand (Finder, the Files app, a LiveContainer guest) logs `boot: game files not found (Documents/romfs.img, Documents/romfs or <App>/romfs)`, and a build with `romfs.id` shows "There is no game file image on this device.", though the complete image is there. Renaming it to `romfs.img` makes the game start.
- **Cause:** the NSP script writes the image as `extract/<version>/RomFS.img`, and `push_romfs.sh` copies it to `Documents/romfs.img`. A hand copy keeps the source's name. The Mac's file system ignores letter case, so the mismatch never shows there, but iOS's does not, and `main.m` looked up only the exact `romfs.img`.
- **Fix:** `main.m` (`romfs_document_images`) lists Documents for `romfs.img` in any letter case, `romfs.img` itself first, and takes the first that is complete and passes the `romfs.id` check; a rejected or incomplete one falls through to the next spelling, then to the folders. The identity report, the backup exclusion and the log lines use the names found. Folder names (`Documents/romfs`) are still matched exactly.
- **Found on:** South Park: The Fractured But Whole 1.05 (`01008F2005154000`, no profile here) on an iPhone 15 Pro Max, [issue #582](https://github.com/seedds/nxnative/issues/582). The Foundation startup test runs the locator on a case-sensitive APFS disk image.

### Building creates a full RomFS tree before packing its image

- **Symptom:** reducing the iPhone transfer to one image still creates thousands of resource files on the Mac, and build scanners require the expanded folder.
- **Cause:** folder extraction followed by a separate image pack duplicates the work; ordinary filesystem APIs cannot address files inside an image.
- **Fix:** the NSP pipeline packs each version's RomFS folder of the dump straight into one `DMROMFS1` image (`scripts/pack_dump.py`, `dm/tools/romfs_image.py`): the writer streams file bytes into a temporary image, appends the sorted directory index and publishes by rename. ExeFS remains expanded; RomFS and each DLC remain one physical file. `dm/tools/romfs.py` gives the scanners read-only virtual paths, bounded seeks and archive mappings (Python 3.12+), without changing the process's standard filesystem APIs. The IPA packer maps the physical image to `Payload/DmIOS.app/romfs.img`; iOS and the Mac launcher validate and mount it in place. Neither installation nor startup expands the resource files. Documents overrides and legacy folder inputs remain supported. A source image is uncompressed; the IPA can deflate it, so file-count reduction does not imply a smaller installed byte count. Full images for separate game versions cannot share unchanged individual files through APFS clones as legacy folder extraction did.
- **Found on:** [ANIMAL WELL](../../dm/games/010020D01AD24000/README.md#files), whose direct image is an empty root (56 bytes); the local Baba Is You provisional build exercises 6,374 files in a 103,473,292-byte image, 131 shaders and an unsigned IPA containing only the single image entry. [Raging Loop](../../dm/games/010020400E1C2000/README.md#files-and-shaders) supplies Unity resources: all 1,473 source manifest entries match the image, and every registered shader remains in the scan. Synthetic integration tests read unaligned archive ranges, and exercise IPA mapping, Xcode staging and bundled-image startup.

### The zstd command given a path inside the image

- **Symptom:** the NSP script stops at the shader split of a registered profile with `[RED] 13744 file(s) could not be read, their shaders are left out (first: AI/FileEntry/FileEntry.Product.100.byml.zs: CalledProcessError: Command ['zstd', '-d', '-c', '-q', '…/extract/v0/RomFS.img/AI/…'] returned non-zero exit status 1.)`.
- **Cause:** `shader_split.py`'s `unzs` read a `.zs` file through `romfs.open`, which reads inside the image, but then handed its path to the `zstd` command, which can only open real files (`Not a directory`).
- **Fix:** `unzs` feeds the command the bytes it read (`input=`). No other tool hands an external command a path inside the image. Test: `test_romfs_read.py` `test_zstd_file_inside_an_image`.
- **Found on:** [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md#shaders): every file of its RomFS is zstd-compressed, 13,744 left out in both versions; the first image-backed build after the folder extraction.

## Add-on content

### DLC in Documents is ignored or removed DLC remains installed

- **Symptom:** a game's DLC works only when packed inside its IPA, although its base RomFS can be deployed separately. After pushing a smaller DLC set, removed indices can remain reported as owned and mounted.
- **Cause:** the iOS launcher originally checked only `<App>/aoc`. Merely adding `Documents/aoc` discovery is insufficient: `devicectl device copy to` merges directories by default, retaining removed indices, and skipping a build with no DLC leaves the entire previous set behind. The host counts and mounts the numeric entries under `DM_AOC_DIR`, so those leftovers remain active.
- **Fix:** `aoc_locate` in `dm/ios/Sources/main.m` preserves an explicit `DM_AOC_DIR` from the launch environment or `env.txt`; otherwise it selects the first directory at `Documents/aoc`, then `<App>/aoc`, and logs `boot: DLC from <path>`. `Documents/aoc` is excluded from backups. Given `resources.env`, `scripts/push_romfs.sh` transfers the complete `DM_RESOURCE_AOC` directory with `--remove-existing-content true`, replacing old `<index>.img` files and legacy `<index>/` trees. An empty or omitted value sends an empty directory, clearing previous content and explicitly selecting no external DLC rather than falling back to bundled content. A nonempty path that is unavailable stops before any transfer. A direct RomFS-image push has no DLC metadata and leaves DLC unchanged. Transfers are not atomic: rerun a failed push before launching the game. Usage: [Quick reinstalls](../development.md#quick-reinstalls).
- **Found on:** synthetic startup and transfer fixtures while reviewing [PR #486](https://github.com/seedds/nxnative/pull/486), part of [issue #388](https://github.com/seedds/nxnative/issues/388). The Foundation fixture runs the actual iOS locator; the push-helper fixture models devicectl's documented merge and replacement behavior, including smaller and empty DLC sets and transfer failure. Applies to every game; no device gameplay validation was performed.

### DLC links in shared storage (Android)

- **Symptom:** no game sees its DLC on Android: every run log says `[dm] aoc: reporting 0 add-on contents {} (/storage/emulated/0/Android/data/<app>/files/aoc/<title ID>)`, although the pack's `pack.tsv` has an `aoc` row and the dump has the DLC's `dlc/<DLC title ID>/<n>/romfs` folder (the same dump shows the DLC in another app).
- **Cause:** `GameActivity` made `DM_AOC_DIR/<index>` (or `<index>.nup`) as symbolic links in `<external files>/aoc/<title ID>`. The external files folder is shared storage, served through FUSE, which refuses `symlink` (the errno is not yet confirmed on a phone: the `[RED] [nxlaunch] DLC: cannot link` line below names it; open). The launcher dropped the `ErrnoException`, so the folder stayed empty and `hle_misc.c` `aoc_load` listed nothing.
- **Fix:** the links are made in internal app storage, `<files>/aoc/<title ID>` (`getFilesDir()`, `/data/user/0/<app>/files`), where symbolic links work; their targets stay where they are (the dump on shared storage, which the game's process already reads for its RomFS; `fd:<n>/<name>` for a `.nup` used where it is, which `aoc_dir` reads with `readlink`). The old external folder is removed. `Pack.makeAocLinks` makes them and returns a line for each link it cannot make; the run log has `[nxlaunch] DLC: <n> links in DM_AOC_DIR <dir> [<names>]` and a `[RED] [nxlaunch] DLC: cannot link …: <errno>` line for each failure. Test: `NupJvmTest` `aocLinkDir` (`test_nup.py`).
- **Found on:** [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game): every one of 377 phone logs reported 0 add-on contents, and a player's report (Lenovo Legion Y700 Gen 5, Android 16, v0.2.0). Applies to every game.

### A DLC that cannot be read stops a .nup game at boot (Android)

- **Symptom:** a game played from a `.nup` stops right after boot, since v0.2.2: `FATAL the game files <file>.nup:aoc/1 (<mount>:) cannot be used as a NUP package (the log line above says why)`, after `[RED] fs NUP …:aoc/1: no package aoc/1 with a RomFS`. `aoc/<index>` is the host's own selector for an add-on mount (`nup_image.h`), not a name from `pack.tsv`. The player may have no DLC at all; v0.2.1 and earlier started the same game.
- **Cause:** two faults. (1) `Pack.aocLinks` linked `DM_AOC_DIR/<index>.nup` for every `aoc` row of `pack.tsv`: to the game's `.nup` when it has that add-on, else to the `.nup` the row names when that file is there, else to the game's own `.nup` regardless. A pack made from a folder dump (row `dlc/<DLC title ID>/0/romfs`), from another `.nup` that had the DLC, or before the `.nup` was renamed, so got a link to a `.nup` without the add-on. Since v0.1.1 (`9a7c2670`); it did no harm until v0.2.2 (`f86575b0`, [DLC links in shared storage](#dlc-links-in-shared-storage-android)) made the links work. (2) The host trusted the folder: `hle_misc.c` `aoc_load` reported every numbered entry of `DM_AOC_DIR` as owned, the game mounted it, and `hle_fs.c` `mount_ex` treats game files that do not open as fatal, which is right for the game's RomFS but not for a DLC.
- **Fix:** `Pack.aocLinks` links a `.nup` only when it has an addon package of that index with a RomFS (`hasAddon`), else no link and a `[RED] [nxlaunch] DLC: add-on <index> … the game runs without it` line; a folder game's missing DLC folder gets the same line. In the host, `aoc_load` reports an index as owned only when `dm_aoc_usable` opens it (a folder, a complete RomFS image, or a `.nup` with that add-on); one that does not is a `[RED] aoc: add-on content <index> … the game runs without it` line, and the game sees it as not owned, as on hardware without the DLC. `h_fs_MountAoc` mounts softly: files that no longer open answer "target not found" (fs 2-1002) with a `[RED]` line, never a FATAL. Applies to folder dumps and `.nup` alike. Tests: `t_fs` (a `.nup` without the add-on, a link to nothing, a cut-off image), `t_pctl` (the owned list leaves out what does not open), `NupJvmTest` (`test_nup.py`).
- **Found on:** [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game): a player's `.nup` on v0.2.3 (Forgejo #30, Poco F5 Pro). Applies to every game with an `aoc` row.

## Launcher metadata

### A Mac front end's default settings change Metal execution paths

- **Symptom:** starting a Mac app through a front end with unchanged settings enables the encode thread, and can disable Metal 4 pipelines and the pipeline archive; starting the same app from Finder keeps the host's defaults.
- **Cause:** Mac `launcher.json` reused iOS defaults from `settings.tsv`. `rec_on` in `nvn_rec.h` defaults off on Mac and on on iOS; `pso4_on` in `nvn_mtl.m` defaults on on Mac and follows the profile on iOS. The exported defaults instead enabled the encode thread everywhere and followed the profile for Metal 4 everywhere. A front end applying those values changed the Mac host's behavior without a player override.
- **Fix:** a setting's default may be `<ios>|<mac>`, selected before resolving a profile macro or build variable. Metal 4 uses `DM_GAME_PSO_MTL4|1`, the encode thread `1|0`. The generator validates the platform and the pair. Tests cover a profile with Metal 4 on and one with it off, and both platforms; the host and shader chain are unchanged.
- **Found on:** synthetic metadata generation for [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md) while reviewing [PR #352](https://github.com/seedds/nxnative/pull/352); checked against the native defaults, without a gameplay run.

### The Mac settings window stays on screen after Play

- **Symptom:** in a Mac app, the settings window stays on screen after **Play**, not responding (a spinning cursor over it), until the game ends.
- **Cause:** the window runs in the launcher's process (`dm/mac/Launcher.swift`). `finish` ordered the window out and stopped `NSApp.run`; then `launcher.c` started the host and blocked in `waitpid`, so the main thread never ran another run-loop pass. A window's order-out is committed only at the end of such a pass, and its default fade-out runs over several passes, so the window never left the screen. With the run loop kept running, the same order-out took effect at once.
- **Fix:** `finish` sets the window's `animationBehavior` to `.none` before the order-out, and `dm_mac_launcher` calls `CATransaction.flush()` after `run()` returns, before it hands back to `launcher.c`. Neither alone was enough. Check: a copy of the window with a timed Play and a `CGWindowListCopyWindowInfo` probe while the thread then blocks; the window was still listed 2 and 4 s after Play before the fix, and gone 3 times in 3 after it. `test_launcher_storage.py` and `test_nsp_mac_app.py` pass.
- **Found on:** the Mac app of [Breath of the Wild](../../dm/games/01007EF00011E000/README.md); applies to every Mac app.

## External drives

### A build folder on an exFAT drive fails to remove a folder

- **Symptom:** with the build folder on an exFAT or FAT drive, a stage stops with `FileNotFoundError` on a `._<name>` path inside `<id>_build/` and the next run fails on the half-deleted folder.
- **Cause:** these file systems have no extended attributes, so macOS keeps a file's attributes (a download's quarantine flag) in an AppleDouble file `._<name>` beside it, and deletes it with the file. Deleting `x` takes `._x` with it, so `shutil.rmtree`'s later unlink of the listed `._x` found it gone; before Python 3.13 that error ended the removal.
- **Fix:** the script's `rmtree` passes ENOENT from `shutil.rmtree` (the entry is gone, which is the goal) and raises every other error. `dm/tools/tests/test_nsp_external_drive.py` covers it without game files.
- **Found on:** the NX2Apple fork's users, who keep games on external drives ([PR #476](https://github.com/seedds/nxnative/pull/476), part of [issue #388](https://github.com/seedds/nxnative/issues/388)); reproduced on an exFAT disk image made with `hdiutil create -fs ExFAT`. Applies to every game.

### The c1 guard stops on an AppleDouble file after the shader build

- **Symptom:** with the build folder on an exFAT or FAT drive, the shader step compiles every library and then stops in `c1_guard.py` with `UnicodeDecodeError: 'utf-8' codec can't decode byte …` (dmsh_build.py: `[RED] c1_guard.py failed`), reading a `._<key>_b.metal`.
- **Cause:** the same AppleDouble files as above, beside the shader build's outputs. `c1_guard.py` took every name ending in `.metal` for a shader's MSL and read the binary `._` file as text. `cb_extent.py` (every `_b.json`) skipped it only because it ignores what it cannot parse, and `dmsh_mtlcache.py` (every `_b.metal`) took `._<key>_b` for a shader, found no readable reflection for it and so filled the Metal cache from none of that folder's libraries.
- **Fix:** the three take only the names the shader build writes, `<16 hex key>_b….metal` / `.json` as `dmsh_build.py` (`OUT_KEY`) and `regress.py` already did: `c1_guard.py` `outputs` (which `cb_extent.py` uses too) and `dmsh_mtlcache.py` `OUTPUT`. None of them is part of the chain version. `dm/tools/tests/test_nsp_chain.py` runs both table tools on a folder with `._` files; the old `c1_guard.py` stops on it. On 13 Sentinels' 751 shaders both tables are unchanged.
- **Found on:** a user's iOS shader build on an external drive ([PR #555](https://github.com/seedds/nxnative/pull/555)). Applies to every NVN game.

## Compressed inputs

### ZBIC-compressed NSO segments

- **Symptom:** the NSP script or any module tool stops on `main`: `compressed with zstd (NSO flag bit 7), which this loader does not decode yet`; with the decoder but with neither libzbicdec nor the zbic package, `ZBIC (zstd) segments need libzbicdec (…) or the zbic package (python3 -m pip install zbic==1.0.1.post1)`.
- **Cause:** from system 22.0.0, an NSO may store its segments as **ZBIC**, NSO flag bit 7 for the whole module (the per-segment compression and check-hash bits keep their meaning). ZBIC is Nintendo's variant of zstd, not a container around standard frames: its frames start with the magic `ZBIC` and its FSE tables are written with binary interpolative coding, so neither `compression.zstd` nor the `zstd` command can read them.
- **Fix:** `dm/tools/nso.py` decodes such segments with libzbicdec ([dm/third_party/zstd-zbic](../../dm/third_party/zstd-zbic/README.md): zstd 1.5.7's decoder with an independent MIT reader of ZBIC's tables, through ctypes: `DM_ZBIC_LIB`, or `libzbicdec.so` on Android), else with the [`zbic`](https://pypi.org/project/zbic/) package (Kinnay's, zstd with Atmosphère's ZBIC changes, GPL-2.0), looked for only for a flag-bit-7 module, so an LZ4 title needs nothing new; every segment is still held to the header's size and SHA-256. zstd has no fixed ratio bound, so a ZBIC segment is held only to its own size, where an LZ4 one is also held to 255 bytes per stored byte. On a PC or Mac install the package with the other tools (README, step 1). The Android packer needs a decoder too (resolved in 0.2.2; on 0.2.1 Prepare of The Legend of Zelda: Ocarina of Time stopped at the rewrite with this message on the phone and in a fresh PC or Mac environment): the APK carries `libzbicdec.so`, built with the NDK by `android/ondevice/build.sh`, and no GPL code (licences: [NOTICE.md](../../android/NOTICE.md)); `android/environment.yml` pins `zbic==1.0.1.post1` and `scripts/bananative_env.py` checks it; `pack_android.py` names a missing decoder before any work when a module is ZBIC.
- **Check:** Well Dweller's `main` decodes to 85,370,056 bytes with segments `0x39680d0 / 0x9f7e74 / 0x9b1930`, every SHA-256 matching; `dm/tools/tests/test_nso.py` checks that a flag-bit-7 module whose segments are not ZBIC is an Error naming ZBIC, that ZBIC segments decode to the LZ4 module's image with each decoder there is, that libzbicdec decodes a committed ZBIC stream of synthetic text (`zbic_synthetic.zbic`, with low-probability counts) and refuses it damaged, that it agrees with the zbic package, and that with neither the Error names both.
- **Found on:** [Well Dweller](../../dm/games/0100217023F6C000/README.md) (SDK 22.2.0); [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (the Android packer).

## Packing on the phone

### Prepare is not offered for a game whose supported build is its base game

- **Symptom:** on Android, **Add game** on a dump folder with `base/exefs` and `base/romfs` but no `updates/` (or a `.nup` with a base package only) does not offer Prepare: it asks to "Pick the pack folder", the game card has no Prepare, and ⋯ has no Prepare again. Only a pack made on a Mac works.
- **Cause:** the app's test of whether a picked folder is a whole dump (`Ondevice.isDump`) asked for an `updates/` folder (and, for a `.nup`, an update package). `DumpCheck`, `pack_dump.py` and the job's steps already took version 0 (the base game itself) as the build to prepare; only this first test refused it. A game whose supported build ships in its base Application content has no update to dump.
- **Fix:** `Pack.isDump` (pure Java, run by `NupJvmTest`): a dump is `base/exefs/main.npdm` and either an `updates/` folder or the base game's own `exefs/main` with a non-empty `romfs/`; a `.nup` is a base package with an update package or with an ExeFS and a RomFS of its own. One version's folder is still not a dump. `DumpCheck` names version 0 as "the base game" in its messages (`Profile.supported`, `Profile.versionName`), and Prepare's dialogs give the time from the game's shader count (`ShaderLibs.jobMinutesText`) instead of a fixed figure.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#prepare-on-the-phone-180) 1.8.0 (version 0). Applies to every game whose profile's build is its base.

### "Pack from other tools" on a pack the app made itself

- **Symptom:** Banana Native's Home shows the "Pack from other tools" chip (the card's note that the code is from other tools) on a pack its own Prepare made, though no rewriter file changed since; ⋯ › **Prepare again** rewrites the code to clear it.
- **Cause:** the rewrite key (`<module>.android.key`, `pack_android.py` `rewrite_key`, the launcher's `RewriteKey`) hashed the profile's whole `game.tsv`. The rewriter reads only its `build` rows (`patch_nso.py`, for the match cuts of a build without registered cuts; no other `REWRITER` file reads the profile); the other rows are the host's (GPU timing, window size, graphics scale). Any such row added to a profile made every existing pack of that game stale: Donkey Kong Bananza's `gpu_timestamps` / `android_window` / `romfs_check` rows, Mario Kart World's `graphics_scale` rows.
- **Fix:** the key hashes the build rows only (`build_rows`, normalized: each cell stripped, other rows left out; under the name `game.tsv build rows`). A key of the earlier formula still counts, with the APK's `game.tsv` or with the pack's own copy (`<pack>/game.tsv`, which `pack_android.py` writes after the rewrite) when that copy's build rows are the profile's: the key proves the copy is the file it was made with. The same rule in `pack_android.py` (`rewrite_keys`: the module is kept) and the launcher (`RewriteKey.keys`, `PackCheck.code`). The packer writes such a key as the current one before it replaces the pack's copy (`upgrade_keys`; the phone's shaders-only pack step replaces it too), so the pack does not lose it. A pack without a copy is judged as before. Tests: `dm/tools/tests/test_android_rewritekey.py` (Python and `RewriteKeyJvmTest`).
- **Found on:** [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game) (the test phone's packs of update 458752, keys of the rewriter at ffe72d71 and b4269ab1) and [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#found-on-this-game) 1.8.0 (all four modules); each now counts as current, checked with the Python and the Java key on the packs pulled from the phone. Applies to every game.

### A game with several registered builds (Android)

- **Symptom:** `pack_android.py` on the dump of one build of a game that registers two stops with `no subsdk1 (the profile's modules are …)` (a build with one module less), flags the modules of a build the profile registers in red (`[RED] main build … is not the profile's build …`), or stops with `the dump's shaders lack N of the M in the profile's shader_map.tsv … the dump is of another version` (a build with a few other shaders).
- **Cause:** the packer took the profile's one module list for every dump, compared a module's build ID with the last `build` row only (`known[m]` kept one ID a module), and wanted every key of `shader_map.tsv` in the dump's split. Two releases of one game (Mario Kart World 1.0.0, SDK 19.3.3, and 1.8.0, SDK 21.4.0) differ in one module (1.8.0 has a `subsdk1`) and in a few shaders, which are otherwise the same game's, found by key.
- **Fix:** `modules` lists every module of either build and a dump takes those of the build row it matches (`dump_modules`: all of them, unless the dump has fewer and a row names exactly those with the dump's build IDs). Every build row counts when a module's build ID is checked (`unregistered`). The profile's `shader_optional.tsv` names the keys of its map that only some builds have (`optional_keys`): the split may lack exactly those, any other missing key still stops the pack, and the lacking ones are written to `<package>/_absent.tsv` (`split_shaders`).
- **Check:** `dm/tools/tests/test_pack_android.py` (every row counts), `test_pack_android_builds.py` (modules of each build row, optional keys, the package's `_absent.tsv`, `absent_optional`) and `test_android_shader_delta.py` (`ShaderLibs.absentOptional`).
- **Fix (library, launcher):** neither change touches a chain file, so no library version moves. `pack_shaders` reads `<package>/_absent.tsv`. When `shader_optional.tsv` names every key in it (`absent_optional`), it runs `vk_android_build.py` with `DMSH_VK_REQUIRE_ALL=0`, which leaves those keys out with one `[RED]` count line. The launcher's split check (`PackService.splitMatchesProfile`) takes a split whose map is the profile's except for optional keys (`ShaderLibs.absentOptional`). Its shaders step then passes the map's other keys as a key list, so `DMSH_VK_REQUIRE_ALL=1` still refuses a shader that did not build, and the card does not say the dump lacks shaders.
- **Open:** not yet run on a dump that lacks an optional key, on the phone or on the PC.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#builds).

### The phone's shaders step fails on a shader that does not build on the Mac either

- **Symptom:** the shaders step of Prepare stops with `[RED] 1 of 11604 shaders did not build: no library written (DMSH_VK_REQUIRE_ALL)` after a `[RED] translation failed: 1 shaders, e.g. <key>` line; Retry translates that shader again and stops the same way. A Mac build of the same version writes the library and logs `[RED] delta check: <key>: not in the library (translation failed: …), the manifest has -`.
- **Cause:** `DMSH_VK_REQUIRE_ALL=1` (the phone's switch: a library missing shaders must never pass as finished) asked for every shader of the profile's map to build. A shader the translator cannot translate yet is missing from the Mac's library too, and the profile's delta manifest (`vk_delta.tsv`, a full Mac build of that library version) records it as `-`; the rule asked the phone for more than the Mac makes. The delta check compared `-` with "no entry" as two different values.
- **Fix:** the rule is "every shader the Mac's build of this version holds": `vk_android_build.py` takes the shaders the profile's manifest of this version has as `-` out of the failures (`vk_android_delta.py not_built_there`) and names them in one plain line; any other failure still writes no library. Without a manifest of this version (a tools change before `--publish-delta`) every shader must build, as before. The delta check takes a `-` shader that is not in the library as the manifest has it (`entry_as_manifest`). The library is byte-identical to the one before the change (`vk_android_same.tsv` row `088af9aa5109`).
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#prepare-on-the-phone-180) 1.8.0: compute `078997bf631992c5` (Ampere instruction `0x481`, not implemented), 11,603 of 11,604 shaders by design.

### Each Retry of the shaders step stops at a new result file "cut short"

- **Symptom:** Prepare stops in the shaders step (around 96 %) with `[RED] …/ondevice/xlate/<key>.r is cut short: delete it and run again`; after deleting that file, Retry stops the same way at another key, every time a new one. The log shows the step was stopped and resumed before (batches of fewer than 64 shaders).
- **Cause:** `vk_android_build.py` `write_result` wrote `<key>.r.tmp` and renamed it without syncing it, so after the process was killed or the phone stopped, shared storage (FUSE) could keep the rename but not the whole file. A file shorter than its head says is not a result, but `result_head` checked only the head (magic and JSON), so the shader counted as done and was skipped; `read_result` then stopped the whole build at the first cut file, and the next Retry found the next one.
- **Fix:** `write_result` (and `write_library`) syncs the file before the rename. `result_file` checks the whole length (12 + head + every module's stored length equals the file's size); a cut file is not a result, is reported once (`[RED] N result files are cut short (from <key>, …): translated again`) and its shader is translated in the same run. A file cut later (`read_result` raises `ResultCut`) is deleted and translated again before the library is written; only a file still cut after that stops the build. Tests: `dm/tools/tests/test_vk_android_results.py`.
- **Found on:** [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game) on an AYN Odin 2 Pro (Snapdragon 8 Gen 2, Android 13; GitHub issue #82). Applies to every game prepared on the phone.

### Prepare stops at "Finishing the pack": no complete main (Android)

- **Symptom:** Prepare goes straight to its last step, "Finishing the pack", and stops there: `pack_android.py --keep-code` says the rewrite step has not finished for `main` (`main.patched.bin and main.android.key missing`), "no complete main (patched.bin and its key)" on the card; Retry stops the same way. The job's earlier steps say done.
- **Cause:** the job and its pack live in different places. `job.json` and the working files (`split/`, `xlate/`, `lib/`) are in the work folder beside the dump on shared storage (`<dump>/../<id>-work/ondevice/`, `Job.fileOf`), which outlives the app; the pack the job writes, rewritten code included, is in the app's own storage (`files/packs/<id>/`, `AppStorage.pack`), which Android deletes when the app is uninstalled (for example to move from an unofficial build to the official one). A job paused or stopped after its rewrite step, resumed by the newly installed app, still recorded the rewrite done: `PackService.work` ran the first step not done (`Job.next`, by `job.json` alone), finished the shaders, and the pack step found no code.
- **Fix:** a step recorded done is checked against its outputs while a later step still needs them (`Job.dropMissing`, `Outputs.redo`): the rewrite's `<module>.patched.bin` and `<module>.android.key` in the pack folder for every module it wrote (`code_modules` in `job.json`, recorded when the step is done; `main` for an older job), the shaders step's library `v-<V>/dmsh_vk.lib` in the folder the pack step copies from. A step whose outputs went is set pending, with the steps made from it, and runs again: when the job starts or resumes, and again in the pack step before `--keep-code`, which goes back to the missing step instead of stopping (a step whose outputs vanish right after it ran in the same run fails with Retry instead of looping). Finished shader results in `xlate/` stay, so the shaders are kept. The simulated engine writes the module keys too. Tests: `OutputsJvmTest` (`dm/tools/tests/test_android_outputs.py`).
- **Found on:** [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game) on an AYN Odin 2 Pro (Snapdragon 8 Gen 2, Android 13; Forgejo issue #3): code rewritten on 0.1.5, shaders finished on v0.2.1 after a reinstall. Applies to every game prepared on the phone (current: JVM tests only, not yet run on a phone).

### Prepare stays at 1 % while it rewrites the code

- **Symptom:** Prepare's bar sits at 1 % under "Rewriting the game code" for minutes, with no count, and looks stalled; players reported it on 0.2.1.
- **Cause:** 1 % is the end of "Checking the dump" (the steps' weights are 1, 5, 12, 78 and 4, `Job.WEIGHT`). The rewrite step that follows (`pack_android.py --code-only --in-process`, one worker) printed no progress lines: `patch_nso.py`'s output went only into `rewrite_<module>.log`, so the bar did not move until every module was done. With one worker the rewrite of a large `main` takes about a minute on the Mac (Splatoon Raiders' 41 MB `main`: x18 scan 16 s, the instruction scan 5 s, functions 8 s, spin waits 32 s) and several times that on a phone.
- **Fix:** `patch_nso.py` prints `progress <n> 1000 <phase>` lines (`PHASES`: each phase a fixed share measured as above, its own count inside it, at most one line a second; one worker splits the spin wait search into 64 jobs instead of 8 so the lines come often enough; the regions are sorted afterwards, so the output is the same). `run_in_process` passes them on to the step log through `ProgressTee`, each module given a share of the step by its code size (`nso_text_size`), as `progress <n> 1000 code`; the card shows "Rewriting the game code (41 %)" (`Job.stepText`). The rewrite output is byte-identical (Splatoon Raiders' and Ocarina of Time's three modules, one and four workers; only `build_src.sha256` differs), so the earlier `patch_nso.py` is in `dm/tools/rewriter_equiv` and existing packs stay current. Tests: `test_pack_android.py` (`Progress`).
- **Found on:** [Splatoon Raiders](../../dm/games/0400380020056000/README.md#found-on-this-game) (measured); applies to every game prepared on the phone.

### Prepare stays paused as "too hot" on a phone that is cool

- **Symptom:** Prepare shows `Paused: the phone is too hot. it goes on when it has cooled. Checking the dump.` at 1 % and never goes on, although the device reads about 45 °C; no step log is written, since the job waits before its first step.
- **Cause:** `PackService` pauses the job while the thermal status (`PowerManager.getCurrentThermalStatus`) is `SEVERE` or worse and goes on at `MODERATE` or better, as documented (ONDEVICE.md). The rule held; what is open is the handheld's thermal HAL, which by all signs reported `SEVERE` (or a status stuck there) while the device was cool (its `dumpsys thermalservice` was asked for). The pause gave neither the status nor the headroom it decided on, and offered no way past it.
- **Fix:** the decision is `PackPolicy` (pure Java, `PackPolicyJvmTest`). Every pause and every going on is a line in the step's log and logcat (`[pack] <time> pausing: thermal: thermal status severe (…); thermal status 3 (severe), headroom 0.62, battery 80 %`), and the card and the notification show the readings. A heat pause below `CRITICAL` offers **Go on anyway** (the card's button, the notification's action, `PackService.ACTION_GO_ON`, adb `--ez ondevice_go_on true`), which lifts the heat pause until the job stops in that service; `CRITICAL` or worse still pauses. The battery pause has no override. Tests: `dm/tools/tests/test_android_packpolicy.py`.
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#found-on-this-game) on an Ayaneo Pocket DS (Snapdragon G3x Gen 2, Android 13; GitHub issue #38). The cause on that device is open (the HAL's readings); the pause rule applies to every game.

### The phone's shaders step translates on about one core

- **Symptom:** Prepare's "Translating shaders" is far slower than the cores allow: Pokémon Pokopia's step reached about 225 of 8,161 shaders in 10 minutes on the phone. The step's threads (`J`, cores less two) are busy, but the process uses about one core.
- **Cause:** most of each shader's time in `vk_android_build.py` is Python that holds the GIL (`finish`: `promote_locals`, `int_outputs`, SPIR-V parsing, `strip_unused_caps`; about 70 % of a Pokopia shader's time on the Mac, 110 ms of it, three times a DKB shader's), so the build's threads take turns on one core; only the translator, the validator and zstd run beside it. Processes would give the other cores, but the app may neither fork nor start programs, and Android's CPython has no `multiprocessing` (ONDEVICE.md).
- **Fix:** worker sub-interpreters of the build's own process (`DMSH_VK_PROCS`, `concurrent.interpreters`, each with its own GIL; [SHADERS.md](../../android/SHADERS.md#build)); `PackService` sets the count to the big and mid cores, at most 4 (`CpuCores.java`). The library is byte-identical for any count and to the tree before the workers (subset builds on the old chain); merged onto the newer chain the tools digest became the library version, without a `vk_android_same.tsv` row (no full build compared there). On the Mac at 4 workers: Pokopia subsets 1.5-3.4x faster (the Mac shared with other jobs and half its cores efficiency cores), a DKB subset 1.8x; 6 workers 2.4x (DKB) and 3.5-3.9x (Pokopia sample) ([measured](../../android/SHADERS.md#worker-interpreters-2026-11-07)). Open: not yet run on the phone; the phone's time a Pokopia shader (about 2.7 s) is far more than the Mac's (0.1 s) times CPython's usual phone factor, which the workers alone do not explain.
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#found-on-this-game) and [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game); applies to every game prepared on the phone.

### A selected profile's shader update translates its whole selection again

- **Symptom:** after an APK with a new Vulkan library version (`DMSH_VK_CHAIN`), Prepare / the shader update of a profile with a selected set translates every shader of the selection again (Pokémon Pokopia: all 8,161, hours on the phone), where a game without one keeps its unchanged shaders; the step's log says `delta: none (a key list): a full build`, and the launcher has no estimate for it (no `from` rows) and no restamp.
- **Cause:** the delta update ([Delta updates](../../android/SHADERS.md#delta-updates)) took the profile's manifest only for a build of the whole map: a key-list build (the selection, as `PackService` passes it) was excluded, and `--publish-delta` took only a manifest of every key of the map, which a selected profile's Mac build never writes. An entry's hash is the key's alone once the tools and the profile's inputs are fixed, so nothing needed the whole map.
- **Fix:** general, for every profile with a `shader_seen.tsv`: a key-list build uses the profile's manifest as a full build does, for the keys the manifest has (`vk_android_delta.py` `coverage`, `reuse_candidates`, `find_entry`, `check`): it keeps an older library's entry whose hash is the manifest's, translates the rest, and checks the keys the manifest has at the end. Keys the manifest lacks (a selection changed since it was published) are translated and not checked, the manifest's other keys do not count, and only its `-` keys excuse a failure. `--publish-delta` takes a selected profile's full build: its manifest must hold exactly the keys the phone builds (`phone_keys`: the selection's keys in the map and their paired pixel shaders, as `ShaderLibs.selection` and `build_keys` give them), so `from` and `stamp` rows work as for any game. The APK takes the `from` and `stamp` rows only while the manifest's keys are the ones Prepare builds (`build.gradle` `deltaCurrent`), so a selection changed after publishing restamps nothing and counts nothing.
- **Check:** `dm/tools/tests/test_android_shader_delta.py` (`KeyList`: reuse, newest library first, a damaged entry passed over, another selection, the check, `phone_keys`); a 26-shader DKB key list on the Mac: kept 26 of 26 from a relabelled older library, byte-identical library; with one key dropped and one added, 23 kept, 1 translated and not checked.
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#found-on-this-game); applies to every profile with a selected set.

### Prepare reads every RomFS file to find the shaders

- **Symptom:** Prepare's "Finding the shaders" step takes long on the phone, and its count reads like shaders but is files: The Legend of Zelda: Ocarina of Time showed "Finding the shaders 186,583" for a game with 42,898 shaders.
- **Cause:** `shader_split.py` makes no use of file names: it reads every RomFS file, inflates it and looks for shader containers in it. The profile's `shader_map.tsv` already names where each of its shaders first appears, and those are few files: Ocarina of Time 1,124 of 186,583, Mario Kart World 1.8.0 44 of 206,326, Donkey Kong Bananza 853 of 77,342. The map alone is not quite enough. A file that holds only copies of shaders found earlier is named in no row, but its variations can pair them in new ways. Donkey Kong Bananza gets 42 of its 15,576 `shader_pairs.tsv` rows that way (2,492 files hold a shader), Splatoon Raiders 5 (571 files), Ocarina of Time 2 (1,442 files). The step's text printed the split's `progress: <files done>/<files>` as a bare count.
- **Fix:** general, for every profile with a map ([Targeted split](../../android/SHADERS.md#targeted-split)). `PackService` and `pack_android.py` run the split with `DM_SPLIT_TARGETED=1`. When main's build is one of the profile's `build` rows, it scans only the RomFS files the map's sources name (a member's source reduced to its RomFS file) and the files of the profile's optional `shader_files.tsv` (every file a full split found a shader in, `DM_SPLIT_FILES`), in the full scan's order. It keeps that result only when its tables are the profile's byte for byte; otherwise it scans every file and logs why (`targeted split: not taken, …`). With `DM_SPLIT_RESUME` the two scans keep separate results, and a targeted scan that differed is not tried again on the same inputs. The card now reads "Finding the shaders: 1,203 of 1,890 files" (`PrepareText.stepCountText`). `shader_split.py` and the new table are in no library version, so no library moves. Donkey Kong Bananza, Splatoon Raiders and Ocarina of Time have a `shader_files.tsv`; the map is enough for Pokémon Pokopia and Mario Kart World. Pokémon Pokopia gains nothing: its RomFS has 36 files and the 5 that hold shaders are the large `.fdata` archives the split spends its time in.
- **Check:** `dm/tools/tests/test_split_targeted.py` (a synthetic RomFS: targeted equals full, a copy that pairs anew takes the full scan or is taken through `shader_files.tsv`, another build, a missing file, no map, resume after a fall back); `PrepareTextJvmTest`. On the Mac, the targeted split's package files and four tables are byte for byte the full split's of the same dump: Donkey Kong Bananza, Pokémon Pokopia and Splatoon Raiders (also the profile's tables), Mario Kart World 1.8.0 and Ocarina of Time (against a full split of the same dump: their profile tables were older than the current split, so the phone fell back to the full scan for them; Ocarina of Time's tables were made again on 2026-11-08 and its targeted split now gives the profile's tables byte for byte). Times on an Apple M5 Mac that was also running another session's split, with a VM holding 7.5 GB and swap nearly full, so the wall times are rough. Full split at J=8 against targeted at J=1, in the app's way (in one process): Donkey Kong Bananza 367 s (402 s of CPU) against 74 s (53 s CPU, 1.1 GB peak RSS); Ocarina of Time 652 s (837 s CPU) against 142 s (85 s CPU, 1.6 GB); Mario Kart World 1,155 s (1,118 s CPU) against 112 s (34 s CPU, 0.7 GB); Splatoon Raiders 387 s (502 s CPU) against 35 s at J=6 (34 s CPU). A full split at J=1 was too slow to finish on the loaded Mac: Donkey Kong Bananza's had read 1,808 of 77,342 files after 266 s. Pokémon Pokopia at J=1 with its selected set: 123 s full, 104 s targeted, about 3.1 GB peak RSS for both.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game), [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game) and [Splatoon Raiders](../../dm/games/0400380020056000/README.md#found-on-this-game); applies to every game prepared on the phone.

### A Prepare step stops with "exit code 1" and no reason

- **Symptom:** Prepare's card names only the step, its exit code and the log: a player's on-device Prepare of The Legend of Zelda: Ocarina of Time update 131072, from a `.nup` picked in place, stopped at "Finding the shaders: exit code 1" with `Log: …/0400486024DEC000-work/ondevice/logs/split.log` and no reason line.
- **Cause:** the card's reason is the step log's last `[RED] ` line (`PackService`'s Tail, `PrepareText.toolStopped`). A tool that stops on an uncaught Python exception writes only its traceback: the packer's runner (`android/ondevice/dm_pack.c`) printed it and returned 1. A `sys.exit(<text>)` whose text is not a `[RED]` line (the profile checks in `dm/games/game.py`, usage texts) gave none either. What raised in the player's split is open: the phone's split of the same game version did not fail on the Mac (Check), so its traceback in the player's `split.log` is needed.
- **Fix:** general, for every step the app runs. The runner writes an uncaught exception, after its traceback, as one `[RED] <Type>: <first line of its message> (<file>:<line>)` line (the innermost frame), and the text of a `sys.exit(<text>)` as a `[RED]` line (`red()`'s lines are not prefixed twice; exit codes pass as before). A `MemoryError` so gets the card's out-of-memory text. The Tail also takes a traceback's last line (`KeyError: 'x'`) when it comes after the last `[RED]` line (`PrepareText.StopReason`), for a run without the runner's line. The cause in the split itself is still to be fixed where it raises, once the player's log names it.
- **Check:** `dm/tools/tests/test_android_packrunner.py` runs the runner's Python, taken from the C source, on tools that raise, exit with a text, a code or a `red()` line; `PrepareTextJvmTest` (`StopReason`, the card's texts). ### The shaders step crashes at once on a game build the profile was not made from

- **Symptom:** Prepare of a dump whose update the profile does not list, after **Try anyway**, stops in the shaders step at `progress 0 <n> translate` with a Python traceback ending in `vk_android_build.py` `open_packs` → `locate` → `record_key` → `shader_split.skey` → `key_ctl` → `ctl_len`: `struct.error: unpack_from requires a buffer of at least 36 bytes for unpacking 4 bytes at offset 32 (actual buffer size is 0)`, on every Retry.

### The host stops at a module its pack does not have (Android)

- **Symptom:** a game of a build with one module less than the profile lists (Mario Kart World 1.0.0 against 1.8.0's `subsdk1`) stops at its start at the missing module: the log ends with `open <pack>/subsdk1.fixups.tsv` (`read_layout` in `loader.c` dies), though the pack was made from the dump with no error.
- **Cause:** `host_preload` (`dm/host/main.c`) loaded the profile's `modules`, whatever the pack holds. The packer writes the modules it rewrote as the `modules` row of `pack.tsv`.
- **Fix:** the Android host takes that row when the pack has one (`pack_modules`, `dm/host/pack_modules.h`) and the profile's list otherwise; a row with a name that is not a plain module name (a `/`, a leading `.`) or with more names than the profile has is not trusted. The command line's own module list still wins, and the Mac and iOS builds, whose folders have no `pack.tsv`, are unchanged.
- **Check:** `dm/host/tests/t_pack_modules.c`.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#builds).

### Every Prepare stops at the shaders step: the translator does not match the lock file (Android)

- **Symptom:** on the phone, Prepare stops at "Translating shaders" on every Retry; `shaders.log` ends with `[RED] translator does not match the lock file: translator library: built from source tree 0295868e4589b4fa, this tree is e67cccd60c5f19ae (dmsh_xlate_android/build.sh builds it again)` (and a line `embedded source <X> / lock <Y> / in repo <Y>`). ### The Windows shader build stops at the first package read (`os.pread`)

- **Symptom:** on Windows, `scripts/pack_android.py` rewrites the modules and finishes the shader split, then stops at `progress 0 <n> translate` in `vk_android_win.py` → `vk_android_build.py` `open_packs` → `locate` → `_rec` with `AttributeError: module 'os' has no attribute 'pread'`.
- **Cause:** `vk_android_build.py` indexes each `.bin` package file with `dmsh_build.py`'s `record_index` (`os.open(path, os.O_RDONLY)`) and reads records on demand with `os.pread(fd, n, offset)`. Python on Windows has no `os.pread`, and `os.open` without `os.O_BINARY` opens the descriptor in text mode (which turns `CR LF` into `LF` and ends `os.read` at `0x1a`). `vk_android_win.py` wrapped the translator command, `NamedTemporaryFile` and `io.open`, not `os.open` and `os.pread`.
- **Fix:** `vk_android_win.py` `install()` sets `os.O_BINARY` on `os.open` calls that do not ask for `os.O_TEXT`, and supplies `os.pread` as a locked `os.lseek` + `os.read` loop (as `dm/tools/nup.py` does). `vk_android_build.py` is unchanged, so `DMSH_VK_CHAIN` does not move. Test: `dm/tools/tests/test_vk_android_locate.py` `test_real_package_files_and_windows_wrapper`; checked on Windows with a three-shader Donkey Kong Bananza key-list build (`delta check: 3 of 3 shaders as the manifest has them`).
- **Found on:** [Donkey Kong Bananza](../../dm/games/040074A01BF12000/README.md#found-on-this-game) update 458752 on Windows. Applies to every game packed on Windows when any shader is translated.

## In-app updates (Android)

### The app says up to date though a newer release is on git.eden-emu.dev

- **Symptom:** Settings › Check for updates answers "You're up to date" on every phone, and no popup comes at start, for hours after a new release is published on git.eden-emu.dev (v0.2.3); the release page shows it, and `curl` of the updater's URL, `https://git.eden-emu.dev/api/v1/repos/moceure/BananaNative/releases?limit=10`, returns the old list (3 releases) with `cache-control: public, max-age=180` and `x-cache-enabled: true`, while `...?limit=11` or `...?limit=10&_=1` returns the current one (4 releases).
- **Cause:** a shared cache in front of the Forgejo host (Cloudflare and/or the server's own), keyed on the full request URL, answered the releases API from a copy taken before the publication and kept it well past its `max-age`. The updater asked the same fixed URL (`UpdateCheck.Source.api`) at every check, so every phone got the same stale JSON; GitHub's API is not cached this way, but every source goes through the same code.
- **Fix:** `Updater.releases(Source)` asks each list through `UpdateCheck.busted(source.api, <System.currentTimeMillis()>)`, the URL with a fresh `_=<time>` query parameter appended at request time (`?` or `&` as the URL needs), so each check is a URL no cache has seen, and sends `Cache-Control: no-cache` and `Pragma: no-cache` (`open(..., fresh)`). The configured URL stays the plain one (docs, `update.txt`, `allowedAsset`). The APK download is unchanged: an asset's URL is new with each release and the file is checked by size and, where the API gives a digest, SHA-256. Checked by `dm/tools/tests/test_android_update.py` (`UpdateCheckJvmTest`: `busted` with and without a query, the source URL a prefix; `test_list_not_cached`).
- **Found on:** the publication of Banana Native v0.2.3 on git.eden-emu.dev (2026-11-08); the launcher, no game. Installed apps up to v0.2.3 keep asking the plain URL: they find the next release once the cache lets it through, or by a manual install.
