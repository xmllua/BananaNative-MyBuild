# Memory and address space

The guest address space, heaps, pools, virtual address memory and the allocators games bring. Each entry: symptom, cause, fix, the games it was found on. The [symptom index](../agents/symptoms.md) lists every symptom.

## Guest layout

### Partitioning the guest block between alias region, stacks and heap

- **Symptom:** large resources silently skipped, later a null deref where the resource is used; also visible as `SetHeapSize` asking for much less than the pool.
- **Cause:** the game reserves "virtual address memory" (Mario: 1.75 GB in `HeapDef.byml`) and maps it into the alias region with `MapPhysicalMemory` on demand; the alias region left after the node area ([The SDK's address-region node area](#the-sdks-address-region-node-area)) was too small.
- **Fix:** repartition the guest block (`hle_svc.c` `mem_init`): Mario uses alias 2.875 GB, stacks 256 MB, heap 1.625 GB (it asks for 1.47 GB), 5 GB in total.
- **Found on:** [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md).
- **Check:** measure before sizing (`DM_SVC=1`: the `SetHeapSize` request and the highest `MapPhysicalMemory` address).
- **Note:** on iOS without the extended-virtual-addressing entitlement a single 6 GB reservation succeeds and 7 GB fails, but Metal and the rest of the process need address space too; 5 GB is the total proven on a phone (D2R).

### Thread stacks placed at random in the stack region

- **Symptom:** an `nn::diag` abort with Result 0 under `nn::os::detail::ThreadManager::CreateThread` → `ThreadManagerImplByHorizon::MapAliasStack`, on some boots and not on others, with no `MapMemory refused` line.
- **Cause:** `CreateThread` moves each stack into the stack region at a random address: `StackGuardManager::MapAtRandomAddress` asks `AddressSpaceAllocatorBase::AllocateSpace` for a place, which tries 512 random addresses and gives up when none has the stack and its guard pages free; `MapAliasStack` aborts on that. Horizon gives a 39-bit process a 2 GB stack region; the host's is the profile's `mem_stack`, 256 MB in every profile until then. Super Monkey Ball Banana Rumble's Unity player maps 48 stacks, 106 MB, in its first 30 s, nine of them 8 MB: the positions those stacks rule out for a new 8 MB one add up to more than 256 MB, so some boots found none. A game whose stacks fill a smaller part of the region only fails more rarely.
- **Fix:** the profile's `mem_stack` sized for the game's stacks with room to spare: 640 MB for Super Monkey Ball Banana Rumble, taken from its alias region in the same 5 GB block (an iPhone has no room for a larger one).
- **Found on:** [Super Monkey Ball Banana Rumble](../../dm/games/010031F019294000/README.md#memory) (SDK 17.5.8: `MapAliasStack` at `sdk+0x13b23c`, the abort at `+0x13b2b8`).
- **Check:** `DM_THR=1 DM_SVC=1`: the `MapMemory <stack region address> <- … +<size>` lines are the stacks; their sum and the largest against `mem_stack` (the `guest AS` line gives the stack region's start).

## Heap and application pool

### Provisional Unreal layout leaves no heap

- **Symptom:** `SetHeapSize OOM: req 0x600000 > cap 0`, followed by an SDK abort in `nninitStartup` on the first provisional boot.
- **Cause:** the provisional Unreal profile reserved `0x1028000000` bytes but assigned `0x1008000000` to the alias region. The 256 MB module region and 256 MB stacks consumed the remainder, leaving no heap.
- **Fix:** `profile_guess.py` gives the alias region exactly 64 GB (`0x1000000000`), leaving 128 MB for the initial heap before the heap check measures the game. `test_profile_guess.py` checks the partition through the real profile generator.
- **Found on:** [SHIN MEGAMI TENSEI V: Vengeance](../../dm/games/010069C01AB82000/README.md) 1.0.3, whose C library asks for 6 MB.

### Heap sized from the application pool less used memory

- **Symptom:** `nnMain` returns right after `nv::InitializeGraphics`, with no error (Hyrule Warriors: Age of Calamity); `[mem] SetHeapSize … + modules … > app pool` (Monster Hunter Rise), `[mem] SetHeapSize … + modules 0x5c00000 > app pool` (Catherine: Full Body); `SetHeapSize` asks for almost the whole application pool and fails at boot (Metroid Dread: 0xc9400000, larger than the heap region); the memory pool for the game's 96 MB GPU heap has no storage (`MemoryPoolInitialize` red line), then a null read at `main+0x2eb954` (Catherine: Full Body); heap allocations fail late in a busy scene.
- **Cause:** the SDK sizes the heap as total − used memory (`QueryMemoryInfo`), so the reported application pool and used memory decide the game's heap size. Age of Calamity's `nninitStartup` does so, calls `SetMemoryHeapSize` and hands the block to its own malloc. The host reported 64 MB used beside the heap ("used" = heap + 64 MB), but `SetHeapSize` checks a request against the real size of the loaded modules (66.6 MB in Age of Calamity), so `SetHeapSize(pool − 64 MB)` failed with ResultLimitReached, `AllocateMemoryBlock` returned 0x1003, malloc was never set up, the 866 MB graphics heap allocation came back null and `nnMain` returned. Monster Hunter Rise's modules take 320 MB (`main` alone 314 MB), so its `SetHeapSize(pool − 64 MB − bss)` failed the same way. Catherine: Full Body's rewritten modules take 92 MB, so `SetHeapSize(pool − 64 MB)` failed and the game ran on a 32 MB heap. The 64 MB covers ordinary modules (Mario's two are about 74 MB, and its heap request matches hardware), but Metroid Dread's `main` carries a 1.8 GB bss that the Switch counts as used.
- **Fix:** report Switch-accurate numbers. The application pool was a host constant (`APP_POOL`, 3285 MB); it is now the profile key `app_pool` (`hle_svc.c`: `#define APP_POOL DM_GAME_APP_POOL`, Mario 0xCD500000, the same 3285 MB). The profile key `mem_used` sets the used-memory figure: 72 MB for Age of Calamity (the image plus stacks); 328 MB for Monster Hunter Rise, which gives a 2.88 GB heap; 96 MB for Catherine: Full Body, the NSP script's guess after the rewrite. Used memory now also adds the bss of modules in the front-patch layout (`big_bss_bytes` in `hle_svc.c`; the layout is in [Patch area before the module base for a large bss](rewriter.md#patch-area-before-the-module-base-for-a-large-bss)); Dread then asks for 1.38 GB.
- **Found on:** [Hyrule Warriors: Age of Calamity](../../dm/games/01002B00111A2000/README.md); [Monster Hunter Rise](../../dm/games/0100B04011742000/README.md); [Metroid Dread](../../dm/games/010093801237C000/README.md); [Catherine: Full Body](../../dm/games/0100BF00112C0000/README.md) (SDK 8.2.1; one boot). The source names no game for the late failures in a busy scene.
- **Check:** probe `DM_SVC=1`'s `svc 0x1` request and the `AllocateMemoryBlock` result.

### Offline NRO copies are not additional guest memory

- **Symptom:** `SetHeapSize OOM: req 0xffffffffe0000000 > cap 0xd0000000`, followed by an abort when allocating the launcher NRO.
- **Cause:** `big_bss_bytes` counted the bss of every offline-mapped NRO, including inactive ones, as additional used memory. The game already allocates the original NRO image and bss buffers from its heap. Subtracting the inflated used value from the application pool underflowed the startup heap request.
- **Fix:** exclude NROs from `big_bss_bytes`, as `image_bytes` already does. Ordinary NSO modules' large bss still counts. No application-pool increase or heap clamp is needed.
- **Found on:** [FINAL FANTASY X/X-2 HD Remaster](../../dm/games/0100BC300CB48000/README.md); after the fix its startup heap is 3.08 GB.
- **Check:** the memory SVC tests compare used-memory queries with an ordinary large-bss module and a larger NRO present together.

### Thread stacks backed by active NRO data

- **Symptom:** repeated `[RED] MapMemory refused (0xd401)` for a stack source inside a loaded NRO's writable data, then an abort in `MapAliasStack` / `CreateThread`.
- **Cause:** the host rejected all NRO-backed stack sources because reload can overwrite their backing. The launcher's static allocator legitimately supplies thread stacks from its bss.
- **Fix:** permit the writable, unsealed range of an active NRO. Deactivation checks outstanding stack borrowers and marks the module inactive under the same memory-map lock used by `MapMemory`; reload cannot replace borrowed backing. Unloading with a live borrower is rejected. Loaded-state reads are atomic.
- **Found on:** [FINAL FANTASY X/X-2 HD Remaster](../../dm/games/0100BC300CB48000/README.md), launcher `nro815+0x124854`, through SDK 5.4's thread creation path.
- **Check:** `make -C dm/host/tests GAME=01007BB017812000 memory` checks active-NRO mapping, refusal to deactivate with a live mapping, successful deactivation after unmap, and rejection of an inactive source under the sanitizers.

### A heap request beyond the heap region returns ResultOutOfMemory

- **Symptom:** `SetHeapSize OOM: req 0x120000000 > cap 0xd0000000`, then `Break#1 reason=0` in `nninitStartup`, with a backtrace through `nn::os::SetMemoryHeapSize` (`sdk+0x967a4`).
- **Cause:** a game may look for the largest heap it can have by asking for more than there is. Donkey Kong Country: Tropical Freeze's `nninitStartup` (`main+0x1e84c`) binary-searches `SetMemoryHeapSize` between 3 and 6 GB (6 GB is the heap region of a 39-bit address space) and narrows on every failure. SDK 4's `SetMemoryHeapSize` (`sdk+0x9672c`) turns the kernel's ResultOutOfMemory (description 104), 103 and ResultLimitReached (132) into `os::ResultOutOfMemory` (0x1003) and aborts on any other result. For a size larger than the heap region the host returned 0xD401 (InvalidCurrentMemory, 106), so the SDK aborted. Horizon's `KPageTable::SetHeapSize` returns ResultOutOfMemory there.
- **Fix:** a request larger than the heap region returns 0xD001 (`hle_svc.c`, svc 0x1). The search then settles on 3.09 GB, the pool less the rewritten modules (the same LimitReached check as before).
- **Found on:** [Donkey Kong Country: Tropical Freeze](../../dm/games/0100C1F0051B6000/README.md) (SDK 4.4.0).

### `nninitStartup`'s heap only without virtual address memory

- Not needed in the end for [Ace Attorney Investigations Collection](../../dm/games/010005501E68C000/README.md) (1.0.0.2, SDK 17.5.3): the process heap of pull request #16. `nninitStartup` calls `SetMemoryHeapSize` / `AllocateMemoryBlock` only without virtual address memory, and nothing else in `main` calls them ([Virtual address memory follows the NPDM's system resource](#virtual-address-memory-follows-the-npdms-system-resource)).

### Unreal games without virtual address memory take a heap

- **Symptom:** the app quits at launch; the host log shows `SetHeapSize OOM: req 0xc5200000 > cap 0`.
- **Cause:** `profile_guess.py` gave every Unreal game the 64 GB alias region and no heap, after the Unreal 4.26+ games ([Unreal's engine address region and its options](#unreals-engine-address-region-and-its-options)). An older Unreal game whose NPDM declares no system resource has no virtual address memory, and its `nninitStartup` sets a heap of the application pool less used memory instead ([Heap sized from the application pool less used memory](#heap-sized-from-the-application-pool-less-used-memory)).
- **Fix:** the guesser's Unreal memory rule applies only with an NPDM system resource; other Unreal games get the usual heap region (3.25 GB here).
- **Found on:** [Yoshi's Crafted World](../../dm/games/01006000040C2000/README.md) (Unreal Engine 4.18, SDK 4.4.1): a 3.15 GB heap; GMalloc is a FMallocBinned on it.

### Sizing the pool and alias region for virtual address memory

- A title that uses virtual address memory may never call `SetHeapSize`: everything comes from `MapPhysicalMemory` in the alias region. The `[mem]` log lines show what it maps ([Measuring address regions and commits](#measuring-address-regions-and-commits)).
- What fills the alias region first is address space, not memory. StandardAllocator reserves the whole free pool (pool − 64 MB, 1 GB aligned) but Engage commits only 0.58 GB of it, and Unity's own regions commit 0.97 GB. So Engage's profile reports a 2.5 GB pool (`app_pool`) and uses a 4.375 GB alias region in a 5 GB block (reserved address space peaks at 3.47 GB of 4.31 GB).
- iOS without the extended-virtual-addressing entitlement allows a single 6 GB reservation, but Metal needs address space too; 5 GB is the total proven on a phone ([Partitioning the guest block between alias region, stacks and heap](#partitioning-the-guest-block-between-alias-region-stacks-and-heap)).
- The pool a game is told decides how much StandardAllocator reserves (`Initialize(nullptr, pool − used)`), and the host does not enforce the pool (only `nninitStartup` reads it), so a pool a little above what the game maps leaves the most address space:
  - Ace Attorney Investigations Collection: with Engage's 2.5 GB pool the game ran, but StandardAllocator's 2.44 GB reservation beside Unity's pools (1.06 GB live, from `main+0x40f1d4`) ended 4.37 GB into the 4.375 GB alias region after 140 s, while the `MapPhysicalMemory` log showed StandardAllocator committing 0.19 GB. The profile reports a 1 GB pool, a little less than the 1.02 GB the game maps at its peak; ten minutes then peak at +2.85 GB of address space, against +3.91 GB with a 1.5 GB pool.
  - Brain Memory Training Academy: with Ace Attorney's 1 GB pool and 5 GB block the game boots to its title in 5 s with no red line; StandardAllocator ends at +1.0 GB, and five minutes of level loads take the alias high-water mark to +2.25 GB with at most 0.5 GB mapped.
  - Patrick's Parabox: with Ace Attorney's 1 GB pool and 5 GB block (in place of the provisional profile's hardware pool) it boots to its title with no red line, and the alias region is mapped up to +1.5 GB with 0.27 GB in use.
  - Advance Wars 1+2: Re-Boot Camp: the hardware pool used the alias region up to +4.25 GB; the heap check's 1 GB pool starved its malloc ([Unity's GPU pool block allocation spins at size 0](#unitys-gpu-pool-block-allocation-spins-at-size-0)); with a 2 GB pool the game maps up to 2.26 GB of the alias region through its menus and first battle.
- **Found on:** [Fire Emblem Engage](../../dm/games/0100A6301214E000/README.md); [Ace Attorney Investigations Collection](../../dm/games/010005501E68C000/README.md) (Unity 2022.3, SDK 17.5.3); [Brain Memory Training Academy](../../dm/games/0100F5D01DA3A000/README.md); [Patrick's Parabox](../../dm/games/0100E44016C22000/README.md); [Advance Wars 1+2: Re-Boot Camp](../../dm/games/0100300012F2A000/README.md).
- **Note:** to measure regions and commits, see [Measuring address regions and commits](#measuring-address-regions-and-commits).

### `nv::GetGraphicsMemoryInfo` with no graphics device

- **Symptom:** `CRASH sig=11 addr=0 pc=sdk+0x4656c8` right after the window is created, with `x0 = 0` and the return address in `main` (`main+0x3508a90`): the faulting code is `ldr x0,[0xc5d000+0xc68]; ldr x8,[x0]; ldr x1,[x8,#0x68]; br x1`.
- **Cause:** the game reports GPU memory in its startup log, so it calls `nv::GetGraphicsMemoryInfo` and then `nv::DumpGraphicsMemoryInfo` (both imported by `main`). The SDK's implementation reads a driver object from its own static (`0xc5d000+0xc68`) that only `nv::InitializeGraphics` sets; a game that never initialises an NVN device — as every EGL/OpenGL game does — leaves it null, and the SDK dereferences it. `nv::MemoryInfo` is 64-bit counters filled from sign-extended 32-bit driver counters, and its size follows the SDK: 0x20 bytes (four counters) on SDK 10 and older, 0x40 bytes from SDK 11 on, where the SDK zeroes all 0x40 when nv is not initialised. Every sdk module checked, from 3.4.0 to 20.5.22, fills four counters; on SDK 3.4.0–10.8.1 the function has no 0x40 path, from 11.4.3 on it has. A host answer of 0x40 bytes on an old SDK overruns the caller's 32-byte record.
- **Fix:** [`dm/gfx/hle_nv.c`](../../dm/gfx/hle_nv.c) answers the five `nv::` symbols such a game imports: it records the allocator callbacks (`SetGraphicsAllocator`, `SetGraphicsDevtoolsAllocator`) and the pool from `InitializeGraphics(void*, size_t)`, and `GetGraphicsMemoryInfo` reports that pool (total and free = its size) or zeroes the structure when nothing was initialised. It writes the record of the game's SDK: 0x20 bytes when `DM_SDK_OLD(dm_sdk_major())`, 0x40 otherwise (the boundary the NVN API version and the shared-font layout follow too); the pool figures lie in the first four counters, so both sizes carry them.
- **Found on:** [Well Dweller](../../dm/games/0100217023F6C000/README.md) (SDK 22.2.0, GameMaker Studio 2, OpenGL through EGL). The game's allocator is never called again, so a zeroed report is equally correct on a GL-only title. The 32-byte overrun on old SDKs was found on Hyrule Warriors: Definitive Edition 1.0.1 (SDK 3.5.1, KTGL, NVN; GitHub issue #708, [PR #709](https://github.com/seedds/nxnative/pull/709)): its startup caller passes a 32-byte record, and AddressSanitizer reported the write past it.
### An SDK 21 Switch 2 game with a 4.5 GB alias region

- **Symptom:** a null pointer in the game's resource code (`main+0x15a69b0`, null + 0x78, thread `BaseProcCreateAndDeleteThread`): a model's load returned null, its status 9, written hundreds of times by a loader thread. The `[mem]` lines end near the top of the alias region.
- **Cause:** the alias region ran out. An SDK 21 game keeps the SDK's 1 GB node area, as the sdk patches that cut it do not match this SDK, and maps past 4.25 GB of it at the first level.
- **Fix:** the profile's `mem_alias`: 16 GB ([Splatoon Raiders](../../dm/games/0400380020056000/README.md): `0x400000000`, with `mem_reserve 0x550000000`). The peak then is about +8.5 GB (upstream seedds/nxnative c8521eeb, measured on the Mac).
- **Found on:** [Splatoon Raiders](../../dm/games/0400380020056000/README.md). **Open:** on Android the reservation is address space only, but a mapped peak near 8.5 GB is more than a phone's free memory may hold; not yet measured on a phone.


## Virtual address memory and the alias region

### Virtual address memory follows the NPDM's system resource

- **Symptom:** `StandardAllocator::Initialize` aborts in `nninitStartup` (Fire Emblem Engage); `nn::diag` abort in `StandardAllocator::Initialize(void *, size_t, bool)` from `nninitStartup` (`sdk+0x2f98e4` ← `main+0x5b69e0`, Big Brain Academy: Brain vs. Brain).
- **Cause:** the SDK's `IsVirtualAddressMemoryEnabled` is `GetInfo(TotalSystemResourceSize) != 0` (`VammManager::IsVirtualAddressMemoryEnabled`, `sdk+0x34e074`), the system resource the NPDM declares (offset 0x14 of `META`). With it the game's allocator takes its memory as address regions in the alias region. Engage's NPDM declares one, so `IsVirtualAddressMemoryEnabled` is true and the allocator reserves all free memory (about 3.2 GB for Engage) as one region in the alias region, after the ~1 GB node area ([The SDK's address-region node area](#the-sdks-address-region-node-area)). Big Brain Academy's `nninitStartup` (`main+0x5b6984`) asks `os::IsVirtualAddressMemoryEnabled()`: when true it gives StandardAllocator a 60 GB address region (`0xf00000000`), when false it sets a heap of pool − used (2 MB aligned) and hands that over. The host reported a 32 MB system resource to every game, while this game's NPDM declares none.
- **Fix:** the profile key `sys_resource` reports the NPDM's size (0 for Big Brain Academy, so the heap path, as on hardware; `hle_svc.c`); the survey writes it for every new game, and profiles without it keep the 32 MB answer. A game with virtual address memory needs a profile `mem_alias` / `mem_reserve` that holds its regions: Engage first used 5.5 / 8 GB on the Mac; its profile now has `mem_reserve 0x140000000` / `mem_alias 0x118000000` (5 GB / 4.375 GB) with the node area cut and a 2.5 GB `app_pool` ([Sizing the pool and alias region for virtual address memory](#sizing-the-pool-and-alias-region-for-virtual-address-memory)).
- **Found on:** [Fire Emblem Engage](../../dm/games/0100A6301214E000/README.md); [Big Brain Academy: Brain vs. Brain](../../dm/games/0100620012D6E000/README.md) (SDK 11.4.3, NintendoWare Bezel Engine).

### The SDK's address-region node area

- **Symptom:** the first `AllocateAddressRegion` fails with 0x1803; `StandardAllocator::Initialize` aborts in `nninitStartup` (an `nn::diag` abort; the NSP script's heap check reports "the host stopped before nnMain"); the alias region fills in minutes; regions a game reserves later fail ([Size-aligned regions exhaust the alias address space](#size-aligned-regions-exhaust-the-alias-address-space), [The movie player's own StandardAllocator](#the-movie-players-own-standardallocator)).
- **Cause:** SDK 16's AddressRegionManager takes 0x3fe00000 at the start of the alias region as a node area, so the alias region must be larger than 1 GB; SDK 8 has the same 1 GB node area as the newer SDKs, and SDK 7 / 8 builds load it in another form (below). On hardware the alias region is 64 GB. On Ace Attorney Investigations Collection's SDK 17 build, `CentralHeap::Init(nullptr, pool − used)` got no 1 GB-aligned region for 3.14 GB after the 1 GB node area.
- **Fix:** shrink the node area with a rewriter cut for that SDK build (`dm/tools/sdk_patches.py`): the two `mov w8/w9, #0x3fe00000` in the AddressRegionManager constructor → 62 MB.
- **SDK-wide:** the same cut is also an SDK-wide function patch (`sdk_patches.py` `MATCH_CUTS`), which every game's `sdk` gets when its build has no `CUTS`: a new game, or a new version of one, needs no cut of its own on a reviewed implementation. A registered build whose cuts the rules give exactly has no row (18 builds, checked on the game drive on 2026-10-29 and 2026-10-30); a build a profile was brought up on gets the rules too (before, the rules skipped such builds, which kept those rows). Six implementations cover the 19 cut builds on the game drives (SDK 7.3.2 / 8.2.1, 10.4.x, 11.4.3 to 13.3.5, 15.3.2 to 18.3.5, 19.3.x / 20.5.x, 22.2.0); on those 19 each rule gives exactly the registered cuts, and on the 36 `sdk` builds there it matched once or not at all. The SDKs of Fire Emblem: Three Houses, Bayonetta, Donkey Kong Country: Tropical Freeze, Xenoblade Chronicles 2 and Yoshi's Crafted World have other implementations, not reviewed. A build with no reviewed implementation keeps the 1 GB node area; the NSP script lists it (not red: a game without virtual address memory never reaches it) ([Function-matched cuts for unregistered builds](rewriter.md#function-matched-cuts-for-unregistered-builds)).
- **Finding the constructor on a new `sdk` build:** search its text for the two `mov w8 / w9, #0x3fe00000` words (`08fca752`, `09fca752`); `sdis.py --fn` names the function `AddressRegionManagerC2Emm` from its dynamic symbols. SDK 7 / 8 builds load the node area with `orr w8 / w9, wzr, #0x3fe00000` (`e8230b32`, `e9230b32`), so the `mov` search finds nothing there.
- **Found on** (the builds that take the cut):
  - [Mario + Rabbids Kingdom Battle](../../dm/games/010067300059A000/README.md) (SDK 4.4.0): the older `VammManager` constructor reserves a full 1 GB rather than 0x3fe00000; its limit and occupied length at `sdk+0x93dfc` / `+0x93e8c` are reduced together to 64 MB. Nodes are mapped in 4 KB increments as needed.
  - [Xenoblade Chronicles 3](../../dm/games/010074F013262000/README.md) (SDK 12.3.9): constructor `sdk+0x346420`, cuts `+0x346430` / `+0x3464cc`, the same offsets as Engage's SDK 12.3.7, beside the large-region alignment cut. The game's own allocator needs a separate compact layout.
  - [Pokémon Brilliant Diamond](../../dm/games/0100000011D90000/README.md) (Unity 2019.4.27f1, SDK 11.4.3): constructor `sdk+0x34e0b8`, node-area limit `+0x34e0c8` and occupied length `+0x34e164`. The original node area prevents StandardAllocator's pool-minus-used reservation from fitting at startup.
  - [Fire Emblem Engage](../../dm/games/0100A6301214E000/README.md): the two `mov w8/w9, #0x3fe00000` in the constructor → 62 MB; without it the alias region ran out of address space minutes into play ([Size-aligned regions exhaust the alias address space](#size-aligned-regions-exhaust-the-alias-address-space)).
  - [Ace Attorney Investigations Collection](../../dm/games/010005501E68C000/README.md) (Unity 2022.3, SDK 17.5.3): `StandardAllocator::Initialize` aborts in `nninitStartup` on SDK 17, then the alias region fills in minutes; the same node area as Engage's SDK; the constructor is at `sdk+0x139458` on that build and takes the same cut.
  - [Brain Memory Training Academy](../../dm/games/0100F5D01DA3A000/README.md) (Unity 2022.3.5f1, SDK 16.2.4): `nn::diag` abort at `sdk+0x126490`, `StandardAllocator::Initialize`, called from `nninitStartup` at `main+0x73adcc`. Its `nninitStartup` is Ace Attorney's: `Initialize(nullptr, pool − used)` with virtual address memory and no `SetMemoryHeapSize`. The `sdk` build is Unicorn Overlord's, whose NPDM declares no system resource, so it never needed the cut; the constructor (`AddressRegionManagerC2`, `sdk+0x134768`) takes it at `+0x134778` / `+0x13480c`.
  - [Sea of Stars](../../dm/games/01008C0016544000/README.md) (Unity 2021.3.25f1, SDK 16.2.0, the `sdk` build of Super Mario Bros. Wonder 1.0.0): `nn::diag` abort at `sdk+0x126440`, `StandardAllocator::Initialize`, called from `nninitStartup` at `main+0x8b6710`; the heap check reports "the host stopped before nnMain". Brain Memory Training Academy's constructor at `sdk+0x134718` takes the cut at `+0x134728` / `+0x1347bc`, beside the [region alignment cut](#size-class-alignment-doubles-unitys-regions).
  - [Patrick's Parabox](../../dm/games/0100E44016C22000/README.md) (Unity 2020.3.30f1, SDK 13.3.7): `StandardAllocator::Initialize` at `sdk+0x324dec`, called from `nninitStartup` at `main+0x1cd080`; the same `nninitStartup` and the same cut, on this build's constructor (`sdk+0x37c3a0`: `+0x37c3b0` / `+0x37c44c`).
  - [Advance Wars 1+2: Re-Boot Camp](../../dm/games/0100300012F2A000/README.md) (Unity 2020.2.1f3, SDK 10.4.1): `StandardAllocator::Initialize` at `sdk+0x2edf90`, called from `nninitStartup` at `main+0x365310`; the heap check reports "the host stopped before nnMain"; the same `nninitStartup`. The `sdk` build is The Great Ace Attorney Chronicles', which has no virtual address memory; its constructor (`sdk+0x340e90`) has the `orr` form (`e8230b32` at `+0x340ea0`, `e9230b32` at `+0x340f3c`).

### Size-aligned regions exhaust the alias address space

- **Symptom:** a null-based write minutes into play, at the pool size minus 0x20 (Engage: a write to `NULL + 0x1fffe0`, `addr=0x1fffe0` at `main+0x9a4664`); NULL index pointers written on several job threads at once (`main+0xdb0ad4`, `0xdaea58`, `0xdadb5c`), with 32-bit mesh indices turning up inside texture objects.
- **Cause:** the alias region ran out of *address space*, not memory (the SDK's node area took about 1 GB of it), so new address regions came back empty. Unity's TLSF heap allocator (`main+0x9a45d0`) added a pool (a new 2 MB pool), and its low-level virtual allocator (vtable at `main+0x61ffeb0`; reserve `main+0x9aa0f4` → `nn::os::AllocateAddressRegion`) got no address region and returned 0. Buffers mapped fresh past 2 MB got no mapping: Unity's particle geometry scheduler (`main+0xd91e0c`) takes its vertex and index chunks from a fallback that creates and maps a fresh buffer each time (`main+0x7b9c64`; Unity's Switch renderer always takes it, as on hardware). The AddressRegionManager aligns each region by its size (64 KB under 2 MB, 2 MB under 4 MB, 4 MB under 32 MB, 32 MB under 1 GB, else 1 GB) and Unity asks for its block plus alignment slack, so a 2.25 MB block takes a 4 MB slot and a 16.25 MB block a 20 MB one. At the crash Engage held 4.17 of the 4.375 GB left after the node area (StandardAllocator 3.14 GB, Unity about 1.05 GB, the rest fragments). On hardware the alias region is 64 GB.
- **Fix:** shrink the node area with a rewriter cut for the game's SDK build (`dm/tools/sdk_patches.py`, Engage: the two `mov w8/w9, #0x3fe00000` in the constructor → 62 MB; [The SDK's address-region node area](#the-sdks-address-region-node-area)).
- **Found on:** [Fire Emblem Engage](../../dm/games/0100A6301214E000/README.md): the prologue battle crash (scripted run, about 357 s; a 12-minute scripted run now plays through the battle) and the idle attract demo crash after about 220 s (from about 180 s 32-bit mesh indices also turned up inside Unity's texture objects). With the cut an 850 s idle run is clean, with no corrupted texture objects; with the old SDK the same run dies at 159 s in Unity's heap allocator.
- **Check:** probe the SDK's `VammManager::AllocateAddressRegion` at its success path and `FreeAddressRegion` after its prologue, and sum the live regions by caller ([Measuring address regions and commits](#measuring-address-regions-and-commits)).
- **Note:** to reproduce the old state: `boot.sh <log> 245` with no input on an SDK rewritten without the cut.

### Size-class alignment doubles Unity's regions

- **Symptom:** a write at NULL + 0x3fffe0 (a 4 MB pool − 0x20) at `main+0x48b770`, about six minutes into the prologue, with Unity's `ALLOC_CACHEOBJECTS_THREAD` allocator in x19; the `[mem]` high-water mark at +4.26 GB of the 4.375 GB alias region while 1.26 GB is mapped (Sea of Stars).
- **Cause:** before SDK 20, `VammManager::AllocateAddressRegion` aligns a region by its size (64 KB under 2 MB, 2 MB under 4 MB, 4 MB under 32 MB, 32 MB under 1 GB, else 1 GB) and starts the next one at that alignment past a 4 KB guard. Unity 2021.3's virtual allocator (`main+0x48deb0` → `main+0x12e12c0`) asks for N MB + 252 KB and aligns its blocks to 256 KB itself, so every region spills just past a size class: a 16.25 MB region takes a 20 MB slot, a 4.25 MB one an 8 MB slot, a 32.5 MB one 64 MB. Measured with probes on the success path (`sdk+0x134868`: x21 size, x22 address) and on `FreeAddressRegion` (`sdk+0x1350cc`: x1 address): 94 regions of 16.25 MB, 35 of 4.25 MB and 15 of 2.25 MB among 167 live regions holding 2.59 GB, with 0.86 GB of gaps between them, ending at +4.22 GB. On a Switch the alias region is 64 GB.
- **Fix:** the 4 MB, 32 MB and 1 GB classes take SDK 20's 2 MB: first a cut on each `sdk` build, now the SDK-wide alignment rule ([1 GB alignment of regions of 1 GB and more](#1-gb-alignment-of-regions-of-1-gb-and-more)), which gives both builds below the same cuts. The same route then ends its live regions (2.59 GB) at +3.24 GB with 0.58 GB of gaps, and the high-water mark stays at +3.0 GB over 20 minutes.
- **Found on:** [Subnautica: Below Zero](../../dm/games/010014C011146000/README.md) (Unity 2019.4.36f1, SDK 13.3.5, the `sdk` build of AI: THE SOMNIUM FILES - nirvanA Initiative and Pokémon Scarlet 1.0.0: `sdk+0x37c334`, `+0x37c33c`, `+0x37c340`; 336 live regions ended at +4.37 GB with 0.87 GB of gaps at the opening's crash site, before any crash; the cut alone took the end to +4.29 GB, and the game also needed its 1 GB bucket allocator reservation cut to reach +3.50 GB). ### Unity 6 takes its memory with no StandardAllocator and no heap

### Measuring address regions and commits

- **What a game really needs:** boot it on the Mac with a Switch-sized alias region, `DM_ALIAS_SIZE=0x1000000000` (64 GB; the heap and stacks stay as the profile has them), so whatever it reserves fits. Absolum, Super Smash Bros. Ultimate and Paper Mario: The Thousand-Year Door were sized this way, then with `mem_reserve` / `mem_alias` keys.
- **Regions:** the rewriter puts three observation gates in every `sdk` that exports `VammManager::AllocateAddressRegion` and `FreeAddressRegion` (`patch_nso.py` "Address regions"): the entry (the size in x2, the caller's frames), the one store of the new address through the out pointer (`mov xB, x1` in the prologue, `str xA, [xB]`; A rides in the gate number), and `FreeAddressRegion`'s entry (x1). They are found by those symbols, so they hold for any SDK build that has them (all 35 of the 36 `sdk` builds on the game drives that have a symbol table; New Super Mario Bros. U Deluxe's is a 32-bit module, whose table this does not read). The host keeps the table (`hle_svc.c` "Address regions", growing as needed): where the request returns to in the game (the first return address outside the `sdk` on the frame chain: the function that asked, or its caller when it tail-called the SDK API, whose frame is gone by then; Z-A's size is set in a function that tail-calls `StandardAllocator::Initialize`, so its request returns to `nninitStartup`) and the SDK API it came through. A region of 256 MB or more is logged when made (`[mem] address region 4.00 GB at alias +0.06 GB, returning to main+0x37c9a64`); `DM_REGIONS=<file>` writes the live table every 2 s with each region's mapped bytes and the part ever opened.
- **The NSP script's region check:** for a provisional or derived profile whose game has virtual address memory, it boots the game that way for 15 s into `nnMain` and reports each region of 256 MB or more and where the regions reach against the profile's alias region. A derived build (a version the profile was not brought up on) has none of the registered builds' fixed-address cuts, only the function-matched ones, so a region those cuts shrank is red here at pack time rather than an abort on the iPhone (Super Smash Bros. Ultimate 13.0.1, GitHub issue #375). That reach is a lower bound: regions the game takes later in play (Tears of the Kingdom's at the first descent, Engage's minutes in) are not in the table (`profile_guess.py region_findings`; stamped `# address regions:` in the profile with the rewrite's key, so a run with other rewritten modules, a new cut for instance, checks again). A red line when they reach past it, which says who lays the region out: one that comes through `nn::mem::StandardAllocator::Initialize` the host makes fit at run time ([StandardAllocators over 12 to 62 GB of address space](#standardallocators-over-12-to-62-gb-of-address-space)), and when the regions made after it need more than the 256 MB the host leaves them, the check sets `stdalloc_cap` in the provisional or derived profile: the alias region less the regions before it, those after it and the same 256 MB for regions made later in play, in 32 MB steps (`profile_guess.py stdalloc_room`; a red line only when that leaves it no room, or when a value set by hand leaves them too little; one the check set is worked out again by a later check); one the game takes with `nn::os::AllocateAddressRegion` for its own allocator works smaller only if that allocator places nothing by fixed offsets (Super Smash Bros. Ultimate: [A 62 GB page allocator behind `nu::VirtualAllocHook`](#a-62-gb-page-allocator-behind-nuvirtualallochook)). Where a region is used does not tell them apart: Z-A's StandardAllocator puts its 3.15 GB startup block at the top of its region, Smash's engine its node pool. Measured: Smash's region 4 GB through `nn::os::AllocateAddressRegion`, returning to `main+0x37c9a64`, opened up to 14 MB below its end; Z-A's 4 GB through `nn::mem::StandardAllocator::Initialize`, returning to `main+0x1b2e690`, opened to its end (both with their cuts).
- **Commits:** probe `VammManager::AllocateMemoryPages` / `FreeMemoryPages` (x1 address, x2 size) and split them by region. On DRAGON QUEST VII Reimagined, `nn::os::AllocateMemoryPages` was probed past its `adrp` (`sdk+0x140f84`).
- **Windows:** `DM_ALIAS_WINDOWS=<window MB>` (for example `DM_ALIAS_WINDOWS=512`) logs, every 30 s, the mapped memory of each window of that size in the alias region (`hle_svc.c`); it measured Octopath Traveler 0's allocator pools and Super Smash Bros. Ultimate's battle commits.
- **Log:** the `[mem]` lines report the alias high-water mark (one line per 256 MB), the total actually mapped (page bitmap) and every heap growth.

### An alias high-water mark near the top is not exhaustion

- **Symptom:** the `[mem]` high-water mark climbs close to the end of the alias region while far less is mapped (SUPER ROBOT WARS Y: +4.27 GB of 4.38 GB with 1.82 GB of live regions), and it looks like the address space is about to run out.
- **Cause:** none to fix: this is how `VammManager::AllocateAddressRegion` places regions. It walks its tree from the highest region down, takes the first hole that fits and places the region at that hole's low end (read on SDK 18.3.5, `sdk+0x13bfd0`; other implementations not read). So while the top has room, every new region lands just past the highest one and freed holes below stay idle, and the mark rises with address churn, not with use. Only when no hole fits does the function return its failure (`w0 = 2` at `sdk+0x13c11c`).
- **Fix:** none. To judge the room left, read the live regions and their holes in the `DM_REGIONS` table, not the mark, or run with a smaller alias region (`DM_ALIAS_SIZE`): if the game goes on with the end of the table pinned at the top, the holes are serving it. A real exhaustion is what [Size-aligned regions exhaust the alias address space](#size-aligned-regions-exhaust-the-alias-address-space) and [Size-class alignment doubles Unity's regions](#size-class-alignment-doubles-unitys-regions) describe: a request no hole fits.
- **Found on:** [SUPER ROBOT WARS Y](../../dm/games/010063301BD50000/README.md#memory): every one of 228 regions placed above the top skipped a hole that would have held it, and with the alias region cut to 3 GB the end stayed at +2.99 GB for about 10 minutes of battle demos with no failure.

## Engine allocators

### StandardAllocators over 12 to 62 GB of address space

- **Symptom:** `StandardAllocator::Initialize` aborts in `nninitStartup` (Pokémon Legends: Z-A: `main+0x1b2e690`); `nn::diag` abort at `sdk+0x11ff34` (`StandardAllocator::Initialize`) in `nninitStartup`, SDK 15.3.2, called from `main+0x31370c` (Paper Mario: The Thousand-Year Door).
- **Cause:** with virtual address memory the game initializes a StandardAllocator over more address space than a phone gives a process, as the Switch's 64 GB alias region allows.
  - Pokémon Legends: Z-A (a 16 MB system resource) initializes its allocator over 12 GB, `StandardAllocator::Initialize(nullptr, 0x300000000)` (`main+0x1b3e3ec`). The alias region must hold the SDK's 1 GB node area and that region, 13 GB.
  - Paper Mario: The Thousand-Year Door's malloc is a StandardAllocator over 62 GB of address space (`Initialize(nullptr, 0xf80000000, false)`, `main+0x3136e8`), out of which it cuts 256 MB, 16 MB and 1 MB allocators. Booted once with a 64 GB alias region, the region came 0.69 GB past the 1 GB node area, at the next 1 GB boundary: this `sdk` build (Celeste's, which has no virtual address memory) aligns regions of 1 GB and more to 1 GB, as Absolum's did ([1 GB alignment of regions of 1 GB and more](#1-gb-alignment-of-regions-of-1-gb-and-more)).
- **Fix:** the node-area cut on the `sdk` build ([The SDK's address-region node area](#the-sdks-address-region-node-area)), where that build aligns large regions to 1 GB the alignment cut, and less address space for the allocator, as below. SDK 19's AddressRegionManager puts the region right after the node area (+0x3fe2c000 before the cut), not 1 GB aligned as Engage's SDK did, so Z-A's 4.25 GB alias region (`mem_alias 0x110000000`) holds both; Paper Mario's `sdk` (Absolum's cuts on Celeste's build) puts its region at alias +62 MB to +4.06 GB in Engage's 5 GB block. The allocator's size was first a cut on each game's `main` (to 4 GB; Absolum's to 2.5 GB); the host's cap replaced those cuts.
- **The host gives the request what the alias region has room for, in every game and build.** The rewriter places a gate at the entry of both `nn::mem::StandardAllocator::Initialize` overloads, found by symbol in every `sdk` that has them (`patch_nso.py` "Address regions"). With a null address (virtual address memory) and a size the alias region has no room for, the host lowers the size in x2 before the SDK sees it (`hle_svc.c` "StandardAllocator's address space"): to the alias region less the regions already made (at least the 62 MB node area) and 256 MB for the regions made after it, in 32 MB steps. The SDK lays the region and its `CentralHeap` out from that size, so it holds all the way down, and the pool, not the region, bounds what the heap maps. The profile key `stdalloc_cap` sets the size instead, where the regions made after it need more room (Absolum's garbage collector); the NSP script's address region check sets it in a provisional or derived profile ([Measuring address regions and commits](#measuring-address-regions-and-commits)): a provisional pack of Absolum 1.1.1 with its `game_env` set `0xa2000000` (2.53 GB), between the 2.5 GB and 2.72 GB that both play its route (without `game_env` its GC's region is 3.75 GB and the check reports no room). A request that fits is never changed, so a Switch-sized alias region (`DM_ALIAS_SIZE`) sees the game's own size. It is a workaround for the iPhone's address space, as the cuts are; a region the game's own allocator takes with `nn::os::AllocateAddressRegion` is not touched, since its layout may be fixed ([A 62 GB page allocator behind `nu::VirtualAllocHook`](#a-62-gb-page-allocator-behind-nuvirtualallochook)). Checked with `main` rewritten without its cut: Pokémon Legends: Z-A 2.0.2 (12 GB → 3.94 GB, frame 2,571 in 90 s headless; without the gate it aborts at `sdk+0x134214` as before the cut; with a 64 GB alias region the request stays 12 GB), Paper Mario: The Thousand-Year Door 1.0.1 (62 GB → 4.06 GB, frame 1,800 in 75 s), Absolum 1.1.1 (40 GB: the default 4.06 GB leaves its GC's 1.5 GB region no room and the SDK aborts at `sdk+0x13a684`; with `stdalloc_cap 0xa0000000`, 2.5 GB, frame 3,900 in 75 s; the region check computes 2.72 GB). Pokémon Scarlet was not checked (no game files). Then the `main` cuts of Z-A, Paper Mario and Absolum (and Z-A's matched rule) were removed: each game's route from a fresh save into play, headless, with and without the cut on the same build (Z-A 380 s into Lumiose City, Paper Mario 480 s into Rogueport, Absolum 320 s into the first level, fighting), reached the same frames with the same `[RED]` kinds and alias region use, and screenshots of the same scenes. Z-A's cut of 4 GB had already been lowered to 3.94 GB by the cap. Pokémon Scarlet keeps its cut (no game files to check it on).
- **Found on:** [Pokémon Legends: Z-A](../../dm/games/0100F43008C44000/README.md) (2.0.2, SDK 19.3.11; one boot); [Paper Mario: The Thousand-Year Door](../../dm/games/0100ECD018EBE000/README.md): the allocator maps 1.5 GB at boot and 2.0 GB by the arrival in Rogueport. The `sdk` build is [Celeste](../../dm/games/01002B30028F6000/README.md)'s. Absolum's malloc StandardAllocator (40 GB, 2.5 GB with its `stdalloc_cap`) is in [.NET NativeAOT malloc and the GC region range](#net-nativeaot-malloc-and-the-gc-region-range).
- **Also found on:** [Pokémon Scarlet](../../dm/games/0100A3D008C5C000/README.md#memory) (1.0.0, SDK 13.3.5): its `main` cut was removed for the cap (2026-10-30, 4.06 GB on its 4.375 GB alias region).

### Bezel Engine's two memory setups

- **Symptom:** a SIGSEGV writing just past a null base as a menu or board loads (`nn::bezel::CoreSystem::Allocate` returned null for a 46 MB request at `main+0x8d9a48`, Super Mario Party Jamboree 2.3.0), sometimes first `[RED] fs ReadFile into 0x0+0x400000 failed at +0 (EFAULT)`, a read into a null buffer from the same allocator; the alias region's `[mem]` lines show `StandardAllocator::Initialize(nullptr, 56.00 GB) … 2.06 GB of address space`.
- **Cause:** Bezel's `nninitStartup` chooses between two setups by `os::IsVirtualAddressMemoryEnabled()`. With virtual address memory, malloc's StandardAllocator gets a 2 GB address region and Bezel's own a 56 GB one (Big Brain Academy: 60 GB); without, it sets a heap of pool − used memory, gives malloc 32 MB of it and Bezel the rest. In the 4.375 GB alias region of the 5 GB block, the [host's allocator gate](#standardallocators-over-12-to-62-gb-of-address-space) leaves Bezel 2.06 GB beside malloc's 2 GB, and Bezel runs out: measured with a 64 GB alias region (`DM_ALIAS_SIZE`), malloc's region held 5 MB and Bezel's 2.3 GB at Jamboree's Party Plaza. Holding both needs about 5.2 GB of alias region, more than a phone without extended addressing leaves beside Metal.
- **Fix:** profile data: `sys_resource 0`, so the game takes its heap path, with the 4 GB layout and the Switch's 3285 MB pool (`app_pool 0xCD500000`): a 3.14 GB heap, all but 32 MB of it Bezel's, as much memory as the Switch's pool gives it. The NPDM's 16 MB of system resource are not reported, so this is a choice between the game's own two setups, made for the phone's address space, not a fix of the virtual-memory path.
- **Found on:** [Super Mario Party Jamboree](../../dm/games/0100965017338000/README.md) (Bezel Engine 2.9, SDK 17.5.9); [Big Brain Academy: Brain vs. Brain](../../dm/games/0100620012D6E000/README.md) has the same `nninitStartup` and declares no system resource, so it always took the heap path.

### Separate virtual ranges in Snowdrop's page allocator

- **Symptom:** a write to `0x20000ffff` in static initialization (`main+0x164990`), after `AllocateAddressRegion` returns `0x1803`; reducing the request to 3 GB still returns `0x1803` with the SDK's original large-region alignment. With only the outer ranges reduced, a later free crashes at `main+0x1668dc` after reading compressed file data as a slab-owner pointer. With all three ranges cut, a write to `0x78` at `main+0x2c534a8` (`lr=main+0x2c53484`) when the opening quest's overalls bush is shaken, or when a later save loads.
- **Cause:** the engine reserves three adjacent virtual ranges before committing pages in them. Its enclosing reservation exceeds the iPhone's available guest address space, and the engine does not check the failed reserve before deriving the page addresses. A smaller reservation also needs the SDK's node area and large-region alignment adapted: a separate metadata reservation comes first, and the 1 GB alignment wastes the remaining contiguous space. The large-allocation child has an independent maximum page count; reducing only the outer range lets it allocate across the boundary used by `free` to distinguish allocation classes. Beside the three ranges, the memory system's startup reserves a 1.06 GB pool of 272-byte slots that nothing allocates from, and every UI node context reserves two small ranges of its own (576 KB and 256 KB) without checking them. With the pool, the regions fill the 4.375 GB alias region in the opening quest; a context left without its range writes its first entry to `NULL + 0x78`.
- **Fix:** the build-gated game cuts reduce the range sizes, their combined reservation and the large allocator's maximum page count together, and the unused pool to 17 MB. The fixed metadata reserve remains large enough, and page allocation, commits and frees retain their behavior. The SDK build gets the SDK-wide [node-area cut](#the-sdks-address-region-node-area) and [2 MB alignment of the large classes](#1-gb-alignment-of-regions-of-1-gb-and-more). Per-range occupancy and the original growth fallbacks remain **open** until sustained gameplay validates the smaller ranges; see the game note for the layout, cut sites and current validation.
- **Found on:** [Mario + Rabbids Sparks of Hope](../../dm/games/0100317013770000/README.md) (1.6.2225577, SDK 13.3.5); [Mario + Rabbids Kingdom Battle](../../dm/games/010067300059A000/README.md) (1.9.589692, SDK 4.4.0), with the same three-pool layout and an independent large-allocation page count.

### .NET NativeAOT malloc and the GC region range

- **Symptom:** `nn::diag` abort at `sdk+0x12dad0` in `nninitStartup`, called from `main+0x756310` (1.1.1: `main+0x7562d0`).
- **Cause:** malloc's `StandardAllocator::Initialize(nullptr, 0xa00000000)`: 40 GB of address space (`main+0x28c084`; 1.1.1: `main+0x28bff4`). Absolum's regions (measured on a 64 GB alias region): malloc's (2.19 GB used into the first level, 1.75 GB of it FNA3D's GPU heap, allocated whole at `FNA3D_CreateDevice`), the .NET GC's region range (3.75 GB) and a few small ones. The GC sizes its range as 5 × its hard limit (768 MB = 75% of the 1 GB its `GetPhysicalMemoryLimit`, `main+0x28c08c` in 1.1.2, `main+0x28bffc` in 1.1.1, reports), and it reads `DOTNET_GCRegionRange` through `getenv` first.
- **Fix:** the host now answers `getenv` from the profile key `game_env` (`hle_os.c`; every other name goes to the SDK's own `getenv`, an empty environment), which sets 1.5 GB. The GC then uses its range from both ends, 756 MB from the start and 748 MB from the end, where it used only the first 1.14 GB of 3.75. The profile's `stdalloc_cap` gives malloc 2.5 GB through the [host's allocator gate](#standardallocators-over-12-to-62-gb-of-address-space), in every build (the 1.1.1 cut on `main` it replaced is gone). One more thing kept it from fitting, the 1 GB alignment of large regions ([1 GB alignment of regions of 1 GB and more](#1-gb-alignment-of-regions-of-1-gb-and-more)), cut beside the node-area cut. The regions then end 4.13 GB into the 4.375 GB alias region of Engage's 5 GB block.
- **Found on:** [Absolum](../../dm/games/0100A83022A22000/README.md) (.NET NativeAOT on SDK 18.3.2).
- **Check:** boot once on the Mac with a 64 GB alias region (`mem_reserve 0x1030000000`, `mem_alias 0x1008000000`) and probe `VammManager::AllocateAddressRegion`'s success path (`sdk+0x13bf8c`: x21 size, x22 address) with `DM_SVC=1`'s map log.

### A 62 GB page allocator behind `nu::VirtualAllocHook`

- **Symptom:** the game aborts in its static initialisers, before `nnMain`, when its own 62 GB address region fails (`main+0x37c9bd0`, `AllocateAddressRegion(&p, 0xf80000000)` at `main+0x37c9a5c`).
- **Cause:** the allocator behind `nu::VirtualAllocHook` is a 64 KB page allocator whose own tables fill the region's last 14 MB, so the size, the header offset, the page count and three region-end bounds all follow from 62 GB.
- **Fix:** the profile's `patches.py` cuts all 11 instructions to a 4 GB region. The cut region still did not fit: SDK 8 has the same 1 GB node area and 1 GB alignment of regions of 1 GB and more as the newer SDKs (constructor `sdk+0x336b40`, `orr w9, wzr, #0x3fe00000` at `+0x336b50` / `+0x336bf0`; alignment at `+0x336d5c`), cut in `sdk_patches.py` as DRAGON QUEST XI S's SDK 7.3.2 build; the region then starts 64 MB into the 4.375 GB alias region of the 5 GB block.
- **Found on:** [Super Smash Bros. Ultimate](../../dm/games/01006A800016E000/README.md) (13.0.5, SDK 8.2.1). Booted once with a 64 GB alias region (`mem_reserve 0x1030000000`, `mem_alias 0x1008000000`) and `DM_SVC=1`'s map log, the game commits from the region's start upward (1.73 GB contiguous at the title) and its page tables from the top; a battle commits up to 2.5 GB (`DM_ALIAS_WINDOWS`).

### Unreal's engine address region and its options

- **Symptom:** the game calls `exit(1)` in `nninitStartup` (Octopath Traveler 0: `main+0x12e74`); `nn::diag::Abort` from `main+0x352fbec` (Unreal's fatal error) after the first commit, `AllocateMemoryPages(0, 2 MB)` while the RHI starts (`main+0x353ff8c`, result 0xe03) (Pikmin 4); a crash in `NumberLineAllocator::Compaction` at boot (DRAGON QUEST XI S, region option 4224).
- **Cause:** Unreal's `nninitStartup` needs virtual address memory and reserves one address region for the engine with `AllocateAddressRegion`, 62 GB by default (`-SwitchVirtualAddressSpaceSize=` in MB, or in bytes above 4095). The other options it reads are `-SwitchMaxMemorySize=`, `-NVNCommandBufferGranularity=`, `-NVNControlBufferSize=`, `-SwitchMainThreadStackSize=`, `-NVNTempMemoryPageSize=`, `-ResX=` / `-ResY=` and `-SwitchDisableVirtualAllocator`, which also exits. It reads them from the game arguments, which the host used to set only after `nninitStartup`.
- **Fix:** the game arguments are set before `nninitStartup` now, as on hardware. The region's size no longer comes from them: the host gives the region what the alias region has room for, in any Unreal Engine 4 / 5 main.
- **Engine-wide:** the rewriter finds the reservation without a build ID (`dm/tools/ue_region.py`, called by `patch_nso.py`), each link unique or nothing is gated: the option's name `SwitchVirtualAddressSpaceSize` in ro, `nninitStartup` (a `b` to the engine's function; in UE 4.18 a `bl` to it), and in that function the one `bl` to the `nn::os::AllocateAddressRegion` PLT stub whose straight-line code sets x0 to the region's base variable and stores the size in the word after it. x1 at the call must be that size (the stored register, or both set from one constant), and written after the store only with that same constant while the stored register still holds it; the rewriter then makes that instruction `mov x1, xS`. Observation gate `OBS_UE_REGION` goes on that store, with the register in the gate number's upper bits. The host (`hle_svc.c`) sets that register and x1 to StandardAllocator's room ([StandardAllocators over 12 to 62 GB of address space](#standardallocators-over-12-to-62-gb-of-address-space)): the alias region less the regions made so far and 256 MB for later ones, in 32 MB steps. That is 2.81 GB in the 3.75 GB block and 4.06 GB in Engage's 5 GB block. With a Switch-sized `DM_ALIAS_SIZE` the request fits and nothing changes. A chain that breaks after the option's name is a `[RED]` line in the rewrite, and the engine asks for its whole default.

### Unreal's FMallocBinned3 replaced by the host allocator

- **Symptom:** a null read in the out-of-memory report at `main+0x1005824` when the engine region is smaller than the allocator's pools (Octopath Traveler 0).
- **Cause:** Unreal's allocator, an FMallocBinned3, reserves 37 GB of the engine region (74 pools of 512 MB, pool index = offset >> 29). The pools are uneven (at character creation the largest holds 68 MB, the 74 together 732 MB; measured with `DM_ALIAS_WINDOWS=512`), so no smaller window fits a phone's ~5 GB.
- **Fix:** the host puts its own allocator in the object instead (`hle_uemalloc.c`: the FMalloc vtable on a host malloc zone, the trivial slots kept). With it the region holds only what the engine maps itself (709 MB at Octopath Traveler 0's character creation).
- **Engine-wide:** the rewriter finds the allocator in any Unreal Engine 4 / 5 main without a build ID (`dm/tools/ue_malloc.py`, called by `patch_nso.py`), each link unique or nothing is cut: the UTF-16 name `Binned3`, its getter (`adrp x0` + `add x0`, `ret`), the one data word holding the getter once the module's relative relocations are applied (OCTOPATH TRAVELER II's and Pikmin 4's vtables are relocated, the others' are in place), the vtable it is a slot of (back to two words of 0: offset to top, no RTTI), the one function other than the vtable's two destructors that stores the vtable (the constructor) and its one call, a `bl`. It cuts that call and puts observation gate `OBS_UE_MALLOC` on it, where x0 is the object (made by `GCreateMalloc`, or a bss object in `nninitStartup`); the fixups table names the vtable and the getter's slot (`UE_MALLOC_VT`, `UE_MALLOC_SLOT`), which names the slot layout: 19 for UE 4.26 / 4.27, 22 for UE 5, 26 for UE 5.6. A chain that breaks after the name is a `[RED]` line in the rewrite and Unreal's own allocator runs. On the 68 `main` builds on the game drive (2026-10-30) it found exactly the call, vtable and layout of the five that had a cut of their own, and nothing in the other 63, Batman: Arkham Knight's included; on SHIN MEGAMI TENSEI V: Vengeance's main, extracted from the archive drive, its registered ones too. Those cuts were removed, with FINAL FANTASY RESONANCE's Asian release's, which had the global release's offsets. Until then each build had a cut and a gate in its profile's `patches.py` and a row of fixed addresses in `hle_uemalloc.c`.

### Thread stacks from the host's Unreal heap

- **Symptom:** an abort right at `nnMain`, under `nn::os::CreateThread` → `ThreadManagerImplByHorizon::MapAliasStack` → `StackGuardManager::MapAtRandomAddress`; with the log line, `[RED] MapMemory refused (0xd401): <stack region> <- <address outside the guest block>`.
- **Cause:** Unreal allocates the stacks of the threads it creates with FMemory (OCTOPATH TRAVELER II's game thread: `nnMain` mallocs it with 4 KB alignment at `main+0x544`; its FRunnableThreads take theirs from inside larger allocations), and `CreateThread` moves such a stack into the stack region with `svcMapMemory`. With [the host allocator](#unreals-fmallocbinned3-replaced-by-the-host-allocator) that memory is a host malloc zone outside the guest block, and `MapMemory` takes only a backed source: the heap, mapped alias pages or a module's writable data (`map_source_backed`, `hle_svc.c`).
- **Fix:** with the host allocator installed, a source outside the guest block that the host has mapped readable and writable is taken too (`dm_ue_heap_owns`, `hle_uemalloc.c`; `vm_region_64`, since malloc has no cheap lookup from an interior pointer). A refused map now logs its arguments.
- **Found on:** [OCTOPATH TRAVELER II](../../dm/games/0100A3501946E000/README.md), after the stricter source check of `MapMemory`; [Pikmin 4](../../dm/games/0100B7C00933A000/README.md) boots with the same host.

### Unreal 5.6's page allocator never gives address space back

- **Symptom:** `nn::diag` abort from `main+0x11bc`, no message, in the first battle, with about 1 GB mapped (FINAL FANTASY RESONANCE with DRAGON QUEST VII Reimagined's 2 GB region).
- **Cause:** the engine hands its region out with a page allocator of its own (`main+0x13ef0`), a bump pointer plus free lists per size class, so the address space it has used only grows, and past the region's end it calls `OnOutOfMemory` (`main+0x13c74`).
- **Fix:** the profile gives the region 4064 MB in Engage's 5 GB block, as DRAGON QUEST XI S's (profile key `game_args`). This SDK build aligns regions of 2 MB and more to 2 MB only (`VammManager::AllocateAddressRegion`, `sdk+0x145e00`), so it needs no alignment cut.
- **Found on:** [FINAL FANTASY RESONANCE](../../dm/games/0100606026F12000/README.md) (Unreal Engine 5.6.1, SDK 20.5.17). Probed where each new block comes back (`DM_PROBE=main:13fcc`: x0 the block, x21 its size, x8 the region's end): a 1 GB block at boot from a static constructor, +1.5 GB 15 s in, +2.0 GB in the battle, level at +2.03 GB over seven minutes.

### Ring heaps cut from a pool at 64 KB alignment

- **Symptom:** write to `0x268` right after the title screen (`main+0x5d6708`, a constructor whose `this` is `0x200`).
- **Cause:** `operator new` (`main+0x5a55d4`) takes the thread's ring heap, a bump allocator whose cursor starts at its base. One ring heap kept base 0, as in 13 Sentinels: the engine cuts ring heaps out of a memory pool at 64 KB GPU alignment, and the host's pool storage from malloc is only 4 KB aligned. The first allocation returned 0, which `operator new`'s null check skipped, and the next returned `0x200`.
- **Fix:** the profile key `alloc_big_align` aligns allocations of 64 KB or more to 64 KB ([dm/games/README.md](../../dm/games/README.md)); the game then plays from the title screen into its opening story scene.
- **Found on:** [Unicorn Overlord](../../dm/games/010069401ADB8000/README.md) (SDK 16.2.4, Vanillaware's engine as in [13 Sentinels: Aegis Rim](../../dm/games/01003FC01670C000/README.md); one boot).

## Mapping SVCs

### `svcQueryMemory` must report each module's real layout

- **Symptom:** C++ exception aborts in `nn::ro::detail::GetExceptionInfo`.
- **Cause:** the SDK's unwinder finds a module from `svcQueryMemory`: it walks back over Code+RX regions to the module start, forward over Code then CodeData, and reads `MOD0` for `.eh_frame_hdr`.
- **Fix:** the host reports each loaded module's real layout and reports other host memory as free (`hle_svc.c`).
- **Found on:** [Fire Emblem Engage](../../dm/games/0100A6301214E000/README.md) (its note lists it among the host changes first needed there). IL2CPP throws a C++ exception for every managed exception, so Unity games need this; Mario ([Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md)) never threw.

### `MapPhysicalMemory` in 16 KB host pages

- **Symptom:** `MapPhysicalMemory` faults on part of a page.
- **Fix:** round to 16 KB host pages.
- **Found on:** the source names no game.

### Maps past the application pool fail as on Horizon

- **Symptom:** the alias region's mapped total runs past the application pool in the first minute.
- **Cause:** `nninitStartup` allocates and frees everything allocatable (pool − used, 3.15 GB, mapped at the top of the region) and the SDK keeps the freed pages mapped; later allocations map new pages at the bottom until a map fails, and only then does it unmap the cached block and retry. The host never refused a map, so the block stayed mapped beside the 0.4 GB the game used.
- **Fix:** on for every game (`hle_svc.c`; profile key `mem_map_limit off` turns it off): a map past the pool fails with ResultLimitReached, and the used memory `GetInfo` reports counts the mapped pages, as on Horizon (without that, the startup probe itself, sized as total − used, was refused).
- **Found on:** [Pokémon Legends: Z-A](../../dm/games/0100F43008C44000/README.md) (2.0.2, SDK 19.3.11; one boot). Measured: one refused 4 MB map, the 3.15 GB unmap, the same map again. [Mario Kart World](../../dm/games/0400C3F00006E000/README.md) (1.8.0): its virtual address heap sizes its free space by `QueryMemoryInfo` total − used, so it lets its blocks go only when the used memory counts the mapped pages (kartnative and plumber-racer-2 set the key on 1.0.0).

### Unmapped guest memory stays resident

- **Symptom:** after a large `UnmapPhysicalMemory` or heap shrink, RAM does not come back. `phys_footprint` may still fall, so it hides this: the `guest` class in `DM_MEMSTAT` shows the real figure.
- **Cause:** on Darwin `mprotect(PROT_NONE)` only removes the page table entries. The pages stay resident and dirty, out of `phys_footprint`, and `madvise(MADV_FREE)` on pages that are not writable does nothing, though it returns 0. Measured on 1 GiB on the Mac: 1,024 MiB still resident and dirty, footprint 1.2 MiB.
- **Fix:** `guest_release` (`hle_svc.c`) puts a fresh inaccessible mapping over the range (`MAP_FIXED`), which empties it at once and gives zero pages. `UnmapPhysicalMemory` then clears the range's exposed bits, so mapping it again needs no `memset`. A memory pool's no-copy buffer over the range keeps the old pages for the GPU until the buffer goes (measured: the GPU still reads the old data, the CPU sees zeros). A guest that unmaps and remaps under a pool it never finalized would see the two diverge, which Horizon does not allow.
- **Found on:** [Pokémon Scarlet](../../dm/games/0100A3D008C5C000/README.md), one A/B on its 180 s route on the Mac: peak footprint 4,540 → 3,775 MiB, guest charged 1,809 → 1,372 MiB, 30 fps held. 437 MiB of the footprint drop is guest memory; the other 328 MiB is not explained. [Tears of the Kingdom](../../dm/games/0100F2C0115B6000/README.md) on its 95 s route: footprint flat (4,935 → 4,969 MiB), guest charged 1,887 → 1,685 MiB, with the baseline's pages partly compressed, so that drop is less certain. Open: the iPhone and Z-A, whose shader libraries were stale, were not measured.

### A host read of guest storage that the guest unmaps meanwhile

- **Symptom:** `CRASH sig=11` in libc `memcpy` on the `vk-replay` thread, during a load. The fault address is a page start in the alias region, and the copy length is 0x1000. The tombstone says `SEGV_ACCERR (read)`, and the backtrace runs `dm_guest_read_mapped` ← `unmapped_content` ← `upload_fill` ← `img_first_use`. It does not happen every time.
- **Cause:** `dm_guest_read_mapped` checked the alias-region page bitmap, then copied the page with no lock and no fault protection. `UnmapPhysicalMemory` on a guest thread made the pages inaccessible (`guest_release`) before it cleared their bits, and it could also start after the check had passed. So the copy read a page that was no longer readable. A lock cannot fix this: Unmap holds `g_map_lock` while `vka_mem_release` waits for GPU fences that the replay thread completes, so a reader taking the lock could deadlock.
- **Fix:** `hle_svc.c` makes two changes. Unmap clears the range's bits before it releases the pages. Each run of mapped pages is copied by `guest_copy`, which turns a page that became unreadable after the check into zeros instead of a fault: `process_vm_readv` on its own process on Android, `vm_read_overwrite` on Apple platforms. `mem_any_mapped` (`vka_tex.c`) reads partly mapped storage through it as well. Upload paths that read storage the guest has fully mapped still read it in place (open). `t_svc_memory` checks a page whose bit says mapped while it is already inaccessible, and the zeros after Unmap.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md) 1.8.0 docked, at the load from the world map into the 3D scene (phone, run mA on dd0caa69).

### `GetInfo(UserExceptionContextAddress)` returns a real buffer

- **Symptom:** a write through a null pointer at +0x1c0 during startup.
- **Fix:** `GetInfo(UserExceptionContextAddress)` must return a real buffer.
- **Found on:** the source names no game.

## Running out of memory

### Large compressed NUP files decompressed into memory (Android)

- **Symptom:** on the phone, resident memory jumps by GBs at a game's start with a `.nup` package, most of it one `[anon:scudo:secondary]` mapping in `/proc/<pid>/smaps` the size of one of the game's files; the file thread is busy for seconds at a time while the game loads.
- **Cause:** a zstd file of a NUP container was decompressed whole into memory when the game opened it (`nup_image.h`, written for Donkey Kong Bananza, whose largest compressed file is 53 MiB), with its compressed extent in a second buffer while it decompressed. Pokémon Pokopia's `0x38f972af.fdata` is 2.38 GiB (2,442 MiB held, 4.8 GiB while it decompressed), and three more are 700-900 MiB; a file the 128 MiB cache let go was decompressed again at its next open.
- **Fix:** a compressed file of at least `DM_NUP_DISK_MB` (64) is decompressed by streaming (8 MiB at a time) into an unlinked temporary file in `$TMPDIR` (the app's cache folder) and mapped read-only, once for the image's life: its pages are page cache the kernel can reclaim, outside the cache's budget. Without a temporary file, or when the streaming decoder refuses the frame, it is decompressed into memory as before (`[RED]`). `DM_NUP_DISK_MB=0` keeps every file in memory.
- **Check:** `make -C dm/host/tests GAME=<id> run` (`t_fs`: a "large" file read from its temporary file, outside the budget, kept after close, the file unlinked). Pokopia on the phone: before, a 2,441 MiB `[anon:scudo:secondary]` mapping 12 s in (3,134 MiB of host malloc resident, 551 MiB more swapped) and the boot at 10 fps for all 75 s of the run with `KtglFsThread` busy; after, 153 MiB of host malloc at 42 s, the files' maps 861 MiB resident as page cache, the boot at 60 fps from about frame 600, 14 large files decompressed once each (0.1-1.8 s, the 2.38 GiB one 1.8 s).
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#memory), packed with `dm/tools/nup_pack.py` (every file one zstd frame).

### A shader split that keeps every shader's code in memory (Android)

- **Symptom:** the phone's Prepare stops at "Finding the shaders" with `the dump's shaders are not the ones this app knows … shader_map.tsv differs … dump the game again`; `split.log` has `[RED] motor_asset_re/KIDS_PLATFORM_OUNCE/0x38f972af.fdata: MemoryError:  (its shaders are left out)` and far fewer shaders than the profile's map (5,476 of 131,426). On 12 to 24 GB phones; the same dump splits on a Mac to the profile's map byte for byte.
- **Cause:** `shader_split.py` held every shader it found until the file ended: Pokémon Pokopia's 2.38 GiB `.fdata` holds 203,120 GLSLC outputs in KTGL G2S containers, 5.9 GiB of control sections and code areas, only 125,950 keys; each container was also joined in memory (`idrk_data`, up to 62 MB stored), and the package was built in memory again before it was written. The split took 15.5 GB at its peak (`/usr/bin/time -l`, peak memory footprint, J=1 as on the phone). The file's `MemoryError` was caught (a file no reader can read is left out, [A file no reader reads](shaders.md#a-file-no-reader-reads)), so the split "finished" without its shaders, and the shaders step blamed the dump.
- **Fix:** general, for every game: the readers append to a `Shaders` collector that keeps one entry per key as they come (a copy is compared by digest, `shader_sig`, and dropped); a container that inflates to more than 32 MiB is inflated into a temporary file and read through a mapping; the package is written record by record. With `DM_SPLIT_SELECTED=1`, which `PackService` sets for a profile with a selected set, only the selected shaders and their pixel shaders keep their code (`shader_seen.tsv`, [Selected shaders](../../android/SHADERS.md#selected-shaders)); every other shader keeps the first bytes the tables need and gets an empty record (`BTCDBTCD` and a zero header), so the map's numbering holds and the tables are those of a full split. The package lists its kept keys (`pkg/selected.txt`); the shaders step splits again when its selection needs others. A file over 256 MB prints `progress: <files done>/<files> <n>%` as it is read (the card adds "of a large file"). When the split left a file out, the shaders step says why (`unreadable:` lines in `split.log`): out of memory, or a file that could not be read, instead of "dump the game again" for both.
- **Check:** `dm/tools/tests/test_split_stream.py`. Pokopia's split of update 655360 from a `.nup` on the Mac, J=1: before 109 s, peak footprint 15.49 GB (max RSS 7.49 GB); after, a full package 69 s, 6.41 GB (byte-identical tables and package); with `DM_SPLIT_SELECTED=1` 72 s, 0.91 GB footprint (max RSS 2.80 GB, mostly the files' mapped pages), identical tables, 8,161 records byte-identical to the full package's and 123,265 empty ones (a 206 MB package instead of 4.3 GB).
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#android) (GitHub issues #33, #39, #68 and two discussions).

### A null-pool buffer from a game heap that ran out

- **Symptom:** a null-pool buffer even with virtual pools working ([Virtual memory pools mapped onto one physical pool](nvn-objects.md#virtual-memory-pools-mapped-onto-one-physical-pool)).
- **Cause:** the game's own heap ran out.
- **Tracing it with probes** ([05](../agents/05-debugging.md#probes-without-a-debugger-dm_probe)): the gsys GPU allocator at `main+0x4290c0` and the heap's `tryAlloc` (vtable slot +0x30) show which heap, its size and every allocation into it; the `!xN` heap walk shows the free and used blocks at the moment of failure.
- **Note:** read the probe log carefully: `tryAlloc` probes show *requests*, not successes, so a running total that already exceeds the heap means an earlier request failed.
- **Found on:** [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md), [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md) (the two entries below).

### Model heaps sized by the host's command record sizes

- **Symptom:** a model load exhausts its resource heap: a null `operator new` at the world load, or `BufferInitialize: pool has no storage` followed by a null-pool crash. A display-list heap that runs out shows as `AddCommandMemory` with a null pool outside a recording, then host-lent segments growing until `FATAL NVN command memory` ([Host-lent command memory segments](nvn-objects.md#host-lent-command-memory-segments)).
- **Cause:** games size model allocations by measuring scratch command recordings; oversized host records can exceed the budgets in their resource-size tables. In Breath of the Wild, each model's heap is its table entry + 0x1008, the file goes in 4 KB aligned, and the setup (`main+0x155a2ac`) takes the rest as a frame heap (vtable `main+0x1d4f950`, head `+0xe0`, tail `+0xe8`). Its use is the same in every run; only the file's alignment pad varies (0 to 0xff8), and the entries leave room for any pad, about 0xd00 to spare on most models. Three models were a 4 KB page short, so the loads with a large pad failed. The game sizes the model's prerecorded commands by recording each mesh's draw and each shape's per-pass state into a scratch command buffer and summing `GetCommandMemoryUsed` (`main+0xf9aeb4`, `main+0xf9bb54`), and our records were larger than the driver's (draws carried the indirect and multi-draw fields, every recording began with a BEGIN record). Super Mario Odyssey keeps its display lists in a 62 MB GPU bump heap named "DisplayList" (`main+0x5e8280`: used at `+0x68`, capacity at `+0x6c`, a null block when full), allocated while a kingdom loads; with 40-byte state binds (39% of the display-list bytes) it filled at the load and every later list got a null block.
- **Fix:** plain draws leave unused indirect fields out and recordings start with their first command. Uniform and single vertex-buffer bindings also use compact 24-byte records instead of 32, preserving full GPU addresses and retaining full-width fallback records for ranges above `UINT32_MAX`; multi-vertex ranges retain their array representation. State binds carry only the state object's bytes (16 bytes for color, channel mask and polygon state, 24 for blend, multisample and depth-stencil, instead of 40), and a single texture bind drops its pool bases when both are 0 (24 bytes instead of 32, the handle still 16 bytes in). Replay expands the compact forms into the same canonical binding state. The native inline uniform command takes 20 bytes and the native vertex-buffer command 24, so these small differences can accumulate into an extra 4 KB GPU-pool chunk. Report the bytes actually recorded; do not underreport usage or add a game-specific heap allowance. See [What `GetCommandMemoryUsed` counts](nvn-objects.md#what-getcommandmemoryused-counts).
- **Check:** for Breath of the Wild's whole scene, probe where the setup heap is cut (`main+0x155a520` with `!x21`, the resource heap) and the end of the setup (`main+0x155a5f4` with `!x2`, the frame heap), with `DM_PROBE_HEAP=28,38,40,e0,f8 DM_PROBE_HEAPFRAME=1d4f950 DM_PROBE_HEAPWORDS=1` ([05](../agents/05-debugging.md#probes-without-a-debugger-dm_probe)). A model fits any placement when entry + 0x1008 covers the resource heap's header and object (0x310), the file, the frame heap's block header and its peak use, plus 0xff8 of pad.
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md), [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md#memory) (buffer bindings; the game note records the failed allocation, measured sizes and validation), [Super Mario Odyssey](../../dm/games/0100000000010000/README.md#services) (state and single texture binds; the note has the heap's measurements).

### Unity's GPU pool block allocation spins at size 0

- **Symptom:** the frames stop at the first loading screen, a graphics worker at 100% CPU (17 s in, `UnityGfxDeviceWorker` running, the main thread waiting on a condition variable, no red line).
- **Cause:** the heap check's 1 GB pool (the hardware pool had used the alias region up to +4.25 GB) left the game's malloc too little: Unity's GPU memory pool block allocation (`main+0x96f430`) calls `aligned_alloc` through `main+0x866810`, halves the request after each failure, and once the request rounds to 0 it calls on for ever with a size of 0.
- **Fix:** a 2 GB pool: the game then maps up to 2.26 GB of the alias region through its menus and first battle.
- **Found on:** [Advance Wars 1+2: Re-Boot Camp](../../dm/games/0100300012F2A000/README.md) (Unity 2020.2.1f3, SDK 10.4.1), after the node-area and alignment cuts.
- **Check:** `sample <pid>` on the Mac host shows such a spin (the guest frames are `???` in the host's image list; subtract the module base from the log's `base` lines); it worked here where lldb does not.

### Host calls on small guest stacks

- **Symptom:** SIGBUS inside a host hook (`snprintf` under `mount_ex` / `h_fs_MountSave`), then the process hangs (Super Mario 3D World + Bowser's Fury); SIGBUS inside Metal (`AGCDeserializedReply`, an AGX compiler block) at an address in the guest stack region (Breath of the Wild).
- **Cause:** host hooks run on the calling guest thread's stack. Super Mario 3D World's save thread has an 8 KB stack (CreateThread stack top `0x…9fe0`, fault `0x21a0` below it), and the file system hooks size their path buffers by PATH_MAX: one file open takes 6–7 KB (`-fstack-usage`: `OpenFile` 1.3 KB → `host_path_ex` 1.9 KB → `path_component` 3.2 KB); on hardware the same call is one IPC. In Breath of the Wild a host NVN call did Metal work on a game thread with a small stack: `nvnQueueSubmitCommands` replays the frame, and ending a render pass made the driver compile its fast-clear blit program on the calling thread.
- **Fix:** every hook in `hle_fs.c` now registers through `HLE_FORCE_BIG` (`hle.h`): a compile-time stub loads the implementation into x16 and jumps to `dm_bigstack_enter` (`hle_bigstack.c`), which moves the call to a per-thread 512 KB host stack (with a guard page) when sp lies in the guest address block, passing x0–x8 and d0–d7 through. Only for functions with register arguments only (no variadic or stack arguments). iOS forbids generating code at run time, so the stubs are static. NVN functions are not registered through `HLE_FORCE`, so they got their own big-stack entry: every implemented NVN function except the `nvnCommandBuffer*` recording calls goes through `nvn_big_entry` (`nvn_entry.S`), which finds the implementation by slot and hands it to `dm_bigstack_enter` ([NVN entry points on the big host stack](nvn-objects.md#nvn-entry-points-on-the-big-host-stack)).
- **Found on:** [Super Mario 3D World + Bowser's Fury](../../dm/games/010028600EBDA000/README.md) (file system hooks); [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md) (NVN entry points).

### Deferred-release drain without an autorelease pool

- **Symptom:** the iPhone app is killed for memory; resident memory grows steadily (about 0.2 MB a frame) while the residency set and the texture counts stay flat.
- **Cause:** the deferred-release drain ran on the guest submit thread with no autorelease pool, so autoreleased Metal objects were never freed (the Metroid Dread leak).
- **Fix:** `defer_drain` has its own `@autoreleasepool`.
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md): GitHub issue #9 (iPhone 16 Pro Max, handheld), killed in the first shrine. An 8 GB iPhone gives this app about 3.4 GB (resident plus `headroom to the system memory limit` stayed at 3,375 MB); resident memory grew from 2.6 GB at the shrine load until the kill. On the Mac a host without that pool grew 1 MB a frame in the shrine (GPU 3.0 → 4.4 GB in 2,400 frames); with it the shrine stays at 2.7–2.9 GB resident and 1.5–1.7 GB GPU, idle or walking (vmmap at 2.8 GB: about 1.6 GB guest memory, 0.75 GB private textures, 0.17 GB IOAccelerator).
- **Note:** found on the way: dead texture serials and the fixed-size pool tracking table ([Dead texture serials kept in a ghost table](nvn-objects.md#dead-texture-serials-kept-in-a-ghost-table), [Memory-pool tracking table grows in blocks](nvn-objects.md#memory-pool-tracking-table-grows-in-blocks)).

### Upload staging grows within one rendering submission

- **Symptom:** travelling produces a brief multi-GB footprint spike, then memory returns to its earlier level; periodic memory lines can miss the peak. Upload diagnostics show many swapped-out blocks still alive in one batch.
- **Cause:** `up_alloc` could append unlimited staging blocks before `up_flush`. Overflow staging then retired on the main rendering fence, so splitting uploads alone still retained completed staging while that submission was being built. Weak-table insertion and enumeration in the staging diagnostics also left temporary strong references in the submission's autorelease pool.
- **Fix:** split GPU deswizzle batches before another block would exceed 128 MiB. The three upload allocator slots provide backpressure, publishing deferred commits before waiting. Retire overflow and CPU-upload staging from the upload completion handler, remove residency and clear its retained array before freeing the slot; keep diagnostic weak-table operations in their own autorelease pools. Rendering destinations keep their existing lifetime. A single texture larger than the batch budget still gets its own block; this is not a cap on all renderer memory.
- **Check:** `make -C dm/gfx/tests GAME=<id> check_t_upload_budget` uses actual Metal uploads during an open render pass, with direct and deferred encoding and Metal validation. A 2 GiB burst retained 2,048 MiB before the fix; afterwards it peaks at 384 MiB and retains only the three reusable blocks (96 MiB) after upload completion, before the rendering fence. It also checks every uploaded pixel and the render pass's clear. For a game, capture both frequent `phys_footprint` samples and the kernel's peak ledger; the existing `resident` log label denotes footprint, and staging blocks `created in total` is cumulative, not live memory.
- **Found on:** [The Legend of Zelda: Tears of the Kingdom](../../dm/games/0100F2C0115B6000/README.md#memory), investigating issue #147. Mac reproduction and device validation are tracked in the game note.

### Placed pools commit what the game only reserved

- **Symptom:** on the phone, `MemAvailable` falls under a few hundred MB right after a game's first frames, with most of the Vulkan memory in placed pools (`memory: placed pools … MiB` lines, `DM_VK_MEMLOG`) and most of the process's PSS in `/dev/kgsl-3d0` mappings.
- **Cause:** the Vulkan replay swapped every NVN memory pool's pages for placed Vulkan memory when the game made the pool (`mtl_pool_add`, `vka_mem.c`). Driver memory is committed whole when it is allocated, while guest memory is committed page by page as it is touched. Games reserve far more pool memory than they fill: the pool census (`DM_NVN_POOLS=1`, `hle_nvn.c`: pools by flags, the bytes their buffers and textures cover, the bytes that are not zero) found 4,641 MiB of pools at Mario Kart World 1.8.0's first frame, of which 765 MiB are not zero: a 2.37 GiB `CPU_CACHED | GPU_CACHED` texture heap with 349 MiB of textures and no buffer, 1,183 MiB of physical pools (`PHYSICAL | GPU_NO_ACCESS | COMPRESSIBLE`) that only back virtual pools, 371 MiB of `CPU_NO_ACCESS` texture pools. The replay reads textures from guest memory on the CPU into images of their own, so none of that needs device memory.
- **Fix:** a pool becomes placed memory when the GPU is first given an address in it (`mtl_pool_need`, `vka_mem.c`): a buffer made on it, `nvnBufferGetAddress`, `nvnMemoryPoolGetBufferAddress`, `nvnTextureGetTextureAddress`, and linear textures (their GPU content is copied back into the storage). NVN gives the GPU no other address of a pool (events and counters are written by the CPU, descriptor and command memory are host state). The pool is placed whole, on the thread that asks. Its pages may be tracked by then, so the swap holds the dirty tracker over its range (`nvn_dirty_hold`: protected pages released and stamped, none protected until the swap ends) and the swap's fault hooks are registered at the first `mtl_pool_add`, before the tracker's. Texture uploads read pages the guest has not mapped as zeros (`dm_guest_read_mapped`, `hle_svc.c`). `DM_VK_PLACE_LAZY=0` places every pool when it is made, as before.
- **Check:** Mario Kart World 1.8.0 on the phone (m21 → m22, `DM_VK_SPARSE_DENSE_MB=32`): placed pools 4,641 → 558 MiB, Vulkan memory 6,371 → 2,320 MiB, PSS 5.8 → 2.7 GB at the first frames; the first frame came at 14 s instead of 16 s. Open: placing a large pool takes about 0.7 ms a MiB on the thread that first asks (a 2 GiB pool 1.5 s), and the tracked textures of a pool upload again after its placement. A buffer, a linear texture or a texture address in a large pool placed all of it: resolved for pools of 1 GiB and more ([Large pools placed whole for one buffer in them](#large-pools-placed-whole-for-one-buffer-in-them-android)).
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md) 1.8.0: stopped by the run script's memory stop 2 s after its first frames.

### Large pools placed whole for one buffer in them (Android)

- **Symptom:** on the phone, the low-memory killer ends a game before its first frame; `[vk] memory pool <addr>+<size> placed when the GPU was given <addr>` names a pool of several GiB, and `placed memory: … MiB faulted in so far` jumps by its size.
- **Cause:** a pool became placed memory whole when the GPU was first given any address in it ([Placed pools commit what the game only reserved](#placed-pools-commit-what-the-game-only-reserved)), and driver memory is committed when it is allocated. Pokémon Pokopia makes a 3.4 GiB `CPU_UNCACHED | GPU_CACHED | COMPRESSIBLE` (0x0a2) pool before its first frame, its general GPU heap, and creates a 3 KiB buffer 38 MiB into it: 3,500 MiB of committed Vulkan memory for it alone (4,088 MiB of placed pools, 12.5 GB resident, killed 28 s in). The pool census (`DM_NVN_POOLS=1`) at present 300 of the opening: 978 buffers covering 8.8 MiB and 551 textures 932 MiB of it, 2,561 MiB covered by nothing.
- **Fix:** a pool of at least `DM_VK_PLACE_PART_MB` (1024) is placed by parts (`vka_mem.c` `mtl_pool_need`, the range arithmetic in `vka_place.h`): the granules of `DM_VK_PLACE_GRANULE_MB` (16, counted from the pool's start) that the range the GPU is given touches become one placed segment; the pool keeps its parts' references (a segment it holds takes no second one in `cover`), a bit a granule says which are placed, and an ask in placed granules returns without a lock. An ask over the whole pool (`nvnMemoryPoolGetBufferAddress`) places the rest. NVN gives the GPU an address only by a buffer, a texture or the pool's own address, so a granule none of them lies in is never sent to. `DM_VK_PLACE_PART_MB=0` places every pool whole, as before. The log names each ask (`… placed when the GPU was given <addr>+<len> (a buffer; …)`).
- **Check:** `make -C dm/host/tests GAME=<id> run` (`t_android_place`: the parts an ask places, clipped to the pool; whole-pool asks). Pokémon Pokopia on the phone: placed pools at its first frame 4,088 → 652 MiB, its first frame at 22 s (cold file cache) instead of the kill; in the opening (frame 7,500, 147 s) the 3.4 GiB pool had 1.3 GiB placed in 16 MiB parts (1.9 GiB in 64 MiB parts), all pools 2.9 GiB.
- **Open:** a range given to the GPU across a part placed earlier and one placed now lay in two segments: resolved, the parts are joined ([A range given to the GPU across two placed parts of a pool](#a-range-given-to-the-gpu-across-two-placed-parts-of-a-pool-android)). Still open: a pool placed whole after parts (an ask over the whole pool) keeps its parts as segments, so a range across their ends lies in two (`placed whole after N parts … ranges across the parts' ends lie in two segments`); joining them would hold the pool's bytes twice for a moment.
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#memory) (v655360) on the Honor PNM-N49.

### A range given to the GPU across two placed parts of a pool (Android)

- **Symptom:** on the phone, objects drawn with parts missing or without their textures, in a game with a pool of 1 GiB or more. The log has `[RED] vk: memory pool <addr>+<size> (placed by parts): the GPU is given <addr>+<len> (a buffer) across two of its parts: lookups over the whole range fail (draws that need it in one piece are skipped)` (once per pool), and later `[RED] vk: index buffer at <addr> is not in placed guest RAM: skipped` (or `indirect draw arguments at …`) with addresses in that pool. Since the fix only when the parts could not be joined: `[RED] vk: memory pool …: <addr>+<len> (a buffer) lies across N of its parts, …, which are not joined (<reason>)`.
- **Cause:** a pool placed by parts ([Large pools placed whole for one buffer in them](#large-pools-placed-whole-for-one-buffer-in-them-android)) becomes one placed segment per ask: one VkDeviceMemory, one VkBuffer, its own device address. A buffer made later from the last bytes of a part placed earlier into a granule not placed yet places that granule as a second segment, so the buffer's bytes lie in two allocations whose device addresses do not follow on. The same when two buffers placed two neighbouring parts and a third is made across both. Lookups that need a range in one piece (`vka_addr`) fail there: an index buffer or indirect arguments skip the draw, a storage buffer is cut at the first segment's end (uniform buffers and copies go by runs and still work). VK_EXT_map_memory_placed maps one allocation at one address, so a segment cannot grow in place.
- **Fix:** general, in `dm/gfx/vk_android/vka_mem.c` "Joining parts" (the run arithmetic `vkp_join` in `vka_place.h`). The ask that lies across parts (`mtl_pool_need`, also when it places nothing: `join_placed`) queues them; at the start of the replay's next submission (`vka_mem_join_due` from `vka_rp_sub_begin`), the open upload batch is flushed and the queue waited idle (`vka_queue_idle`), and the run of segments is made one: a new allocation of the guest type, the bytes copied in under the swap (the dirty tracker held, writers waiting in the fault hook), the old allocations freed (before the new map: the Adreno driver's vkFreeMemory takes the placed range down), the new one mapped placed over the range and prefaulted, the protections put back, and the table's generation bumped, which every cache of segment buffers and device addresses is keyed by. The join waits for that safe point because the GPU may still read or write the old memory and the replay may be recording commands that name its buffer; the game's commands that use the new buffer come in a later submission, which begins with the join. Only segments the pool alone holds are joined, at most `DM_VK_PLACE_JOIN_MB` (256) a join (the joined bytes are held twice for a moment); a larger or shared run, or a pool being placed by another thread at that moment, keeps the old behaviour for that submission (`[RED] … which are not joined (<reason>)`). `DM_VK_PLACE_JOIN_MB=0` turns joins off. Log: `… across two of its parts: they are joined into one at the replay's next submission`, then `memory pool …: N parts joined into one, <addr>+<len>, for <addr>+<len> (…; queue idle X ms, join Y ms; K joins)`.
- **Check:** `make -C dm/host/tests GAME=<id> run`: `t_android_place` checks `vkp_join` (one segment, segments end to end, gaps, the bounds, a wider stride), Pokopia's straddle from the v0.2.6 log (two segments without the join, one after it, the two granules), and a model of placing by parts with joins over 400 asks of 256 B to 48 MiB in a 3.4 GiB pool of 16 MiB granules: every ask, the 9 across parts included, lies in one segment after its submission begins (a buffer over two parts that two earlier asks placed too), the segments stay sorted, disjoint and granule-aligned, and they cover exactly the granules asked for. Not yet run on a phone: the join itself (the placed map at the freed range on both drivers), its hitch (the queue idle and the copy) and the missing textures.
- **Open:** a pool placed whole after parts is not joined ([above](#large-pools-placed-whole-for-one-buffer-in-them-android)). A system call that reads or writes the range during the join, between the free and the placed map, fails with EFAULT instead of waiting, as during a compaction.
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#android) (v655360, v0.2.6) on a player's Lenovo TB321FU (Adreno 750, Turnip): `0x41a99dab00+0x20a60` across two parts of its 3.4 GiB pool at 32 s, then four index buffers in that pool skipped at 168 s, reported as "a Pokémon has missing textures". A second log the same week: `0x41a79f9080+0x6888` in the same pool.

### A log line inside a placed-memory swap stops every thread (Android)

- **Symptom:** on the phone a game stops for good, not crashed: no more frames, and the log stops in the middle of the frame statistics (no audio lines, no control lines, no watchdog line either).
- **Cause:** a cycle through stderr's lock. `LOG` takes stderr's lock (`flockfile`) before it reads its arguments. The thread placing a pool holds the dirty tracker (`nvn_dirty_hold`) across the swap and wrote a log line inside it (`prefault`'s `placed memory: … faulted in so far`). The game thread's statistics line had `mtl_cpu_tex_count()` among its arguments, which takes the replay's texture lock, and the replay thread held that lock while it waited for the dirty tracker (`nvn_dirty_protect`). Placement → stderr → game thread → texture lock → replay thread → tracker → placement. Rare while pools were placed only at boot; with pools placed by parts during play it came within a minute.
- **Fix:** no log line inside the swap (`prefault_line` logs after it ends); the memory line of `vka_mem_grew` after the segment table's lock is dropped; the statistics read `mtl_cpu_tex_count()` and `mtl_pkg_miss()` before their `LOG`. A fault the swap's own thread takes in its range is no longer held back in the swap's fault hook (it spun for ever with every lock the swap holds): it goes on to the crash handler.
- **Check:** Pokémon Pokopia on the phone: the stop at frame 1,200 (p4, the log cut at `translation up to frame 1200`) did not come back with the fix (p5: the log and the watchdog alive to the end).
- **Found on:** [Pokémon Pokopia](../../dm/games/0400A3A01EE4C000/README.md#memory).

### Upload staging grows within one Vulkan submission (Android)

- **Symptom:** on the phone, a game is stopped by the low-memory killer before its first frame, or `MemAvailable` falls under a few hundred MB, while textures are first uploaded. `memory:` lines (`DM_VK_MEMLOG`, every 512 MiB of growth) show scratch rising by hundreds of MiB per line.
- **Cause:** the Vulkan replay deswizzles every upload into scratch memory (`vka_scratch`, `vka_dev.c`), and a span is reused only after the fence of the whole submission that took it. Uploads recorded into one submission therefore stay held until that submission is done, however many parts it is sent in. Before 2026-11-03 the blocks were also never freed: a 144 MiB block made for one level stayed for the process's life.
- **Fix:** staging retires on its own completion (`vka_dev.c` "Upload batches"). A new image's first content (upload or clear) is recorded into an upload batch, a command buffer of its own whose staging is retired at the batch's value on a second timeline semaphore. A batch goes to the queue once its staging passes `DM_VK_UPLOAD_BATCH_MB` (64), and always before the replay hands a part or the submission to the queue, so the queue runs it before every command that uses the image; it ends with a full barrier. Only new images go this way: nothing recorded earlier in the submission reads them, so running them early changes nothing; re-uploads of live images stay in the submission, in order with the draws before them. With more than `DM_VK_UPLOAD_INFLIGHT_MB` (256) of batch staging in flight the replay thread waits for the oldest batch, outside the image table's lock. Sparse textures are uploaded by bands (one row of GOB blocks, one range of the storage, `nvn_deswizzle_bands`): bands with nothing mapped are copied as zero texels from a fixed 4 MiB buffer, so staging is about what is mapped, never a whole level, and the whole-range copy for a sparse pool's other textures is gone. Scratch reuse is best fit, and idle blocks larger than 16 MiB, or beyond 64 MiB idle in all, are freed at every miss and every batch retire. Splitting the submission instead was not taken: `upload()` and `vka_tex_get` take the command buffer as an argument down several levels, and a split inside them would leave callers recording into a buffer already ended. `DM_VK_UPLOAD_BATCH=0` records first contents into the submission, as before.
- **Check:** `make -C dm/gfx/tex/tests run` (N: each band deswizzled from its own bytes only equals the whole level). On the phone, the `DM_VK_MEMLOG` lines: Mario Kart World 1.8.0's scratch peaked at 256 MiB and was 96-144 MiB when its run ended (1,488 MiB before). Donkey Kong Bananza ran unchanged: 30 fps, the same `[RED]` lines, the same PSS.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md) 1.8.0 at boot: 1,488 MiB of scratch in flight, next to 4,494 MiB of placed pools and 3,204 MiB of images (sparse images counted at their full size). The 16 GB phone stopped it 14 s in.

### Write tracking of small textures fills the process's memory maps (Android)

- **Symptom:** (Android) a game that has run for minutes stops with an allocation failure in a thread that has nothing to do with it: `scudo::reportMapError`, an `mremap` check failure in the garbage collector, `SIGABRT` on `vk-present` or `HeapTaskDaemon`, and no `-4` before it. `/proc/<pid>/maps` has about 65,530 lines (`vm.max_map_count`), most of them single pages of `/kgsl-3d0`. Or the host stops on a guest memory call: `FATAL SVC 0x2c mprotect 0x40fe420000+0x22000 errno=12` (MapPhysicalMemory in the alias region, `hle_svc.c`; ENOMEM is also Linux's answer when a split would pass the limit), then `CRASH sig=6 … pc=abort+0xa0`. Since the fix below such a stop is preceded by `[RED] MapPhysicalMemory mprotect …: ENOMEM with N memory maps in the process (vm.max_map_count M)` (also for `guest_release` and `SetHeapSize`), and the `[vk] memory maps:` lines show the count climbing.
- **Cause:** the dirty-page tracker (`nvn_dirty.c`) write-protects a tracked texture's pages. mprotect splits a map, and the kernel driver's GPU memory maps never merge again (kgsl's mappings are special mappings with a close handler, which the kernel never merges), so each page ever protected on its own stays a mapping of its own. A game with thousands of textures of one page each leaves one mapping per texture. Blocks (below) bound a placed pool's splits to its bytes / 64 KiB, which still grows over a long session: every 64 KiB block of a placed texture pool that the game writes once and the replay protects again is a split for good, and Mario Kart World places gigabytes of pool memory with textures in it (a 2.37 GiB texture heap alone is 38,000 blocks). Its title held 34-36k maps after 200 s, and the v0.2.1 report (update 917504, Galaxy Z Fold 8, Adreno 840, Turnip) stopped after about seven minutes of racing, in a second session, with the `FATAL SVC 0x2c` form. A second, smaller source, in anonymous memory: a fixed map inside the guest block (`guest_release`, every UnmapPhysicalMemory and heap shrink; the replay's give-back fallback) had no name, the rest of the block is named `nxnative guest`, and the kernel merges anonymous neighbours only when their names match: each such range stayed a mapping of its own beside its named neighbours, whatever their protections. (Pools given back by the replay (`unplace`) are moved in with mremap and keep their own page offset: one mapping each until the range is given back to the system; bounded by the pools, not fixed.)
- **Fix:** past `DM_DIRTY_BLOCK_AT` regions protected for the first time (default 8,192), protection changes in aligned blocks of `DM_DIRTY_BLOCK_KB` (64 on Android), so splits land only on block boundaries. A write stamps its whole block, so a texture beside it may upload again: that costs recording time, which is why it waits for the count. Regions, not pages: a large texture is many pages and one split. The log says `from now on in blocks` when it starts. Then, general, on Android (`dm/gfx/vk_android/vka_mem.c` "The process's memory maps", the policy in `vka_mapbudget.h`, `nvn_dirty_block_at_least`): a thread (`vk-maps`) counts the lines of `/proc/self/maps` every `DM_VK_MAPS_PERIOD_S` seconds (5), with the pieces of each placed segment, against `vm.max_map_count` (read from `/proc/sys/vm/max_map_count`), and the tracker's blocks follow the count: 64 KiB from 40 % of the limit (whatever `DM_DIRTY_BLOCK_AT` says), 256 KiB from 50 %, 1 MiB from 60 %, 4 MiB from 70 %. A coarser block's boundaries are among a finer one's, so from then on new splits land only on the coarse boundaries (a pool's possible splits fall 4 times at each step). Splits made before stay, so past `DM_VK_MAPS_BUDGET` (75 %) the placed segments with the most pieces get their CPU map made again in one piece (compaction, down to 55 %; at most `DM_VK_MAPS_COMPACT_N`, 8, segments a round and a round every 20 s): the tracker is held over the segment as for a placement (its protected pages released and stamped, so their textures upload again once), the CPU map is unmapped and the same memory mapped placed at the same address, faulted in before any protection splits it ([placed pool memory split by mprotect](rendering.md#placed-pool-memory-split-by-mprotect-on-the-adreno-driver)), and the range's other protections put back; the memory, its buffer and its GPU address do not change. A placed map that fails twice stops the host (`FATAL compacting pool memory …`): the segment's lookups would name memory the CPU no longer sees. And every fixed map in the guest block is named `nxnative guest` again (`plat_mem_name_guest`). Log lines: `[vk] memory maps: N of M (vm.max_map_count, P %): placed memory … in … segments (… split, … pieces more than one each), guest block anonymous …, outside the guest block … (… of them kgsl); dirty tracking by blocks of … KiB` at the first count, every 60 s, at each 10 % step and after each change; `… over the budget: K placed segments … made one piece each again` after a compaction; the count also ends the `placed memory: N placements:` line. `DM_VK_MAPS_COMPACT=0` keeps the blocks and leaves compaction out; `DM_VK_MAPS=0` turns the thread off.
- **Check:** `t_dirty_race` and `t_dirty_retire_race` pass on the device with `DM_DIRTY_BLOCK_AT` at 0, 2 and 8192. Mario Kart World's title, 200 s: 61,247 mappings (38,464 of `/kgsl-3d0`) page by page, 33,807 and 36,164 (10,806 and 13,461) with blocks. Donkey Kong Bananza and Pokémon Pokopia never reach the count. The memory maps budget is checked by unit tests only: `dm/gfx/tests/t_dirty_maps.c` plays the tracker over a 256 MiB pool with the driver's never-merge rule modelled (each boundary an mprotect cuts stays) and a model limit of 4,000 maps: as before, the pool alone reaches 11,433; with the policy from the start the count peaks at 2,565 (blocks of 1 MiB, no compaction); started late, at 80 % of the limit, it peaks at 3,104 and one compaction brings it to 1,265 at the end; no write after an upload is missed in any run. `dm/host/tests/t_android_mapbudget.c` checks the levels, the picks and the parsing of the maps' lines. Not yet run on a phone: the cost of the coarser blocks (uploads again of textures beside a written one), the compaction's hitch (its textures upload again) and that the drivers map a segment's memory again at the same address (Qualcomm's and Turnip), the count over an eight-minute race, and how much the naming fix and the other sources (`guest block anonymous`, `outside the guest block`) contribute.
- **Open:** a system call that reads or writes a segment's range during its compaction, between the unmap and the placed map (microseconds), fails with EFAULT instead of waiting, as during a give-back. Maps outside placed memory (the guest block's anonymous pieces, libraries, the heap, the driver's own) are only counted: if they are what climbs, the `[RED] memory maps: … placed memory's pieces cover only …` line says so.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#found-on-this-game) on an AYN Odin 3 Ultra (Adreno 830, Turnip T30): 66,004 mappings at the abort, 39,726 of them single pages of `/kgsl-3d0`, with about 32,000 tracked textures, most 64x64 ASTC 8x8 of about 4 KiB. It stopped after about five minutes of play. With blocks (v0.2.1): a Galaxy Z Fold 8 (Adreno 840, Turnip, 16 GB), update 917504, after about seven minutes of racing at about 26 fps, `FATAL SVC 0x2c mprotect … errno=12`.

### Long driver compiles at once fill the process's memory maps (Android)

- **Symptom:** (Android, Turnip) stutter that comes and goes during the first minutes, then a crash inside the driver on a prewarm thread: `CRASH sig=11 addr=0` with `vk-prewarm` threads in `libvulkan_freedreno.so`, or `libc++abi: terminating due to uncaught exception of type St9bad_alloc`. Before it, `[vk] memory maps:` lines whose `outside the guest block` count jumps from about 6,000 to tens of thousands within seconds and falls back as quickly, and `[RED] vk: memory maps: … placed memory's pieces cover only 0 of them`. The `DM_VK_MAPS_HIST` lines name two groups as almost all of it, in equal numbers: `rw-p <=1M [anon:scudo:secondary]` and `---p <=64K (anonymous)`, followed by `being made now:` lines of prewarm builds that have run for seconds.
- **Cause:** some vertex and mesh shaders take Turnip 8-22 s to compile, every run (the pipeline cache's creation feedback reports a hit and still 8-18 s in the vertex stage), and for that time the compiler holds thousands of blocks of 64 KiB to 1 MiB. Android's allocator (scudo) gives each block of that size its own mapping with a guard mapping beside it: two process maps a block. The prewarm threads (`DM_VK_PREWARM`, four) checked memory only before a compile started (`DM_VK_PREWARM_MEM_MB`), so three or four such compiles ran at once, two of them sometimes of the same vertex shader: 27,000 blocks, 4.1 GB, 54,000 maps. Past `vm.max_map_count` the driver's next allocation fails. The same compiles take the phone's free memory under 1 GB while they run, which makes the game's own code and the shader library fault in from storage again (up to 2,500 major faults a frame): the stutter.
- **Fix:** a workaround, general, for the compiler's allocations, which the host cannot change (`dm/gfx/vk_android/vka_pso.c` `pw_heavy_hold`): before each compile a prewarm thread holds while any pipeline build in the process (frame path, asynchronous, prewarm) has run for `DM_VK_PREWARM_HEAVY_MS` (1000) or more, or while another build of the same vertex, mesh or compute shader runs. A shader whose build took that long is remembered beside the driver's pipeline cache (`<cache file>.heavy`, `build_end`), and a known one is held from its start while another known one builds: the age check alone let three that started in the same second through (58,619 maps). That still let unknown ones start together: four that had not been built in the runs before (`e963ef2241a51be8`, `cf04467527cbcf8f`, `171409a493cf5268`, 11-12 s each) started within one second and took the process to 66,160 maps again. So on Turnip (`driverID` `VK_DRIVER_ID_MESA_TURNIP`) prewarm builds never overlap at all (`g_pw_one`; `DM_VK_PREWARM_OVERLAP=1` lets each thread build on its own, as before, and is the default on other drivers, whose compilers have not shown the problem, Qualcomm's included (below); `=0` holds them on any driver): the threads look up and prepare their keys in parallel, one of them builds at a time, and a warm run's cache hits take milliseconds each. The frame path and the asynchronous threads are never held. The prewarm summary line says how long the threads held (`… for a long compile (DM_VK_PREWARM_HEAVY_MS)`). Diagnostic: `DM_VK_MAPS_HIST` (40 % of the limit by default) logs the 10 largest groups of maps outside the guest block by name, permissions and size, and the builds running at that moment (`vka_mem.c` `maps_hist_log`, `vka_mapbudget.h` `vkmb_hist`).
- **Check:** `dm/host/tests/t_android_mapbudget.c` checks the line fields, the name folding, the size buckets and the histogram. Galaxy S25, Turnip Gen8 V39-patched, Ocarina of Time from the title, 60-80 s each: before, 55,741 (v0.2.4), 58,566 and 66,160 maps (two runs; the second crashed at 17 s); with the age check alone, 58,619 (three long compiles started in the same second); with the remembered shaders, a second run peaked at 51,073 (77 %) with one long build at every peak and did not crash, frame time p95 17.7-19.4 ms at its end against 30-38 ms before. One long compile alone still adds about 28,000 maps (`e85675e0a97aecfd`, `04452448ac915259`: 18.6 s each). Then a run with four unknown long ones at once crashed again (66,160 at 16 s); with one prewarm build at a time, 72 s through both opening movies: 36,972 maps at most (56 %), one prewarm build at the peak, no crash. Qualcomm's system driver on the same phone (build 03/26/26), second run, 42 s: 21,450 maps at most (32 %), about 9,000 outside the guest block, its long compiles 3-6 s (24 remembered), no crash; that driver's compiler does not take the maps with it. Other games have not run it yet.
- **Open:** why these shaders take Turnip that long and that much memory (a driver matter), and that the same vertex shader is compiled again for each pipeline that uses it; graphics pipeline libraries would make its pre-rasterization part once.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) on a Galaxy S25 (Adreno 830, Turnip Gen8 V39-patched): maps outside the guest block from 6,000 at 7 s to 59,662 at 17 s (66,160 in all), three prewarm builds running (mesh `4c7d6be5a7717c8d` for 13 s, vertex `b1f06157308e3b22` twice), then `CRASH sig=11 addr=0` and `std::bad_alloc`.

### A failed write protection hid CPU writes

- **Symptom:** a texture the CPU writes after its upload keeps its first content (stale or black) while the `packaged textures` line shows no re-uploads for it. With `DM_VK_NANSCAN` on, `NaN scan: watch: storage of texture serial … changed with no CPU fault` names it, and its `mprotect failures N (errno E …)` is above 0. Since the fix: `[RED] dirty-page tracking: mprotect(read-only) of … failed (errno …) in pool …; process mappings …, vm.max_map_count …`, once per pool, and the `packaged textures` line ends with `mprotect failures N (last errno E)`.
- **Cause:** the dirty-page tracker (`dm/gfx/nvn/nvn_dirty.c`) set a page's state to protected after `mprotect(PROT_READ)` whatever the call answered. A page left writable never faults, so no later CPU write to it was stamped and every texture over it kept its first upload. The reverse too: an unprotection that failed set the page to writable while it was still read-only, so the game's next write re-executed in the fault handler forever. The addresses are page-aligned (ranges rounded to the host page, blocks aligned), so EINVAL does not occur; on Android `mprotect` fails with ENOMEM once a split would pass `vm.max_map_count` (the [memory maps limit](#write-tracking-of-small-textures-fills-the-processs-memory-maps-android), which Mario Kart World reaches), or when part of the range is not mapped, and Linux may have changed part of the range before it fails.
- **Fix:** the state follows what `mprotect` did. A run whose protection fails is made writable again (page by page if that fails too), stays writable in the tracker and takes the highest generation, so the textures over it count as written at every check and upload again, as an untracked texture does, until a later protection succeeds and stamps it. A page that cannot be made writable again stays protected (its first write faults into the handler, which tries again). An unprotection that fails leaves the page protected, so the fault reaches the crash handler instead of looping. `mp()` keeps `errno` for the fault path, and the last failure's address, length and protection are kept for `nvn_dirty_debug`.
- **Check:** `dm/gfx/tests/t_dirty_mpfail.c` makes `mprotect` fail on demand (with no effect, or after changing the first page): after a failed protection the pages are writable and the texture counts as written at every check; the next protection that succeeds tracks writes again; after a failed unprotection the page stays protected and read-only. `t_dirty_race`, `t_dirty_retire_race`, `t_dirty_maps` and `t_dirty_slots` pass. Not run on a phone.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game), by reading the code while looking for why Link's house's walls are black. It is not that cause: Swap2-Native's build of the game, which has this fix, logs `mprotect failures 0` on the phone, and our runs in the house stay at 58-62 % of `vm.max_map_count`.

### Cleared images the GPU never writes hold memory of their own (Android)

- **Symptom:** on the phone, the ctl stats show most image memory in images nothing has written: `ctl: images not GPU-written: cleared 1655 MB (325 …)` beside `GPU-written 794 MB`, and `large image: … 16384x16384 … format 0x1 … flags 0x28: 341.2 MiB` four times (`DM_VK_BIGIMG_MB`).
- **Cause:** every image whose content is the GPU's (`storage_mode` ST_ZERO: render targets, copy destinations, shader images) got memory of its own when it was made, cleared to zero, whether or not anything ever wrote it. Engines make such targets long before they draw into them, or never. On the Switch the texture costs only its pool storage, which the game already holds. Mario Kart World 1.8.0's four 16384² R8 terrain targets (SPARSE | COMPRESSIBLE; the Adreno 840 has no sparse residency for 8-bit formats, [GPU-written sparse textures as sparse residency images on the Vulkan replay](nvn-objects.md#gpu-written-sparse-textures-as-sparse-residency-images-on-the-vulkan-replay)) take 1,365 MiB that in the measured scene only ever hold zeros. A diagnostic run (`DM_VK_BIGIMG_MB=16`, the `ctl: large images the GPU has not written` line, the first-write and storage-overlap lines) showed that no draw, clear, copy or shader image writes them, that no other texture object lies over their storage, and that 340-800 draws sample them: zeros are what they hold.
- **Fix:** general, in the Vulkan replay (`dm/gfx/vk_android/vka_tex.c` "Zero-shared images", `vka_imgmem.c` `vka_imem_bind_zero`, `vka_zshare.h`). A new image of at least `DM_VK_ZSHARE_MB` (4) of storage whose content is ST_ZERO, dense, single-sampled, not 3D, not block-compressed, not linear and not a display texture is made with `VK_IMAGE_CREATE_ALIAS_BIT` and bound at offset 0 of one zeroed allocation per identical create info (format, extent, levels, layers, usage, format list, flags, memory type, size and alignment), which Vulkan's aliasing rules let every such image read alike. Each image's first use clears it as before (zeros onto zeros, which also sets its layout and compression metadata), behind the upload batch's barriers. Before its first write (`vka_tex_own`: an attachment at render-pass begin, a colour, depth or texture clear, a copy, blit or resolve destination, a buffer-to-image copy, a shader image, a CPU re-upload, a capture restore) the image gets memory of its own (`img_own`): a new image of the same texture, cleared in the upload batch, swapped in place as `img_storage_upgrade` does (views, the recording memo and the texture IDs that name it are made again); the old one goes after the submission, or once a holder (the present, frame generation) lets it go. A write that comes without it is logged `[RED] … without memory of its own`. The shared bytes are counted once in the `memory:` lines and the stats (`image memory: … zero-shared: N images in K allocations (X MiB, Y MiB saved), M made their own`). `DM_VK_ZSHARE=0` gives every image memory of its own, as before. Checked by `dm/host/tests/t_android_zshare.c`.
- **Check:** Mario Kart World 1.8.0, handheld, the same 24 s roaming run (zs0 off, zs1 on): images 4,037 → 2,964 MB (`zero-shared: 6 images in 3 allocations (429 MiB, 1024 MiB saved), 12 made their own`), cleared images 1,655 → 134 MB, MemAvailable at the snapshot 661 → 992 MB and swap in use 7.6 → 6.9 GiB; 40.0 / 40.8 fps, GPU 11.2 ms both; the same pictures (world map and road), no new `[RED]` kind, and no `R8` alias written. The images' bytes a texel are unchanged with ALIAS_BIT (`target … 4.00-4.02 a texel`). Donkey Kong Bananza with it on: `[mark]` at 32.9 s, 30.5 fps, its usual 14 `[RED]`, picture correct (8 images shared, 24 MiB saved).
- **Open:** a texture ID in the bindless table that names an image made its own in the middle of a submission is written again at the next submission (as after `img_storage_upgrade`), so a bindless sample later in that same submission reads the zeros of the shared memory. GPU writes into a zero-shared image's storage through buffers (copies or shader stores into the pool) are not its content on the replay, as for every ST_ZERO image. If the game draws into the R8 targets on another course, they get their full memory then (a 341 MiB allocation at that moment); the sparse-residency forms for that case are a separate step.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md) 1.8.0 on the Honor PNM-N49 (2026-11-04).

### Zero-sharing capped at 32 MiB leaves out the large targets it was made for (Android)

- **Symptom:** none seen by players yet. With `DM_VK_BIGIMG_MB` the four `16384x16384 … format 0x1` targets of Mario Kart World 1.8.0 are expected to show again with memory of their own (341.2 MiB each), and the stats' `zero-shared:` line to have no such allocation.
- **Cause:** a319e773 caps [zero-shared images](#cleared-images-the-gpu-never-writes-hold-memory-of-their-own-android) at 32 MiB of storage (`vka_zshare.h` `vkz_candidate`: `storage_bytes <= 32 MiB`), to stop the giant depth duplication its commit names on Ocarina of Time. That also turns zero-sharing off for Mario Kart World's four 16384² R8 terrain targets (341 MiB each with their levels), the case it was made for: 0465aa1d measured about 1 GB (1,024 MiB) saved by sharing them. So Mario Kart World probably uses about 1 GB more image memory than with 0465aa1d alone (not measured).
- **Fix:** open. The cap stays in v0.2.0 (the build tested on the phone); `dm/host/tests/t_android_zshare.c` checks the current rule (341 MiB not a candidate, 32 MiB and less one). The fix: find which images made Ocarina of Time's depth copies and exclude what caused them, instead of capping by size; then measure Mario Kart World's image memory with and without it.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md#found-on-this-game) (the R8 targets it no longer shares) and [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) (the depth duplication that led to the cap).

### Shader-code pools placed though the GPU never reads them (Android)

- **Symptom:** NVN `SHADER_CODE` pools sit in unswappable driver memory (`/dev/kgsl-3d0` mappings) though nothing on the GPU reads them, and the [file-backed pools](#pools-the-gpu-never-reads-cost-zram-android)' `shader` kind saves nothing: each such pool is punched out of its file right after the move. Anka Native measured 205 of them in The Legend of Zelda: Ocarina of Time, 345 MiB of driver memory (one pool 244 MiB).
- **Cause:** lazy placement ([Placed pools commit what the game only reserved](#placed-pools-commit-what-the-game-only-reserved)) placed a pool when the game took its address (`nvnMemoryPoolGetBufferAddress`) or made a buffer object over it. For a `SHADER_CODE` pool those are how a game computes program addresses for `nvnProgramSetShaders`, and the Vulkan replay never hands the GPU shader code: the host hashes the code on the CPU (`hle_nvn.c` `keys_hash`) and draws with its own SPIR-V library.
- **Fix:** from [Anka Native](https://github.com/EddizEge/AnkaNative) by EddizEge (MIT, [android/NOTICE.md](../../android/NOTICE.md)), here the default for every game on Android (`DM_VK_PLACE_SHADER_POOLS=0`; `1` places them for their address again, and turns the file-backed `shader` kind off with it; the Metal host keeps `1`, where nothing is saved). `hle_nvn.c` "Shader-code pools" keeps a table of the live `SHADER_CODE` pools, read at record time without a lock. Such a pool is placed only for a use that hands the GPU data in it: a recorded command naming an address in it (vertex, index, uniform, storage and transform-feedback buffers, indirect and multi-draw arguments and counts, copies at either end, buffer-texture copies, clears, uniform updates, reports, conditional render; `shp_bind`, the command's range or, size not known there, to the pool's end), a texture over it, or a mapping of it into a virtual pool. That is every NVN command that carries an address, and the replay resolves only addresses that came in commands. Its address and buffer objects over it do not place it. The key hash reads code in such a pool as guest memory (`nvn_shader_code_readable`). `DM_VK_SHPOOL_LOG=1` logs each pool's uses once per pool and kind, and a `[nvn] shader-code pools at present` summary at presents 60, 300 and every 1800.
- **Check:** `make -C dm/gfx/tests GAME=<id> t_nvn` (section 9: the table, which uses count as program addresses and which as data, the key hash's read, Finalize). Not run on a phone here yet; Anka Native ran Ocarina of Time with it (KGSL memory -0.35 GB).
- **Open:** a shader that dereferences a raw pointer loaded from memory (raw global memory, `vka_draw.c` `gmem_map`) into a shader-code pool that no command named reads the replay's sink, not the data, and a store there is lost: the pool table holds placed memory only. Before this change any pool whose address the game took was placed, so such a pointer was always backed; `SHADER_CODE` pools are now the one exception. No command shows such a use, so `DM_VK_SHPOOL_LOG` cannot list it. The raw pointers known in our games all point at data the game also binds or streams into its data pools: Donkey Kong Bananza's terrain records and agl's compute load ([Global memory at an address loaded from memory](shaders.md#global-memory-at-an-address-loaded-from-memory)), Ocarina of Time's fog probe grid; none is known to point into a shader-code pool, but that is not measured. A picture that differs with `DM_VK_PLACE_SHADER_POOLS=1` is the check.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (Anka Native's measurements).

### Pools the GPU never reads cost zram (Android)

- **Symptom:** on a phone short of RAM, a game's large memory pools that only the CPU reads sit in zram: the footprint lines (`DM_MEM_FOOT=1`) show them swapped, never resident, with thousands of major faults a second where they are read. The Legend of Zelda: Ocarina of Time (`0400486024DEC000`) has two texture pools of 1,737 and 232 MiB; since the [pool-only textures fix](rendering.md#textures-read-only-through-the-pool-were-never-made-android) it also holds about 3 GiB of images.
- **Cause:** a pool the GPU is never given (lazy placement, `DM_VK_PLACE_LAZY`) stays private anonymous memory: written once, then read rarely on the CPU (the Vulkan replay reads texture storage to make its images). Under pressure the kernel compresses it into zram, which keeps about 0.6-0.7 of each byte in RAM. Clean file pages need no RAM copy: the kernel drops them and reads them back from flash.
- **Fix:** `DM_MEM_FILEBACK` (default 1 with the `shader` kind; `0` off), from [Anka Native](https://github.com/EddizEge/AnkaNative) by EddizEge (MIT, [android/NOTICE.md](../../android/NOTICE.md)); the launcher's per-game **Game settings › RAM saver (uses storage)** adds the texture kind (`DM_MEM_FILEBACK=1 DM_MEM_FILEBACK_KINDS=shader,texture`). At `nvnMemoryPoolInitialize` a pool of those kinds becomes a `MAP_SHARED` mapping of an unlinked sparse file in TMPDIR (the app's cache folder) through the placement swap (`vka_mem.c` "File-backed pools", the moves in `vka_fileback.h`): the range read-only, writers held in the fault and pre-write hooks, the pages with data (pagemap present or swapped, not all zero) copied into the file's mapping elsewhere, that mapping moved over the range with one `mremap`, writeback started. The file's blocks are reserved first (`fallocate`), since a write into a hole of a shared file mapping on a full disk is SIGBUS; a full disk leaves the pool anonymous. A range the GPU is given later is placed as before and its file range punched; what is left goes back to anonymous memory at Finalize; a release drops it. `shader` covers `SHADER_CODE` pools; `texture` covers pools of `DM_MEM_FILEBACK_MB` (64) MiB or more that are not physical, virtual or compressible; each area load writes what the game streams into them to flash, so it is a choice, not a default.
- **Open:** the `shader` kind is the default for every game (`DM_MEM_FILEBACK` unset or `1`; `0` turns it off) since shader-code pools stay unplaced ([Shader-code pools placed though the GPU never reads them](#shader-code-pools-placed-though-the-gpu-never-reads-them-android)): shader code is written once a load and read on the CPU only, so its flash writes are about the game's shader code a boot (Ocarina of Time: up to its 345 MiB of pools). `texture` stays a choice. Not measured on a phone yet: free RAM, zram and flash writes (`[vk] file-backed pools:` and `[nvn] file-backed pools at present` lines give MiB moved and read back, the file's blocks and the process's write_bytes). Checked by `make -C dm/host/tests fileback` on Linux only (`t_android_fileback`).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (Anka Native's measurements).

### Texture cache thrash at a fixed image limit (Android)

- **Symptom:** on the phone, a game drops to 1-2 fps in one scene and the log repeats `image cache pruned: evicted N images (… MiB freed …)` (up to its 128-line cap); recording takes hundreds of ms a frame and the replay re-uploads the same textures every frame. Mario Kart World 1.8.0 at the 1,536 MiB default: about 840 textures (about 260 MiB) evicted and uploaded again each frame, 2 fps, recording 320-840 ms a frame. The Legend of Zelda: Ocarina of Time in Kokiri Forest at the earlier 512 MiB default: about 250 MiB a frame, 1.0-1.5 fps.
- **Cause:** the Vulkan replay's texture cache (`vka_tex.c` `vka_tex_prune_locked`) had a fixed limit (`DM_VK_IMG_LIMIT_MB`, 512, then 1536, then 3072) and an eviction rule that broke down at it. Over the limit the minimum age of a candidate fell to one frame, and candidates were taken in the order of the live-image array, not the least recently used first, so images used in the previous frame went before images unused for hundreds of frames. The prune runs on every texture miss in the middle of recording, so an image evicted early in a frame was needed again later in the same frame: once a scene's working set was larger than the limit, the cache uploaded it again every frame. Under the limit it also evicted one image unused for 15 frames (GPU-written for 30) on every miss, a slow churn of images used every few frames. No fixed number fits: Mario Kart World needs about 1.8 GB of images in a frame, and a phone with less RAM cannot hold 3 GB.
- **Fix:** general, in the Vulkan replay (`dm/gfx/vk_android/vka_texlimit.h`, `vka_tex.c` `img_limit_update` and `vka_tex_prune_locked`). The limit is measured every 60 frames: the images' bytes plus `MemAvailable` (`/proc/meminfo`) less a reserve (a 32nd of `MemTotal`, at least 512 MiB), capped by the image heap's `VK_EXT_memory_budget` budget (less a 16th) less what else uses the heap (enabled when the device has it; without it, half the heap), never under 512 MiB; the `image cache limit` line logs it and its inputs. `DM_VK_IMG_LIMIT_MB` still replaces it. Under the limit nothing is evicted. Over it, the candidates are images not held, not a playing video's, with their last submission done and unused for 2 frames (GPU-only content for 120 frames), evicted images that can be uploaded again first and then least recently used first, down to a 16th under the limit. When what is left is all in use, the cache stays over the limit: that frame does no further prune, and `image cache over its limit` is logged once (again only when the excess grows by 256 MiB). Checked by `dm/host/tests/t_android_texlimit.c`, which also simulates a working set larger than the limit (uploaded once, not again every frame).
- **Open:** a GPU-written image evicted after 120 unused frames loses its content (its storage holds what the CPU last wrote, not what the GPU rendered): the same as before, now only over the limit. A game whose per-frame working set does not fit in RAM still pushes the phone into swap: that is the limit's job only as far as stale images go.
- **Found on:** [Mario Kart World](../../dm/games/0400C3F00006E000/README.md) 1.8.0 (phone log 2026-11-07 17:03) and [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (Kokiri Forest), both on the Honor PNM-N49.

### Pipeline cache of earlier shader libraries (Android)

- **Symptom:** on Turnip (`DM_VK_DRIVER`), the game process vanishes 35-53 s after launch, before the first 3D frames, with no error line in the log; on Qualcomm's driver the same run plays. `dumpsys activity exit-info dev.nxnative.android` gives `reason=3 (LOW_MEMORY)`, logcat `lowmemorykiller: Kill 'dev.nxnative.android:game' … device is low on swap … thrashing`. `dumpsys meminfo <pid>` of the game shows `GL mtrack` at about 5.2 GB from the first seconds (Qualcomm's driver: under 1 MB), and `MemAvailable` drops by as much while the pipeline cache line (`[vk] pipeline cache …: N bytes read`) is logged.
- **Cause:** the Vulkan pipeline cache file (`vka_pso.c`, `vk_pipelines-<driver>.bin`) kept the shaders of every shader library ever played: each save writes back everything the cache was opened with plus what the run made, and nothing was ever dropped. Mesa's `vk_pipeline_cache_load` deserializes every object of the data a cache is created with, and Turnip's `tu_shader_deserialize` uploads each shader at once: its code, and private memory from the device's one private-memory buffer, which grows by powers of two to the largest per-fiber size asked, times the fibers of every SP (4,096 × 6 on the Adreno 840), each smaller buffer kept alive by the shaders that took it. Ocarina of Time's 72 MB cache held 1,791 shaders; two came from libraries before the [HMMA spill fix](shaders.md#gathered-hmma-tiles-kept-through-a-long-block-spill-registers-on-adreno) and asked for 80 KB and 54 KB of private memory a fiber (read from the ir3 variants in the cache file), so opening the cache committed 3.2 + 1.6 GB of kernel memory (with the smaller steps 5.2 GB) that cannot be swapped. With the game's own 4-5 GB the phone ran out of memory when the first 3D scene loaded. Qualcomm's driver does not commit memory for a cache's shaders when it opens it.
- **Fix:** general, in the Vulkan replay (`dm/gfx/vk_android/vka_pso.c` `pc_open_once` and `save_now`, `vka_shader.c` `vka_shader_lib_id`). The cache file is kept for one shader library: each save writes a stamp beside it, `<file>.lib`, the hash of the played library's header (chains, game, profile inputs, table and blob sizes, ABI). A file whose stamp is missing or names another library is not read: the run starts with an empty cache (logged `pipeline cache … is of another shader library` / `not stamped …: started empty`), and its first save replaces the file with this library's pipelines only. The replayer copies the stamp with the cache it seeds. A library update therefore cost one cold run, also when few or none of its shaders changed; since then the stamp lists the file's shaders and a file of another library is kept while they are mostly the same: [a shader library update that threw the pipeline cache away](#a-shader-library-update-that-threw-the-pipeline-cache-away-android).
- **Check:** (Honor PNM-N49, Turnip Mainline v32, 2026-11-08; runs in `oot-turnip/runs` of the game's work folder) with the old 72 MB cache: `GL mtrack` 0.08 → 5.2 GB within 1.3 s of the cache being opened, lmkd kill at 35-53 s (t-tur1, u-tur1, u-tur2). Without a cache file (`DM_VK_PCACHE=0`): `GL mtrack` 0.12 GB at start, 1.3 GB at 100 s, no kill (x-tur1). A cache of the current library only (y-tur1 cold, then y-tur2 warm): 823 shaders, 35 MB, largest private memory 4.6 KB a fiber, `GL mtrack` 0.43 GB after opening, 1.6 GB at 113 s, no kill. With the fix (APK of android-int fd88caa7 + this change): z-tur1 logged the old file `not stamped with its shader library: started empty`, `GL mtrack` 0.12 → 1.3 GB, no kill; z-tur2 read the stamped 19.6 MB file, 0.43 → 1.6 GB, no kill, frame 1,996 at 112 s; Qualcomm's driver (z-sys1) dropped its unstamped 92 MB file once and ran cold (frame 1,795 at 112 s, against about 5,500 warm).
- **Open:** a cold Turnip run of Ocarina of Time lost the device at frames 1,892-1,917 (x-tur1, y-tur1: `upload batch … not done in 60.0 s (-4)`, then `GPU hang`) while the warm run did not; its cause is not known. Some vertex shaders (`f4e8b877f70ea62f`, `4671e5e647fc5455`, about 100 KB of SPIR-V) take 6-7 s each to compile on Turnip, so the first 3D frames of a cold run wait about a minute. A shader of the current library that needs more than 64 KB of private memory a fiber would still cost Turnip gigabytes (and at 128 KB its per-fiber size no longer fits `SP_xS_PVT_MEM_PARAM.MEMSIZEPERITEM`, 8 bits of 512 bytes); the current Ocarina of Time library's largest seen is 4.6 KB.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) on the Honor PNM-N49 with Turnip.

### A pipeline cache that never saved a cold first 3D frame (Android)

- **Symptom:** every run starts cold again: the same pipelines log `pipeline cache miss` run after run, the cache file keeps its size (`pipeline cache: … bytes written` repeats one number), and a run stopped before it gets past a long stall of pipeline creation never gets further than the last.
- **Cause:** the cache was saved only from `vka_draw_sub_begin`, at the start of a submission (`vka_pso_save(0)`, at most every `DM_VK_PCACHE_SAVE_S` seconds). A game's first 3D frame can be one submission whose recording makes pipelines for a minute or more (Ocarina of Time: about 13,300 draws, mesh pipelines of 2.5-9 s each on Qualcomm's driver); a run that ends during it (stopped, killed, a test's time limit) saved none of them. The forced save at the end of a run does not come when the process is stopped.
- **Fix:** general (`dm/gfx/vk_android/vka_pso.c`): a graphics, mesh or compute pipeline that took over 1 s on the frame path also asks for the save that is due (the same rule, on the saver thread). Check (Honor PNM-N49, Qualcomm's driver, 2026-11-08, `oot-gmemloop/runs`): before, four 110 s runs each stopped at frame 1,802-1,804 with the file at 2,370,993 bytes; after, the file grew to 9.3 MB in the first run, 19.1 MB in the second (frame 2,532), and the third reached gameplay (frame 4,453).
- **Then (2026-11-08):** "the save that is due" still waited for the 20 s interval, so a slow pipeline made in the last seconds of a run was lost (compute pipeline `3d0d6d61bb9076e7`, 3.1 s, made 5 s after the last save of a stopped run and again 2.3 s in the next): a pipeline of over 1 s now asks for a save due 3 s after the last one (`DM_VK_PCACHE_SAVE_SLOW_S`; [a first start compiled a whole scene's pipelines in one frame](rendering.md#a-first-start-compiled-a-whole-scenes-pipelines-in-one-frame-on-the-vulkan-replay)).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) on the Honor PNM-N49.

### A shader library update that threw the pipeline cache away (Android)

- **Symptom:** the first start after an app or shader update sits on a black loading screen for minutes, every pipeline logged as made again (some 3.3 s each on Qualcomm's driver, 3-4 s on Turnip), although few or none of the game's shaders changed. The log's cache line: `[vk] pipeline cache …/vk_pipelines.bin (2923527 bytes) is of another shader library: started empty (its shaders would all be loaded; the next save replaces it)`. Every release changes the library's version, so every player met it after every update.
- **Cause:** the fix for [pipeline cache of earlier shader libraries](#pipeline-cache-of-earlier-shader-libraries-android) stamped the cache file with one number, the hash of the library's header (`vka_shader_lib_id`), and read no file of another library. The header changes with every rebuild, delta update or restamp (versions, profile inputs, sizes), so a library whose shaders were all byte for byte the same (Ocarina of Time's `v-0035e16073bf` after `v-72c5210a46e5`: only the header's version differs) dropped the whole cache. The header says nothing about which shaders changed, and a `VkPipelineCache` cannot drop single objects, so the stamp could not tell a kept pipeline from a stale one. Keeping the file is safe for correctness: the driver finds a pipeline by its own hash of the SPIR-V and state it is given, so an object of a changed shader is never used, only carried (and, on Mesa drivers, loaded when the cache is opened).
- **Fix:** general, in the Vulkan replay (`dm/gfx/vk_android/vka_pckeep.h`, `vka_pso.c` `pc_open_once` and `save_now`, `vka_shlib.c` `vka_shlib_entry_hash`, `vka_shader.c`). The stamp `<file>.lib` keeps its first line (the library; an older host reads only that) and adds the shaders whose pipelines the file holds, each with a hash of its library entry: the entry with its file positions zeroed, its binding records, its c1 bytes, and each module record with its bytes as stored, so the hash is the same in any library where the entry is byte for byte the same (a restamp, a delta update's reused entries) and differs for a changed module. A file of another library is read when its listed shaders that the new library has unchanged (live) outnumber the stale ones: the changed or dropped shaders of this update plus those counted at earlier updates the file was carried across, at most `DM_VK_PCACHE_KEEP` percent (default 50) of the live ones. Over that, or with no shader the same, the run starts empty and its first save writes this library's pipelines only, with the count back at 0, so a file holds at most one and a half times the shaders its library uses (by count) and a chain change (every module new) still starts empty at once. A stamp of the earlier format (one library, no list) is read once: it holds a single library's pipelines, which earlier runs of that library already loaded. Logged: `pipeline cache … is of another shader library: kept, N of the M shaders it lists are byte for byte the same in this one (K changed or dropped …), S stale shaders in the file in all …`; over the limit `… started empty, … over DM_VK_PCACHE_KEEP=50% …`; `DM_VK_PCACHE_KEEP=0` restores the earlier rule. The prewarm list is unchanged: it records pipeline keys, not driver code, so a record whose shader changed makes the new shader's pipeline in the background, which the game needs anyway. The per-driver files (`vk_pipelines-<driver>.bin`) each have their own stamp. Unit tests: `t_android_pckeep` (stamp text, keep and drop, the count over several updates), `t_android_shlib` (the entry hash under a restamp, a moved blob, a changed module or c1 byte).
- **Open:** not checked on the phone yet. The count covers library changes only: an app update whose host changes what it does to the SPIR-V before the driver sees it (`vka_spvpatch.c`, variants) also leaves stale objects in the file, as it always did, uncounted. ### GPU readback without an autorelease pool

- **Symptom:** GPU memory grows with repeated `nvnTextureReadTexels` calls on a long-lived game thread, even after each readback completes.
- **Cause:** the GPU path in `mtl_read_texels` runs outside a submission's autorelease pool. Metal's temporary command buffer and blit encoder keep the readback buffer alive in the calling thread's undrained pool.
- **Fix:** `mtl_read_texels` encloses texture resolution, readback encoding, the GPU wait and the CPU copy in its own `@autoreleasepool`. The guest-memory path needs no Metal objects.
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md), measured upstream in MacNativeGames commit `635fb31` and ported in [PR #195](https://github.com/seedds/nxnative/pull/195): about 130 readbacks a second retained 3.7 GB of GPU memory after 30 minutes. Those game measurements have not been repeated here.
- **Check:** `make -C dm/gfx/tests GAME=010015100B514000 check_t_readback` checks literal GPU and CPU readback pixels and observes the real readback buffer through a weak reference while the caller's outer pool remains open. Removing only the local pool leaves that buffer alive and fails the lifetime check.

### Completion readbacks survive a guest waiter's pool

- **Symptom:** process footprint and Metal allocation grow during stationary gameplay even after readback fences complete; the deferred-release queue and command allocator sizes remain bounded.
- **Cause:** `post_run` can execute on a long-lived guest waiter through the GPU-event fast-wake path, not only on Metal's feedback thread. `MTLBuffer.contents` returns an interior pointer (`NS_RETURNS_INNER_POINTER`), whose receiver may be retained and autoreleased by ARC. Explicit CF readback/visibility ownership is balanced, but those temporary receiver lifetimes escape into the guest thread's undrained outer pool. A submission's pool or a later callback on another thread cannot drain it.
- **Fix:** give the shared `post_run` body its own autorelease pool, ending after its mutex unlock. Guest-storage writes, event effects, absorption bookkeeping and existing GPU retirement fences keep their order. This caller drains its temporary completion objects before returning; this is not a new global drain-before-completion synchronization guarantee.
- **Check:** `make -C dm/gfx/tests GAME=<id> check_t_readback` gates real GPU feedback and exercises both `DM_NVN_FAST_WAKE=1` guest-owned completion and `0` callback-owned completion. It checks literal mirrored pixels and event visibility, delayed-feedback idempotence, then weak readback-buffer destruction after real retirement while the guest outer pool remains open. The lifetime assertion fails without the local pool and passes with it.
- **Found on:** [Tears of the Kingdom](../../dm/games/0100F2C0115B6000/README.md#memory), M2 Pro stationary cave route. A bounded paired diagnostic on chain `d1043b780a74` showed footprint growth of 617 MiB over about 86 seconds without the pool versus 1 MiB over about 83 seconds with it. This is route-local memory evidence, not an FPS improvement, complete allocation census or verified fix for an iPhone termination.
