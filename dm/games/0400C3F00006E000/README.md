# Mario Kart World (`0400C3F00006E000`)

A Switch 2 game: version 1.8.0, from a dump of one Application content (version 0) that carries the 1.8.0 code and data, with no separate update. SDK 21.4.0 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2. Nintendo EPD's engine (sead / agl / gsys, Phive, Havok 2023.2), modules `main` + `subsdk0` (NintendoSDK movie) + `subsdk1` (`nn::ecli`, Nintendo's embedded Mono runtime) + `sdk`. **Plays on Android** (current: 1.8.0 on a 16 GB phone, checked 2026-11-08; Supported on the player pages; needs a 16 GB phone, `readiness.tsv`). Earlier (resolved): the base build stopped at its first frames on the Mac and the arm64 Android emulator on its sparse textures, and on the phone its image allocations ran out ([Open](#open)); see [Boot (Android; 1.8.0)](#boot-android-180). Its closest relative here is [Donkey Kong Bananza](../040074A01BF12000/README.md) (same engine, NVN2, Ampere shader code).

## Boot (Android; 1.8.0)

Phone, 2026-11-03 (Honor PNM-N49, Adreno 840, system driver; test app `dev.nxnative.android.mkw` from `android-mkw2` f68cff94, `-PnxApp=mkw`; pack `Switch2/0400C3F00006E000-work/android-pack-1.8.0`, the dump at `Switch2/MarioKartWorld/base`, a new save folder): the modules load (subsdk0 and subsdk1 at their own bases, 924 of sdk's symbols bound to earlier modules), the heap is 7.47 GB in a 7.50 GB heap region (the formula above held), `nnMain` starts, the RomFS mounts, NVN2 device API 231.30 (SDK 21), and then, within 2 s of `nnMain`, the main thread stops: `CRASH sig=11 addr=0x20 pc=main+0x69c020`, right after it started the "Prepare Thread" (last svc 0x9). No frame, no image made, so the image allocations were not reached; RSS was not sampled (the process ended inside the first 2 s window).

- The fault: `main+0x69bfd0` (a virtual function, slot 0xc0 of the vtable at `main+0x367a9e0`) loads the global at `main+0x37be900` (through the GOT slot `main+0x36d3a48`) and calls through its +0x20 without a null check; the global was still 0. **Cause (resolved):** the game creates its graphics system, the object that global holds, only when NVN reports major 231 and minor 39 or more (`main+0xdd0890`, then the 0x260-byte allocation and the store at `main+0xdd0900`), and the host answered 231.30. NVN2's versions move with the SDK (21.4.0's sdk answers 231.39 and GPU code minor 20); the host now reads them from the game's own `sdk` (`dm_sdk_nvn2_item`, from upstream nxnative c8521eeb: [The Switch 2's device values](../../../docs/reference/nvn-objects.md#the-switch-2s-device-values)). Not a scheduling problem: the reader and the writer are both on the main thread.
- After that fix (a772aae3; retries m2-m4, 2026-11-03): NVN reports 231.39, the graphics system comes up (window 3840x2160, 3 textures; 2.83 GiB of pools placed, 60 pools, RSS 6.6-6.8 GB within 8 s), and the boot stopped in turn on three SDK calls that reach services the host does not serve: `nn::hid` Jcms / Nmouse (abort 0xe15; hooked, e37131ab), `nn::chat::AttachToRoomInfoChangedEvent` (a null read at `sdk+0x6bc148`; hooked with the sharing key calls, ddb59130), and now (current) `nn::chat::CalculateLocalCameraVideoBufferSize` aborts (`sdk+0x6bf2c8`): it checks GameChat's initialize count (`sdk` data through `[sdk+0xe28038]`), which stays 0 because the host takes over `nn::chat::Initialize`. The size itself is pure: it calls `nn::chat::gsv::MakeImagePreference` and `CalculateRequiredBufferMemory` (imports the sdk takes from `main`). **Resolved (a4cb183f):** every GameChat call the game imports is answered as one state, with no camera ([GameChat at boot](../../../docs/reference/services.md#gamechat-at-boot)).
- After that (m5-m12, 2026-11-03, a4cb183f and later): the game sets up its camera storage at boot whatever the chat state (`main+0xd32270` local, `main+0xd31b20` remote: 384x216, 3 pictures each) and makes a texture of each picture through `nvnNativeImage`; it aborts if one fails. Next, its own `nn::camera::Initialize` (`main+0xcdebc0`, called by its camera manager at `main+0xcdc344`) aborted twice. First `nn::gs::sdk::CheckGraphicsSystemInitialized` aborted at `sdk+0x46e8b8`: the sdk's flag is set only by `BootGraphicsSystem`, inside the `nv::InitializeGraphics` the host takes over. Then `nn::camera::sdk::CreateCameraContext` failed with 0x30af3 (no graphics server session). Both are answered now: the check by the host's `nv::InitializeGraphics` (`hle_nv.c`), the context by a host session with zeroed answers (`hle_sf.c` `dm_sf_host_session`; the game sends command 3 "Default" and command 21 on it).
- The renderer then runs: save mounted, audio out, the replay worker, bindless tables, 29,324 images, the first render targets (1280x720, 2560x1440, 1024x8192). No frame was presented before the phone ran out of memory, 11-14 s in. Either `MemAvailable` fell under 700 MB (the run script's stop) or the low-memory killer ended the game process (m9, m10). The `memory:` lines (m12) at that point: 4,494 MiB of placed pools, 3,204 MiB of images (sparse images counted at their full virtual size), and 1,488 MiB of upload scratch, all of it held by the submission being recorded ([Upload staging grows within one Vulkan submission (Android)](../../../docs/reference/memory.md#upload-staging-grows-within-one-vulkan-submission-android), resolved in 9d48710d: see the next item). The game process had PSS 6.1-6.7 GB. `MemAvailable` was 4.8-5.4 GB at launch, with the phone's other apps resident.
- VmRSS overstates the game: each placed pool block is mapped twice, at its guest address and at the driver's own map, and RSS counts both (m7 smaps: 8.59 GB RSS but 4.3 GB PSS in `/dev/kgsl-3d0`). The run script now stops on PSS (10 GB) and on `MemAvailable` under 700 MB, not on RSS.

## Speed below 60 (Android; 1.8.0)

Resolved in code (2026-11-10, phone check open): the framework's own step count is what the frame rate cap now drives, see [Frame rate cap](#frame-rate-cap-android-180). The step count at `fw+0x214` is also the present interval, and every update loops it, so an interval-2 frame runs two 1/60 s steps (the earlier correction here, "interval 2 adds no step", was wrong). The paragraph below is history: its "nothing found yet that runs the update loop more than once a frame" was found the same day (`main+0x23fd37c`).

Correction (2026-11-10, disassembly of 1.8.0's main): the framework does have a dynamic interval controller of its own, not sead's; see [Present interval 1 ↔ 2 in races](#present-interval-1--2-in-races-android-180).

Open (2026-11-10), superseded: players report the game slows down when its frame rate drops or is limited. Its framework has no sead dynamic interval controller, so [the decoupling of sead's controller](../../../docs/reference/frame-rate.md#a-game-whose-speed-follows-its-present-interval-runs-slow-when-frames-come-late) does not reach it (`dm/tools/nso_code.py` `sead_find` finds nothing in 1.8.0's main, as it should): the frame function (`main+0x25a8d00`) waits for a fixed interval (`framework+0x88`, the wait at `main+0x25a8b50`) and nothing in the framework writes the frame rate field (`framework+0xe0`), which only its VRR path reads (`main+0x25a8710`). The game steps by a fixed 1/60 s: the constant (0x3c888889) is built in code at 20 places in 18 functions (for example `main+0x8df54`, which stores 1/60 and a scale of 1.0 into a step object, `[x19+0x500]`, and three places in `main+0x208200`), none read from the frame time. A variable step would have to reach every one of them and everything that counts frames (the race timer, ghosts and time-trial records, online races that exchange inputs per tick), and would change the physics' results: ghosts and online races depend on the same steps on every machine. The safe form is the game's own: more fixed steps in a frame, not a longer one; nothing found yet that runs the update loop more than once a frame (the framework's mode `+0x50`, 1 or 2, changes only its wait). Not changed; the profile has no `fps_decouple`, so the launcher keeps 60 / 30 / 20 locking for it. An experimental option (the step from the measured frame time at those sites, off by default) was looked at and not built (2026-11-10): the 20 places are of three kinds, and none is the kart simulation's step. (1) Per-second values turned into per-frame ones once, at setup (`main+0x208200`, three `fmul` by 1/60 stored into an object, called from `main+0x200920` and `main+0x253d8bc`; also `main+0x2817324`, `main+0x28224a8`): the simulation then advances by those per-frame values every frame, so a frame-time step cannot reach them. (2) Step objects set to {1/60, 1.0} (and {0.9, 1/60, 1.0}) when a state changes (`main+0x8de90` three times, `main+0x363240`, `main+0x367e20`): written once, not every frame. (3) A 1/60 argument to a subsystem update (`main+0x73e550` and `main+0x73e600`, six callers such as `main+0x2141f78`, `main+0x22831c4`), which also compares a frame counter: a longer step there would speed those subsystems while the karts, stepping by frames, stay slow, so effects and animation would drift from the race. Full speed for the race needs the kart simulation's update found and run more than once a frame (a fixed step, so ghosts, time trials and online races stay exact), not a variable step.

## Present interval 1 ↔ 2 in races (Android; 1.8.0)

Current (2026-11-10, disassembly of the 1.8.0 main, module `d00e4f39…`, decompressed from the work folder's `testpack-v6/src/main`; `survey/main.bin` is the earlier build): the host's `the game sets present interval 1 → 2 (from main+0x69ce28)` lines (696 in one 65 s run) are the game's own controller, working as on the console.

- The call is `blr x8` at `main+0x69ce24` (the log names the return address) to `nvnWindowSetPresentInterval` (the proc variable at `0x3779428`), in `main+0x69cbb0`, slot `+0xe0` of the framework's vtable (`0x367a9e0`, set by the constructor `main+0xdcea00`, which also sets `+0x210` = 0 and `+0x214` = 1). Each frame it compares `fw+0x214` with the window's cached interval and calls the setter when they differ.
- The controller (`main+0x69cc54`-`0x69cce8`): `fw+0x210` = 1 or 2 forces that interval (0, automatic, from the constructor); bit 0 of `fw+0x22c` resets it to 1. Otherwise an accumulator `fw+0x218` += T − interval/60 s (in ticks), clamped to ±66.7 ms (constant at `0x2cf4ab4`); q = acc / 16.7 ms (`0x2cf49dc`), truncated; interval = 1 if q < 0, else min(q + 1, 2). So the interval goes to 2 once the overrun adds up to 16.7 ms and back to 1 as soon as it falls below; no other hysteresis.
- T (`fw+0x128`) is the larger of the CPU update span (`GetSystemTick` after the update minus `fw+0xf0`, the tick taken after the previous frame's waits) and the GPU span (vfunc `+0x118`, `main+0x69ced0`: `nvnDeviceGetTimestampInNanoseconds` of the frame's end counter, written by `ReportCounter` TIMESTAMP after the draw, `main+0x69c230`, read after `nvnSyncWait` on the frame's sync, back to ticks with `ConvertToTick`, minus `fw+0xf0`). The pacing waits (present, acquire) are outside T: the host's present timing does not feed the decision. The host's counters are right: the 31.25 MHz tick on the same epoch as the GPU report's `guest_ns`, written when the submission completes (`vka_exec.c` `post_run`, before the fence is seen done).
- With a work time W between 16.7 and 33.3 ms the share of interval-2 frames settles near (W − 16.7) / 16.7, mostly single frames, two switches each; 10.7 switches a second fits W ≈ 19 ms. The phone's races measured 22-23 ms from recording start to GPU end (`pace` lines: replay recording 20-21 ms a frame for 2,300-2,900 draws, its CPU all of it, at 2.2 / 1.9 GHz caps from heat), interval 2 32-40 % of the time, 42-45 fps. The console would do the same at that load. Corrected (2026-11-10): an interval-2 frame runs two 1/60 s steps, since the count at `fw+0x214` is both the steps every update loops (`main+0x23fd37c`) and the interval set at the next frame's start; the race keeps its speed through the switching, give or take the one frame between the pick and the interval.
- Not changed in the host: overriding the game's interval to 1 would only show the late frames unpaced. A shorter frame (the replay's recording cost a draw, heat) is what gives 60. Writers of `fw+0x210`: see [Frame rate cap](#frame-rate-cap-android-180).

## Frame rate cap (Android; 1.8.0)

Current (2026-11-10, code and unit tests; phone check open). The launcher's Frame rate cap (Game settings and the in-game panel: the game's own, 60, 30, 20) now holds 30 and 20 at full game speed, through the framework's own steps per frame. Before, the profile had no limiter the host writes, so the cap was not applied (`present cap 30 fps not applied: this main has neither a frame step nor an engine frame limit the host writes`), and a plain frame limit would have run the race at half speed. General mechanism: [A framework's fixed steps per frame hold the frame rate cap at full speed](../../../docs/reference/frame-rate.md#a-frameworks-fixed-steps-per-frame-hold-the-frame-rate-cap-at-full-speed); this profile's row is `fps_steps` in `game.tsv`.

- procFrame (`main+0x69cbb0`, the framework at `[[main+0x37c8410]+8]`): (1) if `fw+0x214` differs from the window's cached interval, `nvnWindowSetPresentInterval(fw+0x214)`; (2) the pick: mode `fw+0x210` 0 = the accumulator above (1 or 2), 1 or 2 = that count (`main+0x69cdbc`), any other value leaves the count; (3) the calc tree (`main+0x69c950`), in which the race's update loops `fw+0x214` times (`main+0x23fd37c`: `main+0x23b3b80`, `main+0xe06610`, `main+0x23c2fc0` per step); (4) a global step counter (`main+0x37c8438`) += the count; then the frame's waits and present. A state's step object copies the count at its start (`main+0x2977b90`).
- Writers of the mode: the player count at race setup (`main+0x2d1c80`: 0 for one or two players, 2 for three or four), scene code that sets 2 (`main+0x2400744`, `main+0x2400990`), 1 (`main+0x23b0870`) or a table / config value (`main+0xc82988`, `main+0x1ce7658`, `main+0x2401548`). One list copies the mode into the count (`main+0x4bff84`). Readers that adjust per-frame values for 30 fps where the mode is 2: `main+0x293f30`, `main+0x3700f4`, `main+0x2a8a5b4`; `main+0x26fdd4` where it is 1.
- What the host writes (`hle_fpslock.c` `steps_tick`, every present): 30: mode 2, the game's own 30 fps (two steps, interval 2, its 30 fps adjustments). 20: the count 3 and mode 3, outside the pick's values, so the count stays (three steps, interval 3). 60 and the game's own: nothing; the game's mode 0 goes 1 ↔ 2 as above. A mode the game sets while the cap holds (a scene, a race's setup) is overwritten at the next present and given back when the cap goes up.
- Input: `nn::hid::GetNpadStates` is called only from `main+0x2590aa0` (16 states of history each), which nothing calls directly (a virtual call, sead's controller update), so it is not in the step loop: one read a frame, as in the game's own two-step mode; the two or three steps of a frame see the same pad state. Audio is the system's renderer, not paced by frames; with game time = real time its sounds stay in step.
- Risks: at 20 the four 30 fps readers above take their 60 fps values (their per-frame values move at a third of the speed they would at 60, whatever they are: not identified). A cap changed in the middle of a race reaches the state's step object only at the next state. Three steps a frame is beyond the game's own range (2); the update loops any count. 15 fps (4 steps) is not offered. The time a frame owes is not measured: a frame later than its interval slows the game, as on the Switch (the parked `mkw-fixstep` branch's gate wrote the steps the time owed instead, at the cost of a rewrite of the game's code).
