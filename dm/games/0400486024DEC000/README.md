# The Legend of Zelda: Ocarina of Time

The Switch 2 base dump reaches its title screen on the Mac. VideoToolbox decodes the 1920×1080 AV1 track. The movie library runs its NDVE compute shaders to produce the background behind the logo and menu. Gameplay validation is open.

## Profile

SDK 22.2.8, NVN API 231.40, with Nintendo's sead, agl and gsys. The three loaded modules are `main`, `subsdk0` (NintendoSDK_movie), and `sdk`. The NPDM declares 48 MiB of system resources. Startup requests a 6.20 GiB heap, which fits in the profile's 12 GiB reservation with the stack and alias regions. The registered build is the supplied base dump (`v0`). `vk_prewarm.bin` is the Android host's prewarm seed (dm/games/README.md).

`fps_limit 30` (Android): the host's frame limiter holds the game to 30 fps by default ([dm/games/README.md](../README.md), `hle_fpslock.c` `fps_limit_wait`); the launcher's Frame rate cap (60 / 45 / 40 / 30 fps) and `DM_FPS_LIMIT` override it. `DM_FPS=30` does not cap on Android (it moves only the frame statistics' targets). The game has a frame step ([`patches.py`](patches.py), v131072): the limit is the step's cap in whole vsyncs (30 fps = 2 vsyncs a frame; 45 and 40 run at 30, 20 at 3 vsyncs), and `fps_target 60` has the host decide the step with no limit too (current, 2026-11-10: [a frame limit on a game with a frame step ran it slow](../../../docs/reference/frame-rate.md#a-frame-limit-on-a-game-with-a-frame-step-ran-it-slow-android)). Measured with `DM_FPS_LIMIT=30` in Link's house (2026-11-10, Qualcomm's driver, `DM_VK_EVENT_WAIT=0`): 30.0 fps in every window, frame time p50 33.33 / p95 33.40 ms, the phone 51 → 62-64 C over a run, where uncapped it ran 37-38 fps from cool and 27-32 hot (p95 38.5, max 56.5 ms) and warmed 50 → 74 C; a hot phone (67 C) cools under the cap (→ 63 C). Kokiri Forest runs below 30 anyway. Frame generation counts the limit's period as the game's (two refreshes of a 60 Hz panel a frame: one generated frame, 60 shown). It does not step by the time between frames: under the limiter alone it ran at half speed at 30 (resolved 2026-11-10 by the frame step taking the limit; the phone check of speed is open).

## Render size

Current, 2026-11-10 (static, update v131072's main `e0f3ccfa`; phone check open). As on Mario Kart World, the size the game draws at follows the operation mode and the Switch 2 graphics scale, not a window getter: the swap chain is 3 × 2560x1440 and the game shows the size it picks as the window crop (`[nvn] WindowCrop 0,0 1920x1080` in handheld runs). The applet-state object (`main+0xe376a0`) reads `oe::GetCurrentGraphicsScale` beside the operation, performance and focus modes, and its notification handler (`main+0x3bc0230`) copies the handheld flag (operation mode not console) and the scale into bytes +0x546 and +0x549 of the graphics settings. The display state (`main+0x6502e0`) applies them as +0x547 (mode) and +0x54a (scale) and asks `main+0x112c5e0` for the crop, an index into the size table at `main+0x3f58540` (640x480, 720x480, 1280x720, 1600x900, 1920x1080, 2560x1440, 3840x2160):

| mode | scale 0 | scale 1 | scale 2 |
|---|---|---|---|
| handheld | 1920x1080 | 1920x1080 | 1280x720 if bit 1 of the handheld parameters' first word (+0x2f8) is set, else 1920x1080 |
| console | 3840x2160 | 2560x1440 | 1920x1080 |

The crop is the smaller of that size and the mode's base size times the scale's factor (per-mode parameter blocks of 0x208 bytes at +0xf0; the factors at +0x1e4 + 8 × scale). The scene is drawn smaller still by the dynamic resolution and agl's upscaler takes it to the crop. The game has no `movz w0,#imm; ret` getters for 2560 / 1440 (the two that exist belong to the movie decoder's `RouleauRGBX1Component` templates), so `window_fn` is not its lever; its dynamic resolution moves the NDSR rate, not a level list, so neither is `res_levels`. The scale's other readers (`main+0x224b20`, `main+0x22c400`) draw something only at scale 1 (console).

The profile's `graphics_scale` rows give the Android launcher's Game resolution: Phone 1080p is handheld scale 0 (1920x1080), Phone 720p handheld scale 2 (1280x720, if the handheld parameters allow it), Phone 1440p and Original console scale 1 (2560x1440 at most, the console's docked picture; the base size times the scale's factor may cap it lower, as Mario Kart World's 2048x1152). Console mode changes more than the size: the game sees a docked console (its controller and the two scale-1-only passes above). Phone 540p and 480p have no row: no mode and scale gives less than 1280x720 (the table's 640x480 and 720x480 are never picked), so the launcher gives them the smallest row, Phone 720p's (`Profile.resolutionEnv`: a size without a row takes the largest row that fits in it, else the smallest). Open: the phone runs that confirm the crop for each choice (the log's `oe: graphics scale` and `WindowCrop` lines), what scale 2 gains in frame and GPU time, and whether console mode plays right on the phone (controls, frame rate).

Live from the in-game panel (2026-11-10, by disassembly; phone check open): the game turns on the graphics scale change notification (`main+0x3bc0170`), and the notification handler above takes message 300 to `oe::GetCurrentGraphicsScale` (`main+0x3bc038c`; stored at +0x2c, bit 0x100 of its change mask, bit 1 for message 30), so the panel's Resolution row changes the size while the game runs ([Graphics scale changes while the game runs](../../../docs/reference/services.md#graphics-scale-changes-while-the-game-runs-message-300)). Original and 1440p ↔ the others also change the operation mode.

## Mac dry run

Use the rewritten `patched_v0` and the original extracted `base/romfs`. Build the host with `make -C dm/host GAME=0400486024DEC000` and use the [Mac shader build](../../../docs/development.md#build-by-hand-mac). From the repository, set `DUMP` to the folder containing `base` and `WORK` to the build and run workspace beside it.

```sh
mkdir -p "$WORK/run/save" "$WORK/run/temp" "$WORK/font"
python3 dm/tools/make_ext_font.py "$WORK/font/nintendo_ext.ttf"
DM_ROOT="$WORK" DM_ROMFS="$DUMP/base/romfs" DM_SAVE="$WORK/run/save" \
  DM_TEMP="$WORK/run/temp" DM_MSL_DIR="$WORK/shader/cache" DM_FONT_DIR="$WORK/font" \
  DM_NVN_SHMAP="$PWD/dm/games/0400486024DEC000/shader_map.tsv" \
  DM_WINDOW=1 DM_METAL_HUD=1 DM_AUDIO=1 \
  dm/host/dmhost "$WORK/patched_v0"
```

The profile prewarms the 11 NDVE compute pipelines used by the title. On the Apple M5 that took 17.7 s on a cold run, with a progress screen, and 7 ms with the archive warm. Compiling the same pipelines during the first submission had blocked the first movie frame for tens of seconds. The larger scene shader set also triggers a separate graphics-pipeline prebuild. On the first run with that set, the startup screen took 86.9 s to hand out all pairs, and the remaining workers finished after 110.6 s total.

Start a new game to reproduce the opening scene transition. With the test save and title flow, `DM_KEYS=f2600:A,f2950:A` advances the menu automatically. `DM_NVN_SHDUMP` saves control sections and code for missing keys to the directory it names.

For a run past the opening, copy the committed save folder to the new run's `DM_SAVE` and load slot 00 from the menu. The checkpoint contains both `slot_00/progress.sav` and `slot_00/caption.sav`. The load screen identifies it as **Kokiri Forest Autosave**. A windowed reload reached the playable scene with the HUD and controls, so rendering can be tested without replaying the movie.

## Found on this game

- [Graphics scale changes while the game runs (message 300)](../../../docs/reference/services.md#graphics-scale-changes-while-the-game-runs-message-300): its notification handler re-reads the scale on message 300 ([Render size](#render-size)); Game resolution is live from the in-game panel (2026-11-10, phone check open).
- [The Switch 2's graphics scale sizes Mario Kart World's 3D scenes](../../../docs/reference/services.md#the-switch-2s-graphics-scale-sizes-mario-kart-worlds-3d-scenes): the game's crop follows the operation mode and the graphics scale too; the profile's `graphics_scale` rows give the Game resolution choices ([Render size](#render-size)).
- [A game whose speed follows its present interval runs slow when frames come late](../../../docs/reference/frame-rate.md#a-game-whose-speed-follows-its-present-interval-runs-slow-when-frames-come-late): the rewriter finds sead's frame-rate controller here (v65536 `main+0x3af19ec`, v131072 `main+0x3b4f05c`, `sdiv w1, w8, w21`) and leaves it as it is: the profile has no `fps_decouple sead`, because that gate would not reach this game's time step. The controller hands its rate to setFrameRate (`main+0x4dc0f0`), which turns it back into a present interval (60 / rate when that divides 60, else the next rate that does), and then the framework's setInterval (`main+0x346c5c0`) sets the window's interval and the framework's rate field (`+0xfc = 60 / interval`) from the controller's own interval (`+0x48`); `+0xfc` is read as a rate only by the framework's frame wait (`main+0x346c920`, until 1 / rate after the frame's start). The game time steps by that interval ([`patches.py`](patches.py), the frame step at `main+0x3b4f074`), not by the time between frames as the `fps_limit` text assumes: speed is right only while the interval the controller picks matches the rate the host presents at. Resolved (2026-11-10): the frame limit now drives that frame step ([a frame limit on a game with a frame step ran it slow](../../../docs/reference/frame-rate.md#a-frame-limit-on-a-game-with-a-frame-step-ran-it-slow-android)), so the speed holds at 60 / 30 / 20 fps; the controller's own choice kept interval 1 at 25-33 fps because the framework's measured frame costs (`+0x148` / `+0x150`) said 60 fits (why, open). Open: the phone check of speed under `fps_limit 30`, `DM_FPS_LIMIT=20` and no limit.
