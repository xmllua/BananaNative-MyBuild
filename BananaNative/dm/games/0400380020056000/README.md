# Splatoon Raiders (`0400380020056000`)

A Switch 2 game: update v65536 over the base game, SDK 21.4.4 built for the Switch 2 (`Ounce`), NVN2 API 231.39. Nintendo EPD's engine (sead / agl / gsys, Phive, Havok), modules `main`, `subsdk0` and `sdk`. **Plays on the Mac** (M4 Pro): the opening, character creation, the first level's beach, inking, grates and the first Salmonids, about 4.5 minutes in the last session with no crash (upstream nxnative's measurements; the Mac facts below are upstream's). No IPA has been built. **Not yet run on Android** ([Android](#android)).

## Files

- Built from a dump folder (`base/`, `updates/65536/`). The display version `v65536` is a placeholder: no control data gave a better one.
- Update RomFS: 46,354 files, 13 GB.
- Shaders: 27,195 in [`shader_map.tsv`](shader_map.tsv), from `Shader/*.Nin_Ounce_NVN2.bfsha.zs`, `Sample.Nin_Ounce_NVN2.release.sarc.zs` and `Lib/agl/*`. A full build takes about 34 minutes from scratch, 13 with the Metal cache. 22,147 pipeline pairs prebuild with none failing, in about 200 s.

## Shaders

27,192 of 27,195 build on chain `9bb5d8678204`. The 3 that do not (current): 1 on instruction 0x481, and 2 compute shaders of `agl_technique_pfx` that Metal refuses (`bracket nesting level exceeded`). `fa072659664b2d38` in `agl_common`, which the game asks for at boot, builds now.

## Rendering

- The first level renders at 1707x960 (R11G11B10F), with what the pass inputs suggest is a spatial anti-aliasing step, and one compute program of agl's upscaler (`c1b8edc09e3313b1`, one texture in, no earlier frame) takes it to 2560x1440; that is copied to the 3840x2160 window. The dialogue scene renders at 2560x1440.
- agl's `agl_ndsr.pck` is the same file in the debug and the release library (header word `0x40100`). Its 20 compute variants read colour that is encoded already and come in twos: no decode at the end, or a half-float sRGB decode clamped to 0-1. All past logs name only the 10 that decode; the first level dispatches `c1b8edc09e3313b1` (1707x960 → 2560x1440) and `30d8ee33de9dee85`. With upstream's DM_UPSCALER=metalfx (a Mac switch this repository never had) its GPU p50 was 8.05 ms against 9.1 ms with the network on the beach (M4 Pro, windows of 300 frames, a loaded Mac; the frame rate stays 60 either way), and the picture matches ([An upscaler's colour read from its code](https://github.com/seedds/nxnative/blob/main/docs/reference/rendering.md#an-upscalers-colour-read-from-its-code)).
- Ink is a 6400x6400 RG8 map with a Depth32F-S8 (880x880 in the dialogue scene). A stamp writes depth and stencil in its rectangle, then paints with a barrier before each draw, sampling the map; then about 150-285 occlusion queries a frame measure the map, each its own `SetRenderTargets`, uniform updates and report. These drew the costs on this page.
- Frame and GPU time, M4 Pro, windows of 300 frames: the still beach about 15 ms of GPU at 60 fps (150-190 ms, about 6 fps, before the fixes below). The last play session: a median frame of 16.6-16.9 ms; the slowest 5 % at 17.1-17.5 ms in its last stretch and up to 22 ms in the heavier moments; GPU median 10-16 ms, slowest 5 % 13-22 ms. So 60 fps is not held everywhere (current), and that session shared the Mac with a regression run. The ink map's passes are a large part in inked scenes: 0.32 ms each ([A render area for passes on very large targets](https://github.com/seedds/nxnative/blob/main/docs/reference/rendering.md#a-render-area-for-passes-on-very-large-targets)). Each stamp also took a whole-map snapshot (0.76 ms) and a pass of its own; it now reads its pixel of the map from the tile (resolved, [#1063](https://github.com/seedds/nxnative/issues/1063)): on the route to the first beach, 4.2 → 0.6 snapshots a frame and GPU p50 12.8 → 9.5 ms, M4 Pro. Inked stages are not measured here (the reporter's M2: 22–26 → 13–16 ms with their first patch). A few single frames take 130-535 ms; the worst show little submit time and no new pipelines, and one of 373 ms is nearly all submit time; not traced (open).
- The first boss fight's third stage (resolved, 2026-11-05, 16 GB M2 Air, docked): it measures its ink map with about 1,550 occlusion queries a frame, each after 7 inline updates of the query block and with colour writes masked off (`wm=0xfffffff0`), so those draws read the map directly rather than from the tile. Their 11,010 writes in one submission overflowed the host's list of queued writes, and from then on each query ended its render pass, at 1-2 fps ([the reference entry](https://github.com/seedds/nxnative/blob/main/docs/reference/rendering.md#a-submission-past-8192-queued-writes-counted-as-writing-everywhere)). With a list that grows as needed (a larger fixed limit in the measured build), the stage holds a median of 17.7-19.9 ms with at most 118 render passes. A later stretch of the same run sat at 32-34 ms (frames 15,300-16,200); where in the game that was is not known (open).
- Focus: the game stops drawing its 3D scene when the window loses focus (10 passes, GPU 2 ms), so a frame rate read then says nothing.

Open on Android, by what upstream found:

- The ink map's measurement: the game reads 150-1,550 occlusion queries a frame, and the replay writes every samples-passed counter as 1 ([Report tables that dropped entries](../../../docs/reference/rendering.md#report-tables-that-dropped-entries)). What the game does with the counts is not known.
- [A store only a dispatch's first invocation makes](https://github.com/seedds/nxnative/blob/main/docs/reference/shaders.md#a-store-only-a-dispatchs-first-invocation-makes): `Hoian_Proc` resets its append counter in the first invocation; Adreno gives workgroups no order either, so the plants may flicker. A port needs a SPIR-V pass in `vk_android_spv.py`, a reflection record and a fill before the dispatch (a Vulkan chain change).
- Every inline uniform update ends the replay's render pass (`vka_state_op`), so the ink queries' 7 updates each split the 6400x6400 map's pass; and its passes cover the whole target ([A render area for passes on very large targets](https://github.com/seedds/nxnative/blob/main/docs/reference/rendering.md#a-render-area-for-passes-on-very-large-targets)). Both are frame-rate costs, not measured on a phone.
- A draw that samples an attachment of a pass continued by the same `SetRenderTargets` with no barrier between does not end the pass (upstream's depth rules of [Setting the same targets again continues the pass](https://github.com/seedds/nxnative/blob/main/docs/reference/rendering.md#setting-the-same-targets-again-continues-the-pass)): on the Mac that drew the water's grey blocks.

## Driving it on the Mac

The work folder's `run/drive.sh <name> <secs> "<sec> <control line>"…` boots in a window with the HUD, raises it and appends control lines (`A~0.1`, `LUp~4`, `shot <path>`, `passdump 1`, `texdump <path with %d>`). With the save at the start of the dialogue, four presses of A get to the beach at about 75 s. `DM_NVN_SHOT=<frames>:<relative path>` takes consecutive frames: the path must have no space, as the driver's environment is split on them.
